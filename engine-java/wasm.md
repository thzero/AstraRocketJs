One fix was required to get there: info.openrocket.core.util.ArrayList.clone() did (ArrayList) super.clone(), which WASM-GC's strict typing rejects (TeaVM's java.util.ArrayList.clone() doesn't preserve the subclass). Changed it to new ArrayList<>(this) — behavior-preserving, and it also makes strict=true viable on the JS backend.


So: yes, engine-java can run as WASM-GC — same numbers, ~2× faster, smaller. With honest caveats:


Only one scenario tested. WASM-GC's strict typing surfaces casts the JS backend silently tolerates; ArrayList.clone was the first. A real port needs the full parity battery run under WASM to flush out any others.
The ArrayList.clone edit is in src/java (regenerated by extract), so it must become a patches/ entry to persist. Behavior-preserving, but re-run full JS parity to confirm.
WASM-GC needs modern browsers (Chrome 119+ / FF 120+ / Safari 18+) — drops the older-browser reach the JS build has, so it'd likely be an opt-in/second target, not a replacement.
Web integration differs: the app currently does a synchronous import of the JS engine; WASM needs the async TeaVM.wasmGC.load(...) loader — a real (small) plumbing change to make the engine init async.
Spike changes are uncommitted: the additive teavm.wasmGC block in build.gradle and the ArrayList.clone edit.
