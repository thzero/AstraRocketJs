## Roadmap

- **Multi-stage flight validation** — multi-stage rockets are now **authorable** (the **+ Stage** button adds a booster via `treeEdit.ts addStage`; `PropertyPanel` exposes `separationEvent`/`separationDelay`/`separationAltitude`, and the motor card gates upper-stage ignition to `ejectioncharge`/`burnout`/`never` via `isUpperStageMount`) and **simulate** as independent branches (`FlightResult.branches[]`, plotted per-stage in the Flight charts). Static mass/CG/stability match desktop OpenRocket (`Fireball.ZL1.DD.multi`). **Still missing:** a differential test of a staged *flight* (separation + upper-stage ignition timing, booster descent) against desktop OpenRocket, and the multi-stage report-rebuild path is untested (see `AUDIT.md`). To close: add a staged booster+sustainer flight fixture and validate the flown trajectory end-to-end.
- **Recovery-device packed length/radius** — the only recovery feature not yet wired: parachute/streamer canopy/strip + line **materials**, **shroud lines** (count/length), and streamer **Cd** are all editable now, but *packed* dimensions aren't. The engine's `ComponentFactory` (see `openrocket-engine.mjs`) doesn't read `packedLength`/`packedRadius` from the tree node and never calls `setPacked*`, so packed size can't affect mass/CG without an **engine change** (add the reads in the Java `ComponentFactory`, rebuild TeaVM). `orkFile.ts` export also hardcodes `<packedlength>0.025</packedlength>`/`<packedradius>0.0125</packedradius>` — a round-trip discards the real values. To finish: read the node keys in the Java factory + set them, then add editor fields and make `orkFile` import/export the node keys instead of constants.
- **Landing / ground-track** - DONE. The export half was always built (`flightPathExport.ts` ships KML / GPX / waypoint CSV, so "where does it land" was answerable in Google Earth). Both missing pieces are now in: the flight CSV carries **East** and **North** columns beside altitude (`Px` / `Py`, already in the default summary series, so no engine work), and the app has a **Ground track** view - a sixth `ViewMode` beside Flight and 3D path. `services/groundTrack.ts` holds the pure half (polyline, landing point, distance and bearing from the pad, a square pad-centered extent, 1/2/5-ladder range rings) and `GroundTrack.tsx` draws it north-up with the pad at the center. It reuses the chart's `buildTraces`, so the multi-sim overlay and per-stage colors come along. Still open from the original entry: the drift ELLIPSE across a wind sweep, which needs a sweep to exist first.
- **`.rse` (RockSim) motor import** - currently `.eng` only. **Wanted for HYBRIDS specifically; see (d) in Immediate above.** Check the extraction path first: `RockSimMotorLoader.java` (and `RockSimMotorWriter.java`) already sit unextracted at `engine-java/.openrocket-src/core/src/main/java/info/openrocket/core/file/motor/`, so this may be an extract-and-wire job rather than a new parser. If extracting drags in too much, `services/engParser.ts` is the JS-side precedent to copy - `.rse` is XML rather than RASP's fixed-column text, so `xmlUtil.ts` covers the parsing half. Related: the `.rkt` DESIGN import entry below sits in the same `file/rocksim/` package.
- **Named launch sites / saved launch locations** - DONE. `services/launchLocationStore.ts` is the fourth store in the family (motors, materials, export templates, locations): a typed `LaunchLocationStore` over a `KeyValueStore` under `pads:custom` (the stored key keeps the old name so nothing saved is stranded), swappable via `setLaunchLocationStore`, with a `LaunchLocation` validated on save against the same ranges `LaunchPanel` clamps its fields to - a hand-edited blob cannot put a latitude past ±90 into the kernel's gravity and Coriolis terms or into a KML origin. `components/sim/LocationPicker.tsx` sits at the top of the launch panel's Site group: a dropdown that applies a location through the panel's own `onChange`/`onCommit` (so it is one undoable edit), a Save button reusing `DesignPropertiesDialog` for the name, and a Manage dialog listing each location's coordinates with rename and delete. Which location is "current" is derived by COMPARING THE NUMBERS rather than remembering a selected id, so it stays right after an import, a geolocation fix or a hand edit. A location holds ONLY the site: the rod, wind and atmosphere are conditions on the day. STILL OPEN from the original entry: a curated catalog of real club fields, which is a sourcing-and-freshness question rather than a code one - if it is ever wanted it fits `remoteData.ts` as a `sites.generated.json` under `public/data/`, refreshable from the `data` branch like the motor and component catalogs. This also closes the `SavedPadRepository` half of the **Real weather** entry below.

- **Save custom parts to a reusable library** — let a user save a component they've built (e.g. "my custom nose cone") and pull it from the "Select a part…" picker across *all* their designs, the way custom motors and custom materials already work. Motors have `motors:custom` (`MotorStore.addCustomMotor`) and materials have `materials:custom` (`MaterialStore.add`), but components have **no** equivalent — no `PresetStore` / `parts:custom`. To close the gap, mirror those: a swappable `PresetStore` (localStorage default), a "Save as part" action in the component editor, and merge saved parts into the existing component pickers (flagged + deletable, like imported motors). NOTE: editing/building components with arbitrary geometry already works, and picking real manufacturer parts (the ~2,900-part catalog) already works — this is *only* about saving your own part to reuse it.
- **Support camera shrouds & protuberances** — external add-ons (camera pods, avionics fairings, rail-standoffs). Today they're only vestigial: a mention in the dead `tree/schema.ts` and some stray render scaffolding in `TreeSchematic`, but they're not a real `ComponentType`, can't be added (`treeEdit.ts`), can't be edited (`PropertyPanel.tsx`), and don't import/export (`orkFile.ts`) — nothing can actually create one. NOTE: these are **not** OpenRocket base-model components, so the kernel won't simulate them as first-class aero bodies — treat like the app's `fairing` extension (custom `.ork` element, mass + drawing, approximate/zero aero). To support: add the `ComponentType`(s), wire `treeEdit` (allowed children + defaults), give `PropertyPanel` their fields (dimensions + **angle around body**, reusing the `'angle'` field kind), add `orkFile` import/export as a custom element, and finish the side/aft/3D render paths (honoring the angle, like launch lugs now do).
- **Fin marking guide** — the wrap-around paper template that says WHERE around the body tube each fin goes. You print it, wrap it round the tube so the ends meet, tick through the marks, then rule lines along the axis through the ticks; those lines are where the fins glue. We have no equivalent — `grep -ri "marking"` over `src/` returns nothing. It matters most for **tube fins**, which are the one fin type that gets no cutting template at all (a tube has no planform), so the guide is the only printed aid they have. OpenRocket's `FinMarkingGuide.java` (swing) is the reference: one guide per body tube, its **height** equal to the circumference — `(getOuterRadius() + PAPER_THICKNESS_IN_METERS) * TWO_PI`, with paper at 0.1 mm so the wrapped ends actually meet — each mark at `angle / TWO_PI * circumferenceInPoints`, and everything angular on that tube consolidated onto the one sheet: `FinSet`, `TubeFinSet`, `LaunchLug` and `RailButton`, plus a "Front" tab and arrow so it cannot be wrapped backwards, and dashed fore/aft lines for canted fins. Most of the inputs already exist: `reportPdf.ts` already draws 1:1 in a millimeter document, `tubefins.ts tubeFinRadius` gives the tube geometry, and the nodes already carry the angles (`angleOffset` on lugs and rail buttons, `finCount` on every fin set, `cant` on fin sets). To close: a `ReportOptions` flag and a new section in `downloadReportPdf` that walks each body tube for anything angular and emits one strip per tube — new drawing, not new machinery.

Humidity and gravity ride on `LaunchConditions` (atmosphere and Earth-model groups, and the `.ork`); the angle step is a `SimPrefs` run option with a global and a per-simulation override, like the time step. `engineBoundary.test.ts` flies the real kernel to prove each one moves the numbers, since a passed-through option the Java ignores is invisible from the JS side. Also fixed here: `.ork` export hardcoded `<geodeticmethod>spherical`, so a WGS84 or flat design came back spherical. ALL FOUR deployment thresholds now fire, which needed two fixes beyond passing them. `drogueLowSpeedWarning` got a setting of its own (global + per-simulation override) and `PATCH(drogue-low-speed)` enables the check upstream ships commented out. More to the point, `ComponentFactory` never called `setDrogue`, so `isDrogue()` was false on every device the app built, `stageHasDrogue` never went true, and the kernel took the SINGLE-deployment branch on every flight: `mainHighSpeedWarn`, `mainLowSpeedWarn` and the drogue threshold were all unreachable however they were set, and `RECOVERY_DROGUE_NO_MAIN` could not fire either. Parachutes and streamers now carry a `drogue` key (editor toggle, `.ork` `<isdrogue>` both ways), and `engineBoundary.test.ts` flies a real dual-deployment rocket to prove each branch.

- **NAR/Tripoli flying limits** - `services/safetyLimits.ts` caps the launch rod at 20 degrees from vertical and wind at 20 mph, per the NAR and Tripoli safety codes. The launch-condition fields clamp to them, an imported `.ork` outside them is listed in the loaded banner, and `runSims` refuses those simulations rather than flying numbers the app will not stand behind. Launch conditions are simulation SETTINGS, not design, which is why the file's values are not preserved as authored the way its geometry is. Only the wind AT THE PAD is judged - a multilevel profile's ground layer (lowest altitude, since the list is not kept sorted), or the single wind. Winds aloft are not something a launch is called on, because they are not something anyone at the field measures. Gust standard deviation is deliberately NOT checked either: the codes speak about wind speed, and a mean inside the limit with gusts above it is a judgment call this is not equipped to make - revisit if that turns out to matter in practice.

- **Real weather for launch conditions (upstream PR #3211)** - `openrocket/openrocket#3211`, "Add current weather conditions+current location to flight simulations" (MidasAvocado, open as of 2026-09-19). It adds a **Use Current Conditions** button to the launch-conditions panel that reads the device position, pulls model-derived conditions from **Open-Meteo**, shows them for confirmation, and then applies elevation, temperature, surface pressure, relative humidity, surface wind and gusts plus up to **23 sorted multi-level wind layers** (surface, 80/120/180 m AGL, and the 1000-30 hPa pressure levels). NOTE: the PR is almost entirely `swing/` - a Core Location / WinRT `Geolocator` / GeoClue helper per desktop OS, a bundled signed Swift binary, `OpenMeteoClient`, `WeatherConditionsController`, a `LocationPickerDialog` and a `SavedPadRepository` - so **nothing lands in our kernel** and `extract/extract.mjs --check` will not see it; only `core/.../messages.properties` is touched, for the strings. That makes this a WEB feature to write, not a sync to take.
  Most of the target state already exists here: `LaunchPanel` has the 📍 **Use my location** button (`navigator.geolocation`, which is the whole cross-platform native half of the PR for free), `LaunchConditions` already carries `launchAltitudeM` / `temperatureC` / `pressureHPa` / `relativeHumidity` / `windAverage` / `windStdDev` / `windDirectionDeg`, and `windLevels: WindLevel[]` with the `WindProfileDialog` and `windProfileCsv.ts` is exactly the multi-level target the PR fills. So the work is: an `openMeteo.ts` service (fetch + parse + pressure-level-to-altitude conversion + sorting, pure and unit-testable against recorded fixtures), a confirmation dialog that shows the timestamp, source attribution and fetched values BEFORE writing anything, and one button that applies the result through the existing `onChange`. Two things to settle first: this is the app's **first outbound network call** for anything but the motor/part catalogs, so it needs the same user-initiated, coordinates-only-after-the-click posture the PR states, plus an offline/failure path; and the result must clamp to `services/safetyLimits.ts` like every other launch-condition input, since real weather is perfectly capable of being a no-fly. The PR's `SavedPadRepository` (named pads you fly from) and its forecast date/time picker are separable - worth having, but not part of the first cut.


- **Flight-log import (MAYBE - see the format caveat)** - read an altimeter / flight-computer CSV as a *recorded flight* and put it in the same charts, 3D path and ground track as a simulation, so a design can be checked against what actually flew. ZenRockets (`zenrockets.com/docs/flight-data-import`) is the reference for the shape: the minimum input is a time column plus either altitude or pressure, and every other channel only sharpens the reconstruction. Their pipeline is (a) pressure to altitude through the 7-layer ISA, skipping invalid samples, (b) vertical velocity by Savitzky-Golay smoothing plus analytic differentiation when altitude is all there is, or a Kalman filter that estimates accelerometer bias from the pad period and cross-checks against the barometric profile when an accel channel exists (falling back to altitude-only if the two disagree), (c) horizontal track from measured x/y first, then GPS lat/lon with short gaps interpolated, then a synthetic wind-drift model, (d) every channel resampled onto the vertical profile's timestamps, (e) auto-detection of liftoff, burnout, apogee and landing, with deployments NEVER inferred - the user marks drogue/main by hand.
  **Why this is a maybe:** there is no standard. Every altimeter vendor (Altus Metrum, PerfectFlite, Eggtimer, Featherweight, Missile Works, Jolly Logic, Blue Raven, ...) writes its own CSV with its own column names, units and header junk, and several ship binary or vendor-tool-only formats that never reach a CSV at all. A parser per vendor is an unbounded maintenance tail that ages badly. The only version worth building is the GENERIC one: one CSV reader plus a column-mapping step where the user says which column is time, which is altitude or pressure, which is acceleration, and picks the unit per column - with header auto-detection as a convenience and the mapping saved as a named **profile** so it is a one-time cost per altimeter, not per file. Settle that before starting: a mapper is a week of work, a vendor zoo is forever.
  Most of the downstream half already exists: `flightChartTraces.ts buildTraces` already draws several flights at once with per-series colors, `FlightChartPanel` / `FlightChart` / `FlightChartEvents` own the axis, zoom and event strip, `FlightPath3D` and `GroundTrack` already replay and plot a track, `interpolate.ts lerpAt` samples a series at a time, and `flightColumns.ts` / `csvExport.ts` already hold the column vocabulary in the other direction. The missing piece is a reader that produces a `FlightResult`-shaped object (`series` + `events` + `summary`) so everything downstream takes it unchanged. The kernel has an ISA atmosphere, but a pure-JS 7-layer ISA is ~30 lines and keeps the importer off the engine boundary and unit-testable.
  If it lands, the per-flight **time offset** from `zenrockets.com/docs/comparing-flights` comes with it: a recorded log starts whenever the altimeter woke up, so each flight in an overlay needs its own offset (theirs is 0.1 s steps, persisted) to line liftoff or burnout up with a simulation. Cheap, and the overlay is unreadable without it.

- **Linked dimensions** - let a fit dimension REFERENCE another part's dimension instead of being typed. ZenRockets (`zenrockets.com/docs/sizing-positioning`) puts a small "A" button on every field that supports it: link a coupler's outside diameter to the body tube's inside diameter and it recalculates whenever the tube changes, with guards against circular references and impossible geometry. We are fully parametric already, but every fit value is hand-typed, so resizing a body tube silently leaves its coupler, centering rings, engine block and motor mount at the old bore and nothing flags it. `ScaleDialog` scaling the whole rocket at once is the blunt version of the same need. Obvious link targets: coupler / centering-ring / bulkhead OD to the parent tube's ID, inner-tube OD to the centering ring's ID, motor-mount ID to the mounted motor's diameter, transition fore/aft radius to the neighboring tube radii, fin root chord to the parent tube's length. To build: a `link?: { field, nodeId, sourceField }` on the node (or a `links` map beside the dimensions), resolution in `buildRocket.ts` before the tree reaches the kernel, cycle detection at set time, a linked/unlinked affordance in `DimensionFields.tsx` showing the resolved value read-only, and `orkFile.ts` import/export as a custom element - OpenRocket has no such concept, so a desktop round-trip drops the link and keeps the resolved number, which is acceptable but belongs in the docs.

- **Flight events as a TABLE, plus Max-Q** - events are drawn as a label strip over the charts (`FlightChartEvents.tsx`, `flightChartEvents.ts`) and a handful surface as tiles (`SimSummary.tsx`: rod exit, rail static margin, rail CP, deploy and landing speeds, downrange), but there is no timeline you can read down. ZenRockets (`zenrockets.com/docs/understanding-flight-results`) gives each event its timestamp AND the state at that instant: liftoff; rail departure with velocity, stability, angle of attack and thrust-to-weight; per-motor burnout on a clustered stage; max-Q; stage separations; upper-stage ignitions; each deployment with the velocity it fired at; apogee; landing with touchdown velocity. Almost all of it is already computed - the event list is on `FlightResult.events` and every series needed to sample at an event time is on `FlightResult.series`, with `lerpAt` to read it. This is a presentation gap, not a physics one. The one genuinely missing quantity is **Max-Q** (`grep -i maxq` over `web/src` is empty): dynamic pressure `q = 0.5 * rho * v^2` peaks somewhere in the boost and is the number that decides whether an airframe holds together, so it wants either a derived series in `flightColumns.ts` or an engine-side event. To build: a `FlightEvents` table beside the charts (and a Results-tab section on mobile), one row per event with its own value columns, reusing the existing event clustering and unit chips.

- **Cutaway / section view** - a sectional cut through the centerline of the 3D model so the internals are visible: motor mount, centering rings, bulkheads, couplers, the chute bay and what is packed into it. ZenRockets (`zenrockets.com/docs/building-a-rocket`) ships it as a toggle on the 3D canvas beside the perspective/orthographic switch. We have a 2D schematic, a solid 3D model, an aero view and the flight views, but no way to look INSIDE the 3D one - the only internals view is the flat schematic. It is a clipping plane, not new geometry: a `THREE.Plane` on `renderer.clippingPlanes` (or per-material `clippingPlanes`) at y=0 or z=0, with `material.side = THREE.DoubleSide` plus a cap/stencil pass so the cut face reads as solid rather than hollow. Touch points: `Rocket3D.tsx` (renderer + controls), `RocketModel.tsx` / `rocketPieces.ts` (meshes and materials), `ViewToggle.tsx` / `SchematicControls.tsx` for the affordance. Pairs with the packed recovery-dimension item above - bay space is exactly what a cutaway is for.

- **`.rkt` (RockSim) design import/export** - DONE. Both directions ship: `services/rktImport.ts` and `services/rktExport.ts`, reached from **Import → RockSim** and **Export → RockSim**. Written as a TypeScript PORT of `engine-java/.openrocket-src/.../file/rocksim/` rather than an extraction of it - the question this entry posed. The answer was the port: that package is SAX-based and drags in the desktop's document, appearance and warning machinery, while the schema it encodes (`RockSimCommonConstants.java` plus four enums) is small enough to transcribe, which keeps both directions on the same side of the engine boundary as the `.ork` pair. `services/designFile.ts` picks the reader from the file's bytes so `loadOrk` has one path for both formats. The losses are named in both directions, as this entry asked: ring tails and subassemblies on the way in, rail buttons and parallel stages on the way out, and motors/launch conditions never, since RockSim keeps those with its simulations. STILL OPEN from the original entry: `.rse` motor import (its own entry above), and RockSim SIMULATION import - reading `EngineSet`/`StageNEngines` so a `.rkt`'s motor selection could seat itself on the matching mount, which would need the serial-number cross-reference (`MountSerialNo`) that neither direction currently writes.

- **Resolved-atmosphere / Environment readout** - show what the kernel ACTUALLY flew, not what was typed. ZenRockets (`zenrockets.com/docs/understanding-flight-results`) gives a fourth results tab beside 3D / Charts / Events: conditions at the pad (elevation, pressure, temperature, speed of sound, wind) plus profiles of wind speed, wind direction, pressure and temperature against altitude, and when a live forecast was used it shows the data the run consumed. We have the INPUT side only - `LaunchPanel`'s fields and `WindProfileDialog`'s altitude-vs-speed plot. Nothing shows the resolved profile, so an ISA-defaulted run (`temperatureC` / `pressureHPa` null) leaves blank fields with no way to see what the kernel substituted, and an AGL multilevel profile's actual MSL altitudes are invisible. To build: sample the kernel's atmosphere model over the flown altitude band at run time and carry the samples on the result, or recompute ISA in JS for the no-forecast case; then an Environment section with a pad row and four small profile charts reusing the chart panel. This is also the natural home for the Open-Meteo fetch in the weather item above - a forecast you cannot inspect after the fact is a forecast you cannot trust.

- **Tree mass rollup and stage isolation** - two small readouts on the parts tree that ZenRockets has and we do not (`zenrockets.com/docs/working-with-parts`). (a) A **sigma toggle** flipping each row's mass between THIS part's mass and its whole subtree's total, so a nose cone row can read either its own shell or the shell plus the chute, shock cord and nose weight inside it. (b) A **stage-isolation** dropdown that recomputes mass, CG, CP and stability for one stage alone rather than the assembled stack - which is how you check whether a spent booster is stable on its own way down, and the question a multi-stage design most needs to ask and currently cannot. Both are read-only views over data we already have: `ComponentTree.tsx` / `TreePanel.tsx` render the rows, `buildRocket.ts` already assembles the tree for the kernel, and the stage case is a filtered tree through the same static-analysis path the stability badge uses.
