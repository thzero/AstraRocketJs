# AstraRocketJs — TODO / roadmap

- **Multi-stage flight validation** — multi-stage rockets are now **authorable** (the **+ Stage** button adds a booster via `treeEdit.ts addStage`; `PropertyPanel` exposes `separationEvent`/`separationDelay`/`separationAltitude`, and the motor card gates upper-stage ignition to `ejectioncharge`/`burnout`/`never` via `isUpperStageMount`) and **simulate** as independent branches (`FlightResult.branches[]`, plotted per-stage in the Flight charts). Static mass/CG/stability match desktop OpenRocket (`Fireball.ZL1.DD.multi`). **Still missing:** a differential test of a staged *flight* (separation + upper-stage ignition timing, booster descent) against desktop OpenRocket, and the multi-stage report-rebuild path is untested (see `AUDIT.md`). To close: add a staged booster+sustainer flight fixture and validate the flown trajectory end-to-end.
- **Recovery-device packed length/radius** — the only recovery feature not yet wired: parachute/streamer canopy/strip + line **materials**, **shroud lines** (count/length), and streamer **Cd** are all editable now, but *packed* dimensions aren't. The engine's `ComponentFactory` (see `openrocket-engine.mjs`) doesn't read `packedLength`/`packedRadius` from the tree node and never calls `setPacked*`, so packed size can't affect mass/CG without an **engine change** (add the reads in the Java `ComponentFactory`, rebuild TeaVM). `orkFile.ts` export also hardcodes `<packedlength>0.025</packedlength>`/`<packedradius>0.0125</packedradius>` — a round-trip discards the real values. To finish: read the node keys in the Java factory + set them, then add editor fields and make `orkFile` import/export the node keys instead of constants.
- **Landing / ground-track: the CSV columns and a top-down plot** — the EXPORT half of this is already built and this entry used to imply otherwise: `flightPathExport.ts` projects the kernel's `Px`/`Py` drift onto lat/lon about the launch site (WGS84 degree lengths at latitude, not a sphere — `flightPathExport.ts:359`) and ships KML / GPX / waypoint CSV through `buildFlightPathModel` (`:385`), with an `includeGroundTrack` toggle and its own `groundTrack0` KML style. "Where does it land" therefore works TODAY, in Google Earth. Two pieces are genuinely missing. **(1) The flight CSV carries no horizontal position.** `csvExport.ts flightDataCsv` writes altitude/velocity/acceleration/mass/thrust/drag/mach/stability but nothing for downrange or crossrange — no engine change needed, because the kernel already emits `Px`, `Py`, `Pl` and `θl` in the DEFAULT `series: 'summary'` set (see `SimulationOptions.series` and the symbol-keyed index signature on `FlightSeries`). They arrive as `(number | null)[]`, which `flightDataCsv`'s `at()` helper and its empty-cell rendering already handle; add two columns through `col(units, 'distance')` so they carry the user's unit like altitude does. **(2) There is no top-down plan view in the app** — `grep -ri "ground track"` over `src/` finds only the export dialog. `ViewMode` is `2d | 3d | drag | flight | path` (`ViewToggle.tsx:3`), so this is a sixth entry in `RESULT_VIEWS` plus a drawing component; the projection maths is done and reusable from `flightPathExport.ts`, so it is the same shape of work as the existing `FlightPath3D` — a plan view of the drift footprint with the landing point marked, and ideally the drift ellipse across a wind sweep.
- **`.rse` (RockSim) motor import** — currently `.eng` only.
- **Save custom parts to a reusable library** — let a user save a component they've built (e.g. "my custom nose cone") and pull it from the "Select a part…" picker across *all* their designs, the way custom motors and custom materials already work. Motors have `motors:custom` (`MotorStore.addCustomMotor`) and materials have `materials:custom` (`MaterialStore.add`), but components have **no** equivalent — no `PresetStore` / `parts:custom`. To close the gap, mirror those: a swappable `PresetStore` (localStorage default), a "Save as part" action in the component editor, and merge saved parts into the existing component pickers (flagged + deletable, like imported motors). NOTE: editing/building components with arbitrary geometry already works, and picking real manufacturer parts (the ~2,900-part catalog) already works — this is *only* about saving your own part to reuse it.
- **Support camera shrouds & protuberances** — external add-ons (camera pods, avionics fairings, rail-standoffs). Today they're only vestigial: a mention in the dead `tree/schema.ts` and some stray render scaffolding in `TreeSchematic`, but they're not a real `ComponentType`, can't be added (`treeEdit.ts`), can't be edited (`PropertyPanel.tsx`), and don't import/export (`orkFile.ts`) — nothing can actually create one. NOTE: these are **not** OpenRocket base-model components, so the kernel won't simulate them as first-class aero bodies — treat like the app's `fairing` extension (custom `.ork` element, mass + drawing, approximate/zero aero). To support: add the `ComponentType`(s), wire `treeEdit` (allowed children + defaults), give `PropertyPanel` their fields (dimensions + **angle around body**, reusing the `'angle'` field kind), add `orkFile` import/export as a custom element, and finish the side/aft/3D render paths (honoring the angle, like launch lugs now do).
- **Fin marking guide** — the wrap-around paper template that says WHERE around the body tube each fin goes. You print it, wrap it round the tube so the ends meet, tick through the marks, then rule lines along the axis through the ticks; those lines are where the fins glue. We have no equivalent — `grep -ri "marking"` over `src/` returns nothing. It matters most for **tube fins**, which are the one fin type that gets no cutting template at all (a tube has no planform), so the guide is the only printed aid they have. OpenRocket's `FinMarkingGuide.java` (swing) is the reference: one guide per body tube, its **height** equal to the circumference — `(getOuterRadius() + PAPER_THICKNESS_IN_METERS) * TWO_PI`, with paper at 0.1 mm so the wrapped ends actually meet — each mark at `angle / TWO_PI * circumferenceInPoints`, and everything angular on that tube consolidated onto the one sheet: `FinSet`, `TubeFinSet`, `LaunchLug` and `RailButton`, plus a "Front" tab and arrow so it cannot be wrapped backwards, and dashed fore/aft lines for canted fins. Most of the inputs already exist: `reportPdf.ts` already draws 1:1 in a millimetre document, `tubefins.ts tubeFinRadius` gives the tube geometry, and the nodes already carry the angles (`angleOffset` on lugs and rail buttons, `finCount` on every fin set, `cant` on fin sets). To close: a `ReportOptions` flag and a new section in `downloadReportPdf` that walks each body tube for anything angular and emits one strip per tube — new drawing, not new machinery.
