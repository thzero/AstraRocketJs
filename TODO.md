# AstraRocketJs — TODO / roadmap

- **Multi-stage rockets — untested, not authorable** — only single-stage is supported/validated right now. The plumbing partly exists: the kernel handles staging, and `.ork` I/O (`orkFile.ts`) reads/writes `<stage>` separation (`separationEvent`/`separationDelay`) and per-mount ignition, and the motor-card ignition UI already gates the sustainer triggers (`ejectioncharge`/`burnout`/`never`) to upper-stage mounts (`isUpperStageMount`). What's missing/unverified: no UI to *add* a second stage (`treeEdit.ts` has no `stage` in `ALLOWED_CHILDREN`/`defaultNode`, `PropertyPanel` has no separation fields), and no differential test of a staged flight (separation + upper-stage ignition timing) against desktop OpenRocket. To support: author stages in the tree editor, expose separation config, then validate a booster+sustainer flight end-to-end.
- **Landing / ground-track exports & plot** — add horizontal position (downrange/crossrange) to the flight CSV, and a top-down ground-track plot for "where does it land?".
- **`.rse` (RockSim) motor import** — currently `.eng` only.
- **Save custom parts to a reusable library** — let a user save a component they've built (e.g. "my custom nose cone") and pull it from the "Select a part…" picker across *all* their designs, the way custom motors and custom materials already work. Motors have `motors:custom` (`MotorStore.addCustomMotor`) and materials have `materials:custom` (`MaterialStore.add`), but components have **no** equivalent — no `PresetStore` / `parts:custom`. To close the gap, mirror those: a swappable `PresetStore` (localStorage default), a "Save as part" action in the component editor, and merge saved parts into the existing component pickers (flagged + deletable, like imported motors). NOTE: editing/building components with arbitrary geometry already works, and picking real manufacturer parts (the ~2,900-part catalog) already works — this is *only* about saving your own part to reuse it.
- **Pods (`podset`) — finish add + edit, then re-enable import** — external pods currently **can't be loaded at all**: `orkFile.ts` rejects any `.ork` containing `<podset>` up front (the whole import fails with an error) because pods can't be created or edited in the app. The rendering half already exists — all three views (aft, 3D, side) draw assemblies via `ringInstanceOffsets`, and the exporter (`orkFile.ts` `case 'podset'`) can still write them. What's missing is authoring: add `podset` to `treeEdit.ts` `ALLOWED_CHILDREN` + `defaultNode`, give `PropertyPanel.tsx` the assembly fields (instance count, radial distance, radial reference, angle around body — mirror what launch lugs got), then remove the import block so `<podset>` round-trips. (Parallel boosters — `parallelstage`/`boosterset` — are unaffected; they still import/edit/export.) Deprioritized: pods are rare in most high-power builds.
- **Support camera shrouds & protuberances** — external add-ons (camera pods, avionics fairings, rail-standoffs). Today they're only vestigial: a mention in the dead `tree/schema.ts` and some stray render scaffolding in `TreeSchematic`, but they're not a real `ComponentType`, can't be added (`treeEdit.ts`), can't be edited (`PropertyPanel.tsx`), and don't import/export (`orkFile.ts`) — nothing can actually create one. NOTE: these are **not** OpenRocket base-model components, so the kernel won't simulate them as first-class aero bodies — treat like the app's `fairing` extension (custom `.ork` element, mass + drawing, approximate/zero aero). To support: add the `ComponentType`(s), wire `treeEdit` (allowed children + defaults), give `PropertyPanel` their fields (dimensions + **angle around body**, reusing the `'angle'` field kind), add `orkFile` import/export as a custom element, and finish the side/aft/3D render paths (honoring the angle, like launch lugs now do).
- **Lazy-load the components catalog** — `components.generated.json` is ~880 KB bundled; candidate for dynamic import.
