# AUDIT_PROMPT: `web/` engineering audit (AstraRocketJs)

Paste the block below to a capable agent to (re)run the full audit. It is tailored to this repo's structure: the app lives in **`web/`** (React 19 + TypeScript + Vite + Vitest + three.js); state is a **zustand store** (`web/src/state/store.ts` for the editing core, plus `viewSlice.ts`, `fileSlice.ts`, `workspaceSelectors.ts` and the smaller stores beside them) driven by an effects hook; App.tsx is thin (~350 lines), NOT a god component; the simulation kernel is **TeaVM-compiled OpenRocket** vendored under `web/src/engine/vendor/` (do not audit it). Run from the repo root (`AstraRocketJs/`); all paths below are repo-root-relative.

---

Do a full engineering audit of the **`web/`** package in this repo (browser re-creation of OpenRocket; React 19 + TypeScript + Vite + Vitest + three.js). Cover: security, correctness bugs, bad/over-complex code, architecture, missing unit tests, dead code, linting/tooling gaps, convention drift, accessibility, and the reference data the app ships and publishes.

**Method: fan out, don't read it all in one context.** Launch parallel review agents, one per slice below. Each agent reads every file in its slice fully, reports concrete findings as `SEV | CATEGORY | file:line | issue | why it matters | fix` (SEV = HIGH/MED/LOW), ranked by severity, findings-only (no preamble), each marked VERIFIED (it read the lines and confirmed the claim) or REPORTED (plausible, not fully confirmed), and ends with the number of files it read. Then synthesize all reports into one prioritized `docs/AUDIT.md`, grouped by category, with a "recommended order of attack" at the end.

**Slices.** Defined by folder, so a new file is in a slice the day it is added. A slice that is too large for one agent is split by subfolder, never trimmed to a list of files.

1. **Files, exports, persistence and remote data**: `web/src/services/{files,exports,storage,motors,materials,report}/**`, `web/src/services/app/**` and `web/src/services/design/orkTree.ts`. These parse UNTRUSTED user files (`.ork` = zip+XML via `orkImport`; `.rkt` via `rktImport`; `.eng`/`.rse` motor files), fetch remote data, and round-trip designs back out. Hunt: **decompression bombs** and uncapped reads (fflate has no built-in cap; every reader of a user file has to cap its size before decoding), **unescaped round-trip on export** (XML injection; CSV/formula injection `=+-@` in every CSV writer, comment and title lines included; KML balloon HTML; DXF group-code injection), `Number('')===0`/`parseFloat` accepting malformed tokens → NaN into physics, unbounded recursion on nesting depth, swallowed errors producing a partial model the user thinks is complete, **untrusted stored blobs** parsed and trusted as fully typed, quota errors swallowed, `NaN`/`Infinity` lost through JSON round-trips, remote fetches with no timeout, size cap or shape validation, encoding/BOM assumptions. For the IndexedDB tier: unhandled `onerror`/`onblocked`, transactions that outlive an `await`, version-upgrade paths, quota failures that leave the journal and the store disagreeing, and two tabs writing the same design. File handlers are checked against the desktop's own (`RocketComponentSaver`, the importer handlers, the RockSim handlers), not against the element names.

2. **State layer**: `web/src/state/**`, `web/src/App.tsx`, `web/src/main.tsx`. Business logic lives in the **store actions** and **`useWorkspaceEffects`**. Hunt: physics or business logic trapped in store actions or effects that belongs in a pure, tested service; **effects-as-events** and effects that write state derived from other state; over-broad effect deps forcing redundant engine rebuilds; `exhaustive-deps` disables (assess each); actions that **mutate shared tree/state objects in place**; actions that record an undo step and then change nothing; async actions that resolve on failure so their callers cannot tell; an action started again while its previous call is still running; autosave or persistence triggered by loading rather than editing; dead store state/actions.

3. **Components**, split in two agents: **3a** `web/src/components/canvas/**`, **3b** the rest of `web/src/components/**`. Hunt: god-components; business, geometry or unit-conversion logic that belongs in a service; **missing memoization on expensive render work** (three.js scene builds, chart data, SVG scenes, sweeps, mesh generation) and heavy child re-renders from inline props; mid-async `setState` after unmount; **weak numeric validation** (HTML `min=` is only a hint; check every `NumberInput` caller and every clamp against the kernel's own setter clamps); `dangerouslySetInnerHTML`, unsafe `href`/`target="_blank"`; **inert controls** (anything that looks clickable and does nothing, including pointer events disabled by a parent); accessibility (pointer-only SVG interaction, icon-only buttons without a name, dialogs without focus trap/restore, `div onClick` instead of `button`, status shown by color alone, live regions that never speak or that flood on pointer moves); user-facing literals that bypass i18n; duplicated-and-drifted JSX.

4. **Tree and geometry**: `web/src/tree/**`, `web/src/services/exports/solidMesh.ts`, `web/src/services/report/{reportGeometry,reportModel}.ts`. `noUncheckedIndexedAccess` is ON, so hunt the `?? 0`/`!`/`as` that silences it while feeding a wrong default into physics; divide-by-zero / NaN / Infinity from zero dimensions; degenerate meshes; in-place mutation of shared nodes; wrong formulas in mass/CG/inertia/profile sampling; **duplicated-and-drifted helpers** (the `num()` readers and `round()`/snap helpers were consolidated; flag any new copy); math with no test coverage; truly-unused modules (grep before claiming).

   **4b. Flight and design services**, its own agent: `web/src/services/{flight,design,parts,landing,tools,weather,map}/**`. This is where the app resolves geometry for itself before the kernel sees a design (automatic radii, bores, shoulders, catalog parts) and where it reads flight results back (events, recovery, wind, safety limits). Check every rule against the Java (see "Ported kernel math" below) and every flight reading against what the kernel records. This slice found three of the five HIGH findings on 2026-10-09; do not fold it into slice 4.

5. **Dead code and tooling (whole `web/` package).** **knip IS installed** (`web/knip.json`, `npm run knip`): run it first and treat its output as a starting point; verify each claim by grepping `web/src`, and distinguish real dead code from the deliberate "exported only so a unit test can reach an internal helper" pattern and from **side-effect imports**. `noUnusedLocals`/`noUnusedParameters`/`noUncheckedIndexedAccess` are ON, so focus on unused **exports** and unimported **modules**.

   Tooling: read `web/eslint.config.js`, `web/.prettierrc.json`, `web/package.json`, `web/tsconfig*.json`, `web/knip.json`, `cspell.json` and CI at `.github/workflows/{ci,gates,dev,deploy,e2e-full,sync-catalogs}.yml`. The CI layout: `gates.yml` is a reusable workflow (`workflow_call`) holding the gate set, and `ci.yml` (every pull request), `dev.yml` (every push to a branch other than master) and `deploy.yml` (every push to master, before the Pages publish) call it. Its jobs are `parity` (JVM vs TeaVM-JS vs WASM-GC, plus a rebuild-and-diff that the committed engine matches `src/java`), `reproducible` (`extract:check`), `validate`, `build-and-test` (`npm run verify:ci`), `e2e` (`npm run e2e:core`, the core specs) and `update-flow` (the service worker update path and offline catalogs against production builds). `npm run verify:ci` is `npm run gates` (`format:check`, `spell`, `typecheck`, `lint`, `knip`, `vite build`, with `format:check` first) followed by `test:coverage`. The full e2e suite runs by hand in `e2e-full.yml`. `sync-catalogs.yml` is scheduled (see slice 6). `cspell.json` covers `web/src/i18n/locales/en.json`; the other locale files are outside the spell gate, so check them for garbled characters and English left untranslated. `prettier` and `cspell` are exact pins on purpose (`docs/DEPENDENCIES.md`, rule 5). Do not re-report any of this as open; verify and move on. Are there gates whose SCOPE excludes the thing they claim to cover? Named-vs-default export consistency; duplicated helper modules.

   Lint and accessibility tooling: ESLint runs all of typescript-eslint `recommendedTypeChecked` on `**/*.{ts,tsx}`, with `no-floating-promises` and `no-misused-promises` set explicitly. In tests (`tests/**` and `**/*.test.{ts,tsx}`) `require-await`, the `no-unsafe-*` family and `no-unnecessary-type-assertion` are off; `web/eslint.config.js` states the reason for each. `eslint-plugin-jsx-a11y-x` runs its recommended set on `src/**/*.tsx`; it is the es-tooling fork of `eslint-plugin-jsx-a11y` with the same rules, used because the original's peer range stops at ESLint 9. `web/e2e/a11y.spec.ts` runs axe (`@axe-core/playwright`, WCAG 2.0/2.1 A and AA tags) in the dark, light and daylight themes on Design (2D, 3D and Aero), Configurations, Simulations, Results (Flight, 3D path, Ground track and Environment), Tools and Settings, and checks that the charts describe themselves to a screen reader. Check that every `jsx-a11y-x` disable comment states its reason, that the axe scan still covers every top-level view, every alternate view and every theme (a view added since is a finding until it is scanned), and that code comments state the constraint in present tense with no change history.

6. **Reference data and its pipeline**: `web/scripts/**` (the `sync-*.mjs` scripts, `scripts/lib/*`, `scripts/preset-digests/PresetDump.java`), `web/public/data/*`, and `.github/workflows/sync-catalogs.yml`. The deployed app reads its catalogs from the orphan `data` branch through jsDelivr (`VITE_DATA_BASE` in `deploy.yml`) and falls back to `web/public/data`, so **the published copy is what users get**: fetch it (`https://raw.githubusercontent.com/<repo>/data/components.generated.json` and the manifest) and compare it with the committed copy and with what the workflow would produce. A workflow that runs green while publishing a stale or incomplete catalog is a HIGH finding; a published parts catalog without digests means every saved `.ork` drops its part links, and a motor catalog without digests leaves desktop OpenRocket picking among motors that share a name. Hunt: a step the local refresh runs that the workflow does not, or the reverse; a third-party input that floats instead of being pinned (the database ref, the OpenRocket jar and its SHA-256); a refresh that changes the manifest hash when no data changed (every browser downloads the catalog again); a step that writes a catalog without refreshing the manifest, or writes it indented (the files are downloaded and cached offline); and every place the catalog's data differs from what desktop OpenRocket's library holds. The parts catalog has to match the desktop library built from the same release: the community database plus the files OpenRocket ships in its jar (`datafiles/components/internal`); parts that share a part number kept as separate rows; each row's digest matched on type, manufacturer, part number and description; materials looked up in the part's own file first; a stated mass applied the way `ComponentPresetFactory` and each component's `loadFromPreset` apply it. Compare the catalog's row count per type with what `PresetDump` reports for that release.

**Ported kernel math: check it against the Java, NEVER against another copy in `web/`.**
`web/src/tree/*` and the services in slices 4 and 4b re-implement OpenRocket math in TypeScript. The `parity` CI job does NOT cover any of it: parity compares the kernel to ITSELF across JVM, TeaVM-JS and WASM-GC. The authoritative reference is the committed Java under `engine-java/src/java/info/openrocket/core/`. Open it and compare term by term.
This is not hypothetical. The elliptical fin planform was a sine arch instead of a half-ellipse in three of four modules from 2026-09-07 to 2026-09-19, and THREE audits missed it because each one compared the four copies to each other and took the oldest as ground truth. On 2026-10-09 the automatic radius rules had five defects against `BodyTube` and `Transition` (a stored tube fin radius never re-resolved, a 12 mm fallback where the kernel uses 25 mm, no chaining through automatic tubes, no stage crossing, flipped nose cones ignored everywhere), and the earlier audits had passed the same code.
**A test is not evidence when it pins the app's own number.** The 12 mm fallback survived because its test asserted `KERNEL_DEFAULTS.bodytube.outerRadius`, the value under test. A test of ported math takes its expected value from the kernel (built through the bridge) or from a closed form written out from the Java, never from an app constant or a hand-typed number. Also distrust any test that pins a parameterized curve only by its point count, endpoints or extremum; demand an interior-point assertion.
**The mechanical checks.** `web/tests/services/design/geometryParity.kernel.test.ts` builds 200 generated designs in the kernel and compares every automatic radius, bore, nose cone or transition profile and fin tab limit with the kernel's own (`getComponentGeometry` on the bridge), and requires the pre-run check to let each design fly. `web/tests/tree/geometryFlags.test.ts` toggles each flag that changes a part's shape (`flipped`, `filled`, `clipped`) and requires every reader (station radius, schematic, report side view, PDF template, printable solid, 3D view) to react, or to be listed in its `UNAFFECTED` table with the reason it cannot. `web/tests/services/parts/catalogPatch.kernel.test.ts` requires every catalog part that states a mass to fly within 0.5% of it. The first two keep a `KNOWN` list of failures tied to findings; both lists are empty, and a new disagreement is either fixed or listed against a new finding. A new app-side copy of kernel geometry, a new shape flag, a new reader or a new catalog field is a finding until it is added to these tests. Do not re-read what they already cover; read their generators and tables and audit what is missing from them (a part type the generator never builds, a flag combination it never sets).
`web/tests/tree/finPlanform.kernel.test.ts` is the pattern for a new closed-form port.
**The bridge is part of the port.** `engine-java/src/api/java/api/ComponentFactory.java` turns the app's node fields into kernel calls, and the app's meaning of a field has to be the one the bridge applies. A flipped nose cone's automatic base was set on its tip there until 2026-10-09; the geometry test found it only because the kernel's answer disagreed with the app's. Read the bridge's handling of every field the slice touches.
**Which OpenRocket.** The kernel is upstream `unstable` at the commit in `engine-java/extract/UPSTREAM`, newer than the desktop release most people run (24.12). Physics and geometry follow the kernel the app ships. File formats and part digests follow the desktop release, because that is what reads the files. Where the two builds disagree (a catalog part's volume since upstream 90a57aa33), a value derived from one must not be flown in the other.

**Verification discipline: do NOT relay agent claims unchecked:**

- Independently confirm every HIGH finding, and every HIGH/MED **security** finding, against the actual source lines (and the Java, for a port) before it goes in the report.
- Confirm every **dead-code** claim by grepping all of `web/src` for imports (and note test-only usage) before asserting it.
- Re-resolve every citation by content; agents misquote line numbers.
- Be skeptical: only report issues with a specific `file:line` and a plausible failure scenario. No style nitpicks presented as findings.
- Merge duplicates raised by more than one agent into one entry.

**Codebase-specific notes: verify current state, don't blindly carry forward:**

- **`web/src/engine/vendor/`** is the TeaVM-compiled OpenRocket kernel (`openrocket-engine.mjs` + `.wasm`), GENERATED; do NOT audit it. The audit boundary is the `@JSExport` facade wrapped by `web/src/engine/openRocketEngine.ts`; the facade itself is audited by `docs/AUDIT_PROMPT_ENGINE.md`.
- Browser `DOMParser` does not resolve external entities → **XXE not exploitable** in `orkImport`.
- `orkImport` mints node ids via `freshId()` (Maps/Sets), so parsed strings are not used as write keys → **no prototype-pollution write surface**; only report proto-pollution if you find an actual `obj[untrustedKey] = …` write.
- `import './kernelLogSink.js'` (in `openRocketEngine.ts`) is a **side-effect import**; the module has no exports.
- Some exports exist only so a unit test can reach an internal helper; deliberate, label "test-only export (intentional)", not dead.
- **Fin planform geometry is centralized** in `web/src/tree/finPlanform.ts`. No consumer may sample a fin outline itself. A guard test fails on kernel trigonometry outside `tree/{finPlanform,tubefins,shapeProfile}.ts`.
- **A cone's end radii come from `tree/shapeProfile.profileEnds`**, which knows a flipped nose cone is a tail cone. A reader that takes `aftRadius` as the base end itself is a finding.
- **Kernel behavior that is not a defect:** the kernel mounts fin sets only on body tubes (a tapered parent cannot occur); two automatic ends that each follow the other resolve to -1 in the kernel, as on desktop; an end that follows a flipped cone's tip, or a ring placed where its parent has no bore, resolves to 0, and the pre-run check then reports the zero.
- **`web/scripts/lib/presetVolume.mjs` repeats `catalogPatch`'s geometry on purpose** (a data script cannot import the TypeScript); `catalogPatch.kernel.test.ts` fails if the two drift.
- **Import notes are keyed** (`web/src/services/files/importNote.ts`): an importer that builds an English sentence for the banner is a finding. A plain-string note is final text, kept for workspaces saved before notes were keyed.
- `App` and `i18n` use default exports intentionally; the rest of the tree is named exports.

**House rules that are findings when broken:** code comments state the constraint in present tense with no change history, ticket tags or named people; the OpenRocket desktop UI and file handlers are the spec, and the kernel owns the physics (an app-side estimate is allowed only if it says it is one and defers to kernel figures after a run); no inert controls; user-facing strings come from i18n; American spelling and no em dash characters in docs and strings. New fin fillets default to West System Six10 epoxy on purpose. RASAero is export-only.
