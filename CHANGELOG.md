# Changelog

All notable changes to AstraRocketJs are recorded here. The engine is validated
against desktop **OpenRocket** (`.ork` round-trips and its Component Analysis),
so most entries describe getting a computation to match OpenRocket exactly.

## [Unreleased]

### Added
- **Launch-guide clearance is a choice, and the two guide types are measured by one rule.** OpenRocket keeps the rocket on the rod for the full rod length wherever its guides actually sit: `SimulationStatus` computes a lug-aware effective length and `BasicEventSimulationEngine` then compares travel with the full one and never reads it, so its only consumer in the whole kernel is the NaN guard. A lug or rail button above the rocket's aft end is therefore credited with guided travel it does not have, and the reported rail-exit velocity reads high. Rail buttons are not in that calculation at all, and its lug search looks at one instance, which on a fore/aft pair is the forward one.

  Settings ▸ Simulation ▸ Flight model now offers **Guide-aware rod clearance**, off by default. On, the guided phase ends when the aft-most guide leaves the rod, and the rocket is RELEASED there as well as reported there: reporting a departure the rocket has not made would leave it mechanically constrained past its own exit, which is a different flight rather than a different number.

  **No kernel file is patched, so the default flight is byte-identical to upstream.** The engine already has every hook this needs, which makes the precise model an extension rather than a divergence: `firePostStep` runs before the engine's own clearance check and is handed the mutable status, handling a `LAUNCHROD` event does nothing but set `launchRodCleared`, the engine's own check is guarded on that same flag so an earlier event suppresses the later one rather than fighting it, both steppers key the rod constraint entirely on it, and `FlightData` already interpolates `launchRodVelocity` at the event's own time against the velocity series. So the whole model is `api/GuideClearanceListener.java`, attached only when the option is on, and the patched-file count is still 18 with `DIVERGENCE.txt` unchanged. Off, nothing is attached, which is why there is no switch inside the flight to get wrong.

  **Lugs and buttons are one rule with two geometries**, because the guiding point is the aft-most place the part still touches the rail. A lug is a tube lying along the body, so that is its aft end at `origin + getLength()`. A button is a stud whose `getComponentBounds` spans -r..+r in x, so its origin is its axial center and its aft edge is `center + outerDiameter / 2`; it never sets `length` at all, so measuring it like a lug would take its center and quietly lose its radius. Every absolute instance of every guide is searched rather than the first. A design with no guide keeps the full rod length either way, which is a tower.

  That symmetry is invisible in the numbers unless something compares the two, so `tests/engine/rodClearanceModel.test.ts` does, flying the real kernel: an 80 mm button and a 40 mm lug at the same place must report the same departure, and the button must NOT report what a zero-length lug there would. The same file pins the default as upstream's, by flying a design whose guide sits most of a tube length above its aft end and requiring it to depart exactly where one with no guide does. Its time step is 1 ms on purpose: the event lands at the end of whichever step crossed the threshold, so at the default 0.05 s two departures 40 mm apart fall in the same step and the symmetry cases pass for the wrong reason.

  **What moves if you turn it on.** Nearly every mid and high power design, because a rail button typically sits 10 to 20 cm above the tail: on a 1.8 m rail that is roughly 8% less guided travel and a few percent off the rail-exit velocity, downward. Lug designs move too, and by more when a lug sits well forward. It is the only setting in that panel that changes what the flight does rather than what it warns about, which is why it sits under its own heading with the difference spelled out, in all ten languages.

- **The guide is searchable, from the site and from inside the app.** Two searches, because there are two places to search from and neither one can serve the other.

  The published site gets `@easyops-cn/docusaurus-search-local`, indexing both locales and the docs only. Its index is deliberately kept OUT of the app precache: it is about 1.5 MB, and the box it feeds lives in the Docusaurus navbar, which the embed stylesheet hides on every page shown inside the Help dialog. Precaching it would cost every install that download for a control nobody in the app can reach. The precache went from 193 entries to 197 rather than gaining two megabytes. The index request carries a hash of the sources it was built from, so a deploy cannot be served against a cached old index, and that hash is taken over `docs` AND `i18n`: the plugin defaults to the English sources alone, which left a Spanish-only change with the same hash it had before and a reader holding a stale Spanish index. The NAME stays plain on purpose (`hashed: true`, not `'filename'`), because the published site replaces its files and a tab still holding the previous build would ask for a name that no longer exists.

  **The Help dialog searches the pages it already renders.** The contents rail now has a search box above the page list. The first search fetches every page the rail lists, splits each at its own `h2`/`h3` anchors and keeps that index for the session; a section is a hit only if EVERY word typed appears in it, ranked heading over body over page title, and each row names the section, the page it is on and quotes the text around the match. Opening a row goes to that section, marks the words in the page and scrolls to the first one, which is what makes a hit findable on a long page: the glossary is one heading per letter, so the anchor alone lands you at a hundred entries. Enter opens the top result and Escape clears the search rather than closing the guide.

  **Offline by construction, not by a cache rule.** It reads `docs/<slug>/index.html`, which is the exact key Workbox precaches each page under, so the index is built from cache hits with no index file shipped and nothing that can go stale against the pages it describes. `npm run e2e:offline-help` now proves it: with the network off it searches the guide, checks that no docs request failed, and opens a result. Nothing is generated at build time either, so a new page is still registered in `sidebars.ts` and nowhere else, and both searches pick it up.

- **The guide has a glossary, in both languages.** Every term the app puts on screen, and the symbols in its plots and downloads: 163 entries A to Z, a table of the file types it reads and writes, and a table of every column a flight-data export carries. Each entry is a plain definition and then where you meet it, rather than a paragraph of theory, because the question it answers is "what is this field asking me for".

  It leads the Appendix, ahead of the comparisons, and `sidebars.ts` says why: a glossary is reference you reach for mid-task, while the comparisons answer "should I use this?" and are read once.

  **The Spanish page is a translation, not the English page with Spanish in it.** It has its own letter sections, its own alphabetical order and headwords a Spanish reader would actually look up, which is a different set of entries in a different order rather than the same list relabeled. Cross-references are checked mechanically in both: every `See` and every `Ver` has to name an entry that exists.
- **The component catalog carries OpenRocket's own part checksums, and a committed script puts them there.** A `.ork` names a catalog part with `<preset type=… manufacturer=… partno=… digest=…/>`, and the digest is how the desktop decides whether the part in its library today is the part the file was built with. There is no match-by-name fallback: an element with no digest is rejected outright, as `Invalid ComponentPreset for component Body Tube, no digest specified`, and the component opens as a plain shape with no part behind it.

  `npm run sync:preset-digests` now attaches them, 2839 of the catalog's 2941 rows. The remaining 102 are rows OpenRocket's own databases do not contain at all, and those are written with no link rather than with a broken one.

  **It shells out to the real OpenRocket instead of reimplementing the checksum**, because the digest is an MD5 over the preset's properties as `ComponentPresetFactory` leaves them, not as the `.orc` file states them: a tube's wall is derived from its two diameters, a material density is looked up from a stated mass, and an integer property contributes its key name and no value. A wrong digest is worse than none, because the desktop then reports the part as CHANGED rather than missing. So `scripts/preset-digests/PresetDump.java` boots the application's own `ComponentPresetDatabaseLoader` and asks each preset for its own digest, and the script only merges, on manufacturer and part number, refusing to write at all if coverage falls.

  **It reads an installed release, not a source checkout.** A part whose row states a MASS has its material replaced by one looked up by density, so its digest depends on the material database that build ships: Estes PNC-50KA is `b3b5899e…` on the 24.12 release and `d1a20a7d…` on the 26.x source tree, while every part with no stated mass agrees across both. The script finds the installed OpenRocket itself and takes `--jar` or `--or` to point it elsewhere. Reading the application's database rather than the `.orc` files matters for the same reason: the two disagree for some types, Estes PK-12 came out `cd19839d…` from the files and `e38b3873…` from the application, and the application's is the one the desktop compares against.

  Nothing here is in the app build. It is a data step, run when the catalog is refreshed, and `tests/state/defaultRocketParts.test.ts` holds a floor under it so a catalog refreshed without it fails rather than quietly shipping parts that no longer reach the file.

### Changed
- **Descent sizing says it is an estimate, and hands over to the kernel once a run has one.** Every figure in the parachute panel's **Descent sizing** block, and the **Mass (Recovery)** stats tile, was the app doing its own physics: the mass is loaded mass less the propellant that burns off, the rate comes from the descent equation at an air density we model ourselves, and the two suggested diameters are that equation solved backwards. None of it came from the engine, and none of it said so.

  The block now reads *Estimated for a descent mass of…* before a run, and *Measured in the last run…* once one has flown that device, with the mass and the rate read straight out of the kernel's own series at the time of its own events: the mass series at the deployment event, and the velocity at the end of that device's descent phase (the next chute, or the ground) where the rate has settled. The tile's label reads **Mass (Recovery, est.)** until the same thing happens. The marker sits on the label rather than in place of the unit chip beneath it, because that chip is the control that sets the tile's unit and a marker is not worth a control.

  **That also settles the multi-stage case the estimate cannot.** A booster that separates descends on its own flight branch with its own mass, and the estimate has only one number for the whole stack, so it was the sum of two pieces and the mass of neither. `recoveryFlown.ts` reads per branch and names which branch a figure came from when the flight had more than one.

  **The two suggested diameters stay an estimate and are marked as one**, permanently: "what size should I use" is a question about a design that has not flown, and no simulation answers it. They are computed from the measured mass when there is one, which makes the suggestion better without making it a result. An OUTDATED run falls back to the estimate rather than quoting figures for a rocket that has since moved.

- **A settings change ages the results it invalidates, like a design change already did.** Four things decide what a flight computes: the design, the simulation's own inputs, its flight configuration and the global run preferences in Settings, Simulation. Three of them already marked a saved result outdated when they moved: the design through the tree watcher in `useWorkspaceEffects`, a simulation's launch conditions and overrides through `patchTargets`, and a configuration's motor, ignition, deployment and separation through `patchConfig`. The globals were the one input nothing watched, so changing the time step left every result on screen claiming to be current, and results are persisted to their own storage key, so it survived a reload.

  `SimPrefs` is the list it keys off, because that type is by definition the settings a flight reads: `SimulationSettings` also carries `confirmDelete` and `autoRunOutdated`, which are interface behavior, and `railExitVelocityMin`, which only colors the rod-exit tile and never reaches the engine. Listing those would age every result for a change that cannot move a number. `SIM_PREF_KEYS` names the nine at runtime with a compile-time check that it is the whole type, so a tenth added later cannot silently stop invalidating: leaving it out fails the build, and the error names the missing key.

  **A row that pins the key for itself is left alone.** A per-simulation override wins at run time, so a row with its own time step still describes its own numbers after the global one moves, and flagging it would be wrong in the other direction. `markPrefsOutdated` takes the changed keys and ages only the rows that do not override them.

  The comparison is key by key rather than by object identity, because the settings store hands out a new `simulation` object on every unrelated change in it. Comparing objects would age every result the moment somebody switched a unit or a part color.

- **The `.rkt` reader matches OpenRocket's own, handler by handler.** It was written from the RockSim element vocabulary, which is not the specification: the specification is `file/rocksim/importt/`, and a dozen of those handlers do something the file format alone gives no hint of. Read against all twenty of them plus the exporter DTOs, the reader was wrong in ways that changed mass and geometry, and `tests/services/files/rktDesktopParity.test.ts` is now one design per rule, each naming the handler it comes from.

  **A canopy was a hundred times too light, and an exported one a hundred times too heavy.** The whole rocksim package converts inbound by DIVIDING by its constant and outbound by multiplying, and `ROCKSIM_TO_OPENROCKET_SURFACE_DENSITY` is 1/10, so a surface density comes in at ten times the file's number and goes out at a tenth. We had the two factors swapped, which cancels on a round trip and is why the reader's test and the writer's test agreed with each other and with nothing else. The physics settles it independently: 1 g/cm2 is 10 kg/m2, and our own `units.ts` says so, so ripstop nylon at 0.067 kg/m2 sits in a `.rkt` as 0.0067.

  **A streamer or chute whose material is stated in BULK was twenty thousand times too heavy.** `RecoveryDeviceHandler` overrides the base conversion because RockSim states these two parts in whichever density kind its material database happened to hold: a volumetric density only becomes an areal one once multiplied by the fabric's own `Thickness`, which we never read. 0.05 mm mylar at 1390 kg/m3 is 0.0695 kg/m2, and it was arriving as 1390. A LINE density on the same part converts like a surface one, and a zero density is a RockSim bug whose fallback is the part's own computed mass over its area.

  **Every stage flew at our computed mass instead of the measured one.** RockSim states `Stage3Mass`, `Stage2Mass`, `Stage1Mass` and, under three differently spelled tags, each stage's CG. `RockSimHandler` applies each positive one as a stage-level override with "apply to subcomponents" on, which is its way of saying the figure covers the stage rather than the empty stage object. We read none of the six.

  **A zero `<ID>` means solid, not missing.** `BodyTube.setInnerRadius(r)` is `setThickness(getOuterRadius() - r)` and the handlers call it unconditionally, so a RockSim solid rod, coupler or engine block states a zero bore. Treating that as an absent value left the bridge's default 1 mm or 0.5 mm wall on a part that should have been solid. An absent `<ID>` still falls through to the default, which is a different thing.

  **A fin had no cross section, and an airfoil one no mass.** `TipShapeCode` is what RockSim calls a fin's cross section, and neither our reader nor our writer touched it, so every fin was square in both directions. Downstream of that, `FinSetHandler` deliberately overrides an AIRFOIL fin's mass and CG with RockSim's own computed pair even when the file asks for no override, because RockSim computes one mass per fin whatever the section and OpenRocket does not.

  **A fin set on a nose cone or transition could not be built at all.** `Transition.isCompatible` admits an internal component and a `FreeformFinSet` and nothing else, and a nose cone IS a transition, so `addChild` refuses anything else. `FinSetHandler` converts a trapezoid to freeform before attaching it, and the outline it reads is the four plain corners, because it detaches the fin first and a fin with no parent has a single root point. An elliptical one gets the handler's "can not be attached, ignoring component"; ours is dropped with a note that says which fin set went.

  **Smaller ones, all from a named handler.** A mass object's stated CG is measured from the front of its parent and is already carried in its position, so `MassObjectHandler` zeroes it rather than counting it twice. Most RockSim shock cords do not say they are shock cords, because of bugs in RockSim's own databases, so `inferAsShockCord` also accepts any mass object at least twice its parent's length made of a LINE material; a cord's packed length is a hundredth of its real one and its radius is its parent's bore. A shoulder gets its part's wall, or its own radius when the part is filled, and it arrives capped, since the kernel caps it when it first gains a length and desktop never turns that off. A shape parameter applies only to power, parabolic and haack, because RockSim writes one for every nose cone and applying it elsewhere causes oddities. A chute's packed radius is nine tenths of the tube it is stuffed in. A fin tab measured from the fin's front already contains a tapering body's drop in radius and has to give it back. A pod's children carry absolute roll angles that the pod's own angle comes off, and a pod marked detachable or already ejected is a strap-on booster rather than a fixed pod. Dimensions are floored at zero, as the handlers floor them.

  **What deliberately does NOT match.** Every RockSim `RadialAngle` and `CantAngle` is degrees, and our nodes hold radians. The desktop importer feeds those degrees straight into `setAngleOffset`, `setRadialDirection` and `setBaseRotation`, all of which are radians, and its exporter writes radians back into the degrees field. We convert in both directions at all six sites, so an imported design differs from desktop's wherever a part carries a roll angle. Also kept: the wall is computed from `OD` and `ID` together rather than from whichever tag the file lists first, `CantAngle` is read although the desktop importer drops it while its own exporter writes it, a shroud line's density and material are held separately rather than depending on parse order, and a cord with no stated density takes a line density derived from its mass rather than flying weightless.

  `ComponentFactory` is unchanged: it sets a shoulder's cap after its length from a key defaulting to false, which undid the kernel's own answer, and the reader now states the cap explicitly instead. Flipping that default would change every saved design whose node means "not capped" by omission.

- **Every numeric box obeys one rule about what a typed number may be, in one module.** The property panel refused an entry that could not survive its unit conversion; twenty-odd boxes elsewhere did not, and no two of them agreed on what to do instead. Some converted whatever the box reported. Some used `Number(x) || 0` or `parseFloat(x) || 0`, which reads like a guard and is not one: the `||` fires on `NaN` and on `0` and does nothing at all for `Infinity`, because `Infinity || 0` is `Infinity`. One clamped without a finite check, which also does nothing, since `Infinity < min` is false and most fields declare no `max`.

  `web/src/prefs/entryValue.ts` is now the only place that decides, and it decides once: a value is stored only if it is finite after every conversion has been applied and inside the bounds the field declares. `FieldUnit.toSi` converts and checks in one call and answers `null` for a value that cannot be stored; `onSi` wraps a store-this callback so a box can be handed straight to it, settling the three cases the same way everywhere. `fromUi` stays for a number that is not being stored, such as a chart axis or a ruler step, and `tests/prefs/entryValueCoverage.test.ts` lists the three files allowed to call it, so a conversion that skips the check fails a test rather than waiting to be read.

  **Where the overflow is reachable is a property of the unit, not of the field.** A conversion can only overflow where a display unit is LARGER than the SI one, which is eight quantities: distance, density, surface density, line density, pressure, force, impulse and acceleration. Length is safe today only because every length unit is a meter or less, which stops being true the moment a unit is added. That is pinned as its own test rather than left as something to work out per field. The boxes that were genuinely exposed and unguarded were the per-configuration deploy and separation altitudes, the custom-material density and the launch-site fields, plus the motor-impulse and component-diameter filter bounds, which checked the entry and then converted it.

  **A blank box and a refused entry are no longer the same answer.** `NumberInput` reported `null` for both, and an optional field turned `null` into `0`, so a refused value committed a zero. That is how an overflow became a stored zero, and how a leading `-` on the way to a negative number snapped a freeform fin vertex to the origin. Clearing a box still reports `null`, because it is a real edit; text that is not a storable number now commits nothing and leaves the draft showing what was typed.

  **A bulk density has a ceiling of 30,000 kg/m3.** The densest material that exists is osmium at about 22,590, so nothing real is refused, and a key-by-key prefix of a mistyped exponent can no longer save a custom material at a density that makes every part made of it unflyable. It is the one entry in a deliberately short table of physical bounds; a quantity with no real ceiling does not get an invented one.

  Also fixed by the same routing: an infinite ejection or ignition delay reaching the kernel, an infinite stride reaching the saved flight-path export options, and a custom ejection delay above `PLUGGED_DELAY`, which every consumer already reads as plugged, now landing on that meaning instead of passing through as an Infinity.

- **The header fits one row in a Linux browser, which is what the CI runner is.** `system-ui` is whatever the operating system supplies: Segoe UI on Windows, DejaVu Sans on the runner, about 12% wider for the same text at the same size. The row's width budget was measured in the narrow one and asserted as a pixel height, so it fit on the machine it was written on and wrapped to two lines on the other one, putting back the row the workbench tabs were moved into the header to remove. It was wrapping at 1024 and at 1180, in six languages. Two things gave the width back, in all ten.

  **The language switcher is as wide as the language you picked, not as wide as the longest one it offers.** A native select takes its width from its widest option, so `Português (Portugal)` set it in every language: 161px of header spent to show the word `Español`, and each language added is another chance to make it wider. The width now comes from an invisible sizer holding the SELECTED name with the select laid over it, still one real `<select>` carrying the full names, and the open dropdown is as wide as the browser wants. The arrow is drawn rather than native, because a select left to its own appearance lays that arrow out INSIDE its content box on top of the padding, which squeezes the name into what is left and closes `English` as `E...`. The cap that used to apply only below `sm`, where the longest name pushed the action group past a 320px viewport, now applies at every width: that name is exactly the case the header has least room for, since the longest translation of the pre-release word sits beside it.

  **The identity block reads the same at every width.** The mark, the app name, the version, the pre-release word and the engine backend were each gated on their own breakpoint, so a 1139px window showed none of them and a 1024px one showed a rocket and nothing else. They are what the header answers at a glance, and a laptop window is exactly where somebody checks which build they are flying, so no breakpoint takes any of the five away any more: phone, tablet and desktop all get the same header.

  **What gives instead.** Below xl the save status says `Saved` without the age, which its tooltip carries at every width, and the menu button is its glyph without the word, which its title attribute carries; the row's gaps are 6px rather than 8px there. Below 1180, in the wordiest languages, the row WRAPS: at 1024 in German there is not enough width for four tabs, the identity block, the save status and four controls, and a flex row's answer to that is a second line. English is one row at every desktop width. The header wrapping on a phone is what it has always done.

  In a wide face the row is one line from 1180 up in every language, with 70px of slack there in the worst one (pt-PT), and one line at every desktop width in English. `e2e/workbench-header.spec.ts` measures both widths twice, once in the local font and once in a deliberately wide one, so the budget is held against the worst font rather than whichever one the machine running the test happens to have. Reverting either fix fails it.

- **The comparison page no longer lists two gaps that are closed.** Packed recovery-device dimensions reach the kernel: `ComponentFactory` sets the radius on a parachute, a streamer and a shock cord, and `componentFields` gives packed length and packed diameter their own editor rows with the automatic flag. Staged flight is checked against unmodified upstream OpenRocket by `engine-java/reference`, which flies a serial, a gap-staged and a strap-on fixture on both engines and gets identical event sequences on all six branches. Both rows are gone from the page and its Spanish twin, and the staged note in **Designing a rocket** now says what is compared instead of calling multi-stage numbers preliminary. What is left is an apogee disagreement of ~5.9e-4 m on two of the six branches, a number no flyer acts on; it stays recorded in `engine-java/reference/README.md`, where anyone who would chase it looks.

- **Nothing advertises the opt-in supersonic-aero extensions, because nothing turns them on.** `setSupersonicAero` sits on the engine wrapper with no caller anywhere in `web/src`, so the README's "extended Barrowman **+ RASAero** aerodynamics" and the Safety page's "(with supersonic extensions)" both named physics that never runs. The README names extended Barrowman alone, and the Safety page's list of what the model computes now matches the kernel as it is actually configured, which matters more on that page than on any other. The RASAero II `.CDX1` export is untouched, and so is the attribution in `engine-java/ATTRIBUTION.md`: the extension code ships, it is simply off and unreachable.

- **The README and the docs say ten languages instead of two.** The README's responsive bullet, the Features page's **Multilingual** bullet and the Getting-started tour of the top bar all still said English and Spanish, written before de, fr, pt-BR, pt-PT, nl, pl, ru and ja landed.

- **Opening the report no longer updates the rest of the app in the middle of its own render.** Assembling a multi-stage report builds each stage on its own, which resets the shared engine, so `assembleReport` rebuilds the whole rocket afterwards and re-seats it as the live handle. The export dialog assembles in a state initializer, which runs during render, so that re-seating was a store write mid-render and every other subscriber was asked to update from inside a component that had not finished rendering. React said so on every open ("Cannot update a component (`DesignWarnings`) while rendering a different component (`ExportDialog`)"), which is the same hazard the dialog's own spec is named after.

  `assembleReport` now takes the install step as an argument. Outside React, `store.saveDesign` keeps the default and re-seats the handle itself. The dialog passes its own, takes the rebuild back, and installs it in a layout effect: after the commit, before the browser paints, so nothing is ever shown against an engine left on the last stage that was built. The engine is whole either way by the time the call returns; only the store's view of it moved.

- **The ground-track drift readout is checked against a band, not a string.** The two map specs pinned `377 m · 270°`, and the same design in the same wind lands on 377 m or 378 m from one run to the next, so they failed about one run in four. Both tests are about the readout being on screen at all, since the pane used to cut its ends off, and neither is the place that owns the number. They now read the figures out of the readout and check the distance and the bearing against bands wide enough to absorb the meter that moves and far too narrow to absorb a change to the design.

- **The report and 3D-print exporters are out of the initial download, which is 419 kB smaller.** Two paths already imported their heavy half dynamically so it would load only when somebody actually exports: `store.exportPrint` for `rocketPrintExport` (the three.js meshers and the 3MF writer) and `store.saveDesign` for `reportModel`. Neither was splitting anything. A dialog that the header mounts eagerly held a static import of each, and one static import is enough to pin a module and everything under it into the main bundle. The build said so twice over (`INEFFECTIVE_DYNAMIC_IMPORT`), and the warnings were correct: the eager JS came to 2,004 kB across 31 chunks, with `solidMesh`, `meshValidate` and `threeMf` inside it.

  For the print export the fix is a light half. `printableParts.ts` holds the tree walk and the `PrintablePart` shape and imports nothing heavier than `componentFormats`, which is the same split `componentFormats` and `componentExport` already have for the per-component ⬇ button. The export dialog imports that to draw its tick list; only `store.exportPrint` reaches the builder, now a 1.5 kB chunk fetched on demand.

  The report dialog has no such seam, since it and the store both want `assembleReport` itself, so it is `lazy()` in the dialog host instead, behind the same Suspense-inside-an-ErrorBoundary arrangement the 3D views and the component picker use: a failed chunk fetch on a stale deploy must not take the window down. Its fallback is nothing rather than an empty modal frame, because a dialog that arrives a beat late reads better than one that flashes a shell first.

  Initial JS is **1,585 kB across 15 chunks**, and the build no longer warns. Nothing changed about what either dialog shows or writes.

- **`web/src/services/` is eleven buckets instead of ninety-nine loose files.** The directory had grown to the point where the flat listing was the only map of it, and a listing sorted by name puts `motorCurve` next to `motorDb` and `orkTree` next to `orkTypes` while the module each of them actually belongs with sits screens away. Three buckets already existed, `ork/`, `rasaero/` and `report/`, which is the shape the rest was missing.

  The split is by subject, not by kind: **`design/`** (the tree and the component model: the automatic diameter and shoulder passes, the field table, the derived fields, the fin helpers, `treeEdit`), **`parts/`** (the component catalog, its filter and fit ranking, saved parts), **`materials/`**, **`motors/`** (the catalog, the picker, the thrust-curve client and the two motor-file parsers), **`flight/`** (configurations, simulations, the wind models and sweep, events, drift and ground track), **`files/`** (the design formats in both directions, with `ork/` and `rasaero/` moved under it), **`exports/`** (the derived artifacts: mesh, DXF, 3MF, schematic, CSV, flight path), **`report/`**, **`storage/`** (the key-value tier and everything persisted on it), **`map/`** and **`app/`** (identity, help, updates, remote data). `tests/services/` mirrors it file for file, snapshots included.

  Nothing but import paths changed. No module was split, merged, renamed or given an index barrel, so every import still names the file it reads and a moved module still turns up in a plain grep.

- **The component editor is a dialog on any window narrower than 1536px.** The Design tab is three columns: the part tree, the drawing, and the selected part's properties. Three of them only fit past 1536, which most laptops are not, so this is about ordinary desktop windows and not only phones. Below that the property column took 380px a 1024, 1280 or 1440 wide window does not have to give, and what it took them from was the drawing, which is the pane with the most to lose: a hobby airframe is 15 to 25 times longer than it is wide. The editor now opens as a dialog over the drawing at those widths. At 1536 and up the column is exactly what it was, splitter included, and the tree can now be dragged to its full 640 below that, since there is no longer a column on its other side to leave room for.

  This also gives the editor to the widths that never had it. Below 1024 neither the tree nor the property column is on screen, so tapping a part in the drawing selected it and then showed nothing to edit: a phone could see a design and not change it. The same tap now opens the editor, with the same fields, in the same units.

  It is one editor at any width, never a column and a hidden copy of it. A hidden panel is still in the document and its fields still answer to their labels, so "Shoulder length" would resolve to two elements and a phone's accessibility tree would carry a desktop column nobody can reach. The dialog opens on the selection GESTURE rather than on which part is selected: closing it leaves the part selected, and tapping that same part again opens it again instead of doing nothing, which is what keying on the selected id alone would have done.

- **The version, the pre-release word and the engine backend come back at 1180px instead of 1280.** The three sat behind the `xl` breakpoint because at `lg` (1024), with the workbench tabs in the header and the save status showing, the row wrapped to two lines in six of the ten languages, which puts back the row the tabs were moved into the header to save. That gate was a round number rather than a measured one, and it cost the badges every window between 1024 and 1280, which is most laptops.

  They are one pill now rather than three: three cost two extra gaps and two extra sets of padding to say one thing, and a row of small unrelated-looking chips reads as clutter where one grouped stamp does not. The colors still separate them, amber for the pre-release word and emerald or slate for the backend. That, a tighter pill and 4px off the tab strip's left margin took the requirement from 1220px to **1176** in the longest language (Russian; pt-PT wants 1172, German 1168, English 1120), so the badges now show from a named `--breakpoint-badge` of 1180. Every width measured in the browser, in all ten languages, with all four tabs and the save status in the row, and pinned by `workbench-header.spec.ts` at 1180 and at 1179 so a longer version string or a wordier translation fails the test rather than silently wrapping the header.

- **The default rocket is built out of what a rocket is built out of.** Its nose cone is **polystyrene** and its fins are **basswood**: basswood rather than balsa because the fins are large for the airframe and swept, and a sport model meant to be flown more than once gets the stiffer of the two. They were weighing as cardboard at 680 kg/m3, the engine's stock material for a part that names none: 1.6x too light for the nose cone and a third too heavy for the fins. Both are mass at the ENDS of the airframe, where an error moves the CG and the stability margin furthest. The airframe, the motor tube and the centering rings keep the stock cardboard, which is the right answer for them.

  The numbers move, and that is the point: **45.2 g empty against 48.3 g**, a CG at 32.8 cm rather than 35.9, and a margin of 3.52 calibers rather than 2.81. Flown into the 7 m/s wind the ground-track spec uses, it now drifts 377 m rather than 364.

  Names, densities and `.ork` groups all come from the material catalog rather than being typed in, and `defaultRocketMaterials.test.ts` checks them against the shipped file, so a catalog sync that renames or re-weighs one fails the build instead of quietly flying a different rocket.

- **A new part says what it is made of, instead of "Not specified".** A part the app created carried no material at all, so the panel showed "Not specified" with an "automatic" badge beside it. That was never a lighter part: `ComponentFactory` only assigns a material when the node carries a positive density, so the part kept the one its Java constructor was given and flew as **Cardboard**, **Ripstop nylon** or **Elastic cord** regardless (`ApplicationPreferences.StaticFieldHolder`). The editor simply could not say so. Desktop OpenRocket has no such state at all, since every component there is constructed WITH one of those three, and the state did not even survive a save here: the `.ork` writer fills the same three materials in and the reader hands them back, so adding a body tube and reopening the identical design changed the panel's answer from "Not specified" to "Cardboard".

  A new part is now seeded with the material the kernel would weigh it with anyway, unless Settings ▸ Materials says otherwise, and so is every part of the default rocket. `RocketSpec` names no density at all, so that design opened with its nose cone, body tube, fin set, motor mount, both centering rings and its parachute all reading "Not specified" - the first rocket anybody sees, disagreeing with its own simulation about what it is made of. **No mass moves anywhere** - these are the densities those parts were already flying at. "Not specified" remains only for designs stored before this change that genuinely have a part with no material.

  The three materials were written out four times over: in the `.ork` writer's bulk, surface and line fallbacks, and in the prose of the hint under the picker. They are one table now (`KERNEL_MATERIALS`), cited to the kernel that owns them. The list of which material slots each part type has was also duplicated between the Settings page that draws a row per slot and the seed that fills them; that is one list now too.

- **The Motor section sits below the material on a body tube and an inner tube.** Everything above it describes the tube itself, its dimensions and then what it is made of, and the Motor section is the first thing about the job the tube has been given rather than about the tube. Between the wall thickness and the material it split the description of one object in half, and on an inner tube its six rows, the cluster among them, pushed the material picker most of a screen down. Those are the only two types with a section there; nothing else moves.

- **The Automatic switch says what it is.** It was a bare 13 by 13 pixel checkbox at the right end of a dimension row, with the word only in a hover tooltip. On a centering ring, which has one on each of its two diameters, that read as two unexplained ticks, and the feature they turn on was reported missing from parts that had it all along. All eighteen of them now carry the word **Auto** beside them: a centering ring's two diameters, a bulkhead's, a coupler's, an engine block's, a tube fin set's, a nose cone's base and its shoulder, a transition's two ends and its two shoulders, a body tube's diameter, a packed device's radius, and the values the simulator works out for a recovery device - a parachute's drag coefficient and line length, a streamer's drag coefficient, a shock cord's length.

  The row had to stop being one big `<label>` for this. A label binds to a single control, so the word "Auto" written inside it focused the number box rather than ticking the switch beside it, which is why it could not be worded before. The field's label and the switch's are now separate, and the switch's accessible name still leads with the field ("Outer diameter: Auto") so the two rows on a ring are told apart when the page is read aloud. Nothing moves horizontally: the rows measure clean at the 380px column, the 300px minimum column, the dialog and a 320px phone.

- **A new centering ring, bulkhead, coupler or engine block starts automatic, as the kernel's own does.** The Automatic checkbox beside those diameters was always there; what was missing is that it starts ticked. `TubeCoupler()`, `Bulkhead()` and `EngineBlock()` each call `setOuterRadiusAutomatic(true)` in OpenRocket, and `CenteringRing()` turns on both its outer diameter and its inner one. The app created all four with the flags off and a hardcoded 25 mm outer diameter, so a ring dropped into a 54 mm airframe arrived sized for a different rocket, drew at that size, and flew at that size until somebody noticed the checkbox. It now takes the bore of the tube it lands in, in the same edit that adds it, and a centering ring's own bore follows the motor mount running through it. With no mount beside it that bore is zero, a solid disc, which is what `CenteringRing.getInnerRadius` gives as well.

  One thing had to be fixed for this to be safe. Picking a part from the catalog writes the diameter the part states, and nothing turned the automatic flag off, so the resolver overwrote it on its next pass. That was unreachable while nothing started automatic, and it would have made the parts picker read as doing nothing on exactly these four types. A dimension a picked part states now pins itself, which is what the kernel's own `setOuterRadius` does. A saved part stored AS automatic stays automatic.

- **Comment is the bottom of the component editor.** It was sitting above the material, which put a free-text box in the middle of the part's geometry: dimensions, then a note, then what the part is made of. It is now dead last, below even the overrides. It is the only field in the panel that is about the BUILDER rather than the rocket, so nothing the panel says about the part belongs under it, and overrides are the last thing about the part itself.

- **My Parts and the rocket's name go where the component tree goes.** Both are design-authoring chrome with nowhere to land when the tree is not offered, which is any window under 1024px and any window with the drawing maximized. **My Parts** is the saved-part library, and a saved part is applied THROUGH a component: a window that cannot add the component it belongs on would open the library onto a design it has no way to put anything into. The catalog picker inside the component editor is a different thing and stays at every width, since it re-sizes a part the design already has, and Save as part still fills the library from there. The **rocket's name** on the design banner, and the configuration behind it (designer, design type, comment, revision history), are set on a design you are building; where parts cannot be added the banner shows the name as a plain title rather than a control, since the ✎ and the tint are what say the line does something.
- **The stability margin is the engine's figure now, both ways of stating it.** The percentage was computed in the app, in four separate views, as `((cp - cg) / length) * 100`. Right shape, wrong denominator: OpenRocket measures it against the AERODYNAMIC length, and `length` is the span of every component including the ones with no aerodynamic effect. A motor tube hanging out the back of the airframe is enough to separate the two, and that is an ordinary rocket, not a corner case - on the test design it understated the margin by about 12%.

  The kernel does both conversions now, using OpenRocket's own `CaliberUnit` and `PercentageOfLengthUnit` bound to the selected configuration, so there is no arithmetic of ours left in the path at all. The two denominators are not variations on one number and never were: calibers divide by the largest body DIAMETER, the percentage by the aerodynamic LENGTH. The engine also reports that aerodynamic span, so the denominator can be read rather than inferred.

  Parity against the JVM is unchanged - 342 reference values, bit-identical or within ULP on both targets - which also confirms the caliber figure did not move: `CaliberUnit` and the default `maximum` reference type compute the same diameter. They would only diverge for the `nosecone` and `custom` reference types, and those cannot be set in OpenRocket's own UI.

  CP and CG were always the kernel's. This closes the last place the app was doing physics of its own.

- **Every round dimension in the component panel is now a diameter.** It was the only part of the app that spoke in radii, and it spoke in them because the node keys mirror the `.ork` tags, which store radii, and the panel renders node keys straight through. Everything around it had already picked the other convention: the parts picker's own column is an outer DIAMETER and halves it when you apply a part, the component tree's rows print `outerRadius * 2`, the DXF cut sheet labels parts `Ø`, a rail button stores a diameter outright, the motor catalog is in millimeters of diameter, and so is OpenRocket. Pick a 29 mm tube from the catalog and the panel beside it said 0.0145.

  Nothing about storage moves. The `.ork` tag, the engine bridge and the saved-parts catalog still carry radii, and the doubling and halving happen at the edit boundary and nowhere else, as a per-field flag rather than a rule about key names - a fin fillet's radius really is a radius, and stays one. The warning about tube fins that overlap now states the largest tube that fits as a diameter too, since it sits directly under the field it is about.
- **The 3D quick-glance card sits below the view buttons rather than level with them.** The preset row is pinned to the top right and the card to the top left, which reads as two corners only while the pane is wider than both of them together. Narrower than that they overlap, and the card is `z-20` against the row's `z-index: 2`, so it covered Reset / Side / Aft and swallowed their clicks. Buttons you can see and cannot press is the worse half of that, and every button added to the row made it worse. A readout yields to a control.
- **Saved launch locations are a two-pane library too.** The same master-detail shape the saved parts got, for the same reason and with the same rules: the locations on the left with their coordinates, the selected one open on the right, one pane at a time on a phone. Correcting a set of coordinates is something you do to several fields in a sitting, and a dialog-over-a-dialog per location made each one a separate errand - it also left the map, which is the whole answer to "is that the right field?", squeezed into a panel opened over another panel. It now has the room. Saving leaves the location selected, Discard puts it back as it was stored, and moving to another location with unsaved edits asks first.

  Two behavior changes fall out of it. **Applying a location is now a Use button** rather than a click on its row: a row click selects, and applying-by-clicking was an action with no visible affordance, announced only by a `title` nobody hovers. Use is refused while there are unsaved edits, because what the list offers is one of the sites you have SAVED, and handing the simulation a set of coordinates that exist nowhere is not that. And **Discard remounts the number fields** rather than just restoring their props: `NumberInput` holds a text draft while it is focused and drops it on blur, so putting the value back was only working because clicking Discard blurred the field first, which is an ordering accident rather than a guarantee.

- **A freeform fin outline that crosses itself is refused, and says so, instead of flying a different fin.** The kernel has always validated a freeform outline, and it validates by ROLLING BACK: it snaps the outline to the body, tests it for self-intersection, and on a crossing puts the previous outline back and writes a line to a log nobody reads. On the desktop the previous outline is the one being edited. Here it is the outline the engine built a moment earlier, the kernel's own default fin, so a design holding a crossed outline was silently simulated as a rocket with a fin nobody drew: on the test design the crossed outline reported 0.325 m of rocket and a CP at 0.2588 m, which are the default fin's numbers, where the outline as drawn gives 0.300 m and 0.2454 m. No error, no warning, and nothing on screen to tell the two apart.

  The refusal is now recorded and read. A crossed or touching outline names the fin set and says it cannot be simulated, the CG, CP and stability readouts go blank rather than showing another rocket's, and the Run button stays down until the outline is fixed. This is a deliberate divergence from desktop OpenRocket, which substitutes in silence.

  Opening a file is not flying it, so an `.ork` or `.rkt` that states such an outline still opens: the design arrives exactly as the file wrote it, with the reason in the import notes, since the design that cannot be simulated is the one somebody needs to open in order to fix it. Every outline the kernel accepts is unaffected, bit for bit: parity against the JVM is unchanged at 342 reference values on both targets.

- **A seated motor is named with its delay.** The configurations table printed `C6` in each mount column, which does not say which motor the mount is flying: the delay is when the nose comes off, and Estes sells that same C6 in 0, 3, 5 and 7. It now reads `C6-5`, or `C6-P` for a plugged one, which is the desktop's own format (`ThrustCurveMotor.getDelayString`) and what is printed on the casing. `P` is not translated, because a `C6-P` that read `C6-T` in another language would name a motor nobody sells.

  Only where a motor is SEATED and the delay has nowhere else to go. The motor card already states the delay on its own line, and a catalog row in the picker is not seated and has no delay yet, so both keep the bare designation.

- **The motor the app seats for you is on the delay it would have picked.** Any mount with nothing in it gets a stock Estes C6 (`flightConfigs.reconcileConfig`), and that one was fixed at a 3 s delay while the picker's own rule takes the middle of a motor's own charges, which on a C6's 0, 3, 5 and 7 is 5. So the one motor nobody chose was the one the app would not have chosen. It is 5 now, and `flightConfigs.test.ts` reads the charges Estes publishes out of the motor catalog and checks the seeded delay against the same rule, rather than against a number typed twice.

- **The default rocket is a kit, not a set of dimensions.** Every structural part of the design the app opens with is a standard Estes part named by part number, carrying the same preset link the component picker writes: a PNC-50KA nose cone, an 18 in BT-50 airframe, 2.75 in of BT-20 for the motor mount with an AR-2050 centering ring at each end, and a PK-12 canopy. So the airframe weighs as Estes spiral kraft glassine at 894.4 kg/m³ rather than the kernel's generic 680, which is a third of the heaviest structural part of a model this size and moves the mass, the CG and the margin together.

  It also has the parts no preset database carries, and that the design was missing: a nose cone shoulder sized to the tube's BORE rather than its outside, which is what was raising *Body diameter discontinuity* on open; an engine block for the motor to push against; a shock cord; ejection wadding between the canopy and the motor; and a launch lug that now sits at the tail rather than most of a tube length up the body, which is both where a kit glues it and where guide-aware rod clearance can credit it.

  **The fins are the same planform, scaled.** Root, tip, sweep and span are one 0.7 factor on the shape the design has always had, written in `defaultRocket.ts` as ratios of the root rather than as four numbers, because a fin edited one dimension at a time stops being the same shape. At full size the span was 2.3 body diameters, a competition fin on a sport model, and 5.6 g of balsa at the very tail; at 0.7 it is 1.6 diameters and 2.1 g, and the rocket flies 54 m higher on the same motor. The thickness is 2.38125 mm, the exact 3/32 in rather than a rounded 2.4, because balsa is sold by the fraction.

  **The margin is set by the tube, not by the fins.** Flown against the kernel, the design is 536 mm long, 57.3 g with a C6 loaded, and 4.5 calibers stable, which is 21% of its length. Fin size barely enters it: across the whole scale range the margin moves between 4.29 and 4.65, because shrinking a fin at the tail moves the CP and the CG forward together. What moves it is how many calibers long the rocket is, and an 18 in BT-50 is 21 of them. On the same parts a 12.7 in tube gives 2.8 calibers and a 9.5 in tube 1.8.

### Fixed
- **A design saved here and opened in desktop OpenRocket no longer arrives with its parts and its motor unrecognized.** Three separate things in one dialog, all of them in what we write rather than in what the desktop reads.

  **The part links had no checksum, so every one of them was thrown away.** We wrote `<preset type=… manufacturer=… partno=…/>` and the desktop answered `Invalid ComponentPreset for component Nose Cone, no digest specified`, then opened the component as a bare shape. A link now carries the digest the catalog holds for that row, and a row with no digest is written with no link at all, because an element the desktop rejects is worse than silence. The catalog digests are OpenRocket's own, computed by OpenRocket (see **Added**).

  **The preset type was our name for the part, not the desktop's.** The attribute is a `ComponentPreset.Type` enum name, so `bodytube` had to be `BODY_TUBE`, `nosecone` `NOSE_CONE` and so on; `ork/presetTypes.ts` now maps our row types to the kernel's in both directions, and the importer reads the kernel's spelling back.

  **The motor said it came from `custom`, and then that it could be any of three.** `exportMotors.ts` wrote a fixed manufacturer rather than the motor's own, so a stock Estes C6 was filed under a manufacturer no database has and the desktop reported `no motor 'C6' for manufacturer 'custom'`. It now writes the manufacturer the motor states, and omits the field rather than inventing one.

  That exposed the next one. The desktop resolves a motor by manufacturer, designation, diameter and length, and its database holds SEVERAL entries behind one of those names: Estes C6 is a plugged one and a delayed one, and `DatabaseMotorFinder` answered `Multiple motors with designation 'C6' for manufacturer 'Estes' found, one chosen arbitrarily`. A `<digest>` is the only field that says which, which is why the desktop writes one into every `<motor>` block it saves, and we now do too. `npm run sync:motor-digests` attaches them to the motor catalog, 756 of 815 rows, each entry with the delays it offers, and the writer picks by the delay the mount seated, so a plugged motor and a delayed one are told apart; where a name resolves to several entries with the same delays, the sync has already put the one whose curve is closest to our own first.

  **The lookup happens when the file is written, not when the motor is picked**, because a seated motor's whole spec is persisted with the design. A digest attached at pick time would reach only motors seated after the catalog gained one, and nothing re-resolves a spec that is already on disk: every design anybody already has would have gone on saving files with no digest in them. `fillMotorDigests` therefore reads the catalog at save time, which makes the digest a property of the file rather than of the session that seated the motor, and it leaves the motors untouched if the catalog cannot be read, because a save must not depend on it. A motor the desktop's database has no entry for is written with no digest, for the same reason a part is: a checksum that matches nothing makes it report the motor as CHANGED rather than resolving it. A digest read from an imported file is carried back out, so a design we could not resolve still names what it named.

  Covered where it can actually fail. `tests/services/files/defaultRocketOrk.test.ts` reads the exported XML of the DESIGN THE APP OPENS WITH and asserts the exact `<preset>` line for each of its parts, and `tests/services/motors/motorDigests.test.ts` does the same for the motor, with every checksum read from the catalog rather than typed in, so neither half can drift into agreeing with itself.

  **And one check asks the desktop itself.** `npm run check:ork -- <file.ork>` opens a file in a real OpenRocket through its own `GeneralRocketLoader`, prints every component that came back carrying a catalog part and every motor that resolved, and exits non-zero on any warning. Our own tests can prove the writer puts a link in the file; only this proves the desktop accepts it, which is exactly what was not true before. It needs a JDK and an installed OpenRocket, so it is not in `npm run verify`; it is what to run after changing anything the `.ork` writer emits.

### Added
- **Flight configurations, in their own tab.** A configuration is one way the rocket is set up to fly: a motor in every mount with its ignition, when each recovery device opens, when each booster lets go, and which stages are in the air at all. Every simulation names the one it flies, and several simulations can share it. That is OpenRocket's own model, and it is the last structural difference in how a design is set up to fly rather than in how it is drawn.

  Before this, the motor loadout was inlined into each simulation row: `motor` for the first mount, `extraMotors` for the rest, ignition beside them. It was the only part of a run with no name, while the design, the launch site and the wind profile were all named things several runs could point at. Comparing a C6 against a D12 meant duplicating a row rather than choosing a setup, and the first mount being held apart from the others is why three separate places carried the same "skip the primary or a vanished mount" filter.

  **The tab is a table, the way the desktop's panel is.** Rows are configurations, columns are the parts they configure, and a sub-tab picks which parts: the mounts, the recovery devices, or the stages. Reading across a row says what that setup does everywhere; reading down a column says what the same mount or chute does under each setup, which is the comparison a staged or clustered rocket is designed around and the one a list of names cannot show. **New** always adds a row, even when an identical setup exists, because a button that sometimes silently selects something else is a button that does nothing. **Delete** moves the simulations that flew it to the first one left, and asks first when any do; the last configuration cannot be deleted, since every simulation names the one it flies. A configuration nobody named is labeled by its motors, which is what the desktop shows and what a column of blanks could not.

  **Motors moved there, and nowhere else.** The simulation editor now picks a configuration and shows what it seats; the motor cards, the picker and the thrust-curve popup are in the Configurations tab. A loadout several simulations share cannot also be editable from one of them without the two surfaces disagreeing about whether a change is about the row or about the setup. Editing a motor there changes it for every flight that uses that configuration, and ages all of them.

  **Recovery and staging are per configuration too, field by field.** Leave a field empty and the part's own value on the design applies, shown as the placeholder so the control reads as the number the flight will actually use. "Deploy the main at 150 m on this flight" is one field, not a second copy of the chute. A part that some configuration flies differently says so in the property panel, naming those configurations, each a button that opens the tab on it: the one hazard of a value living in two places is a panel that shows an altitude the flight ignored.

  **A stage can be left on the ground.** A grounded stage contributes no mass, no drag and no motor, which is how a two-stage design is flown as its own sustainer without deleting the booster. This is the one part that needed the engine: a new `setStageActiveById` on the facade over OpenRocket's own `FlightConfiguration`, addressed by component id rather than by the kernel's stage number, because numbers are handed out in the order stages are added and a parallel booster shifts every stage after it. Both engine targets were rebuilt; JS/WASM parity and the golden reference values are unchanged.

  **The `.ork` carries all of it, in both directions.** A file with three configurations opens as three configurations, each keeping the file's own `configid` so a round trip is identity rather than a rewrite, and each arriving as a simulation of its own so there is a run to put numbers against. Saving writes every one of them. Three things that were quietly lost before: a configuration you had not opened used to have its recovery settings replayed from import and its staging overwritten with the opened one's, so a chute set to pop at apogee in one setup could come back deploying at 300 m; the stage-activeness flags were written as `active="true"` for every stage whatever the file said; and a design with a parallel booster declared fewer stage flags than it has stages.

  Workspaces are stamped `version: 2`. An existing one is lifted on open, minting a configuration per distinct loadout, so twelve rows that flew the same motors arrive as one setup rather than twelve copies of it. A workspace written by this build will not open on an older one.

- **A tube tells you its bore, and a launch lug has a wall.** Body tubes, inner tubes, couplers, engine blocks, tube fins and launch lugs show an **inner diameter** between the outer diameter and the wall. It is the dimension a tube is actually bought and fitted by - what slides into it, what it slides over, whether the motor goes in - and it existed only as a derived value inside the DXF, print and 3D-cutaway paths, shown nowhere.

  It is not a fourth independent number. A tube has an outside and a wall, and the bore is what the two leave, so typing a bore writes the WALL and leaves the outer diameter alone: the outside of a tube is decided by what it has to slide into, and the wall is what gives. That is how OpenRocket's three linked tube fields behave. A bore typed wider than the tube itself clamps to a zero wall, which is already flagged as degenerate on its own row, rather than to a negative one, which would have flowed into the mass, the mesh and the `.ork` as a number no consumer checks for.

  A **launch lug's wall** is editable for the first time. It round-trips through `.ork` and sizes the lug's printed solid, and nothing could ever set it, so the bore - the only dimension of a lug that has to be right, since the rod has to pass through it - was whatever the file said or the 0.3 mm default.

- **A design remembers which catalog parts it is built from.** OpenRocket puts that at the top of every component dialog, in the Parts Library row, and our picker is the same control; the link itself was read nowhere and written nowhere, so a design that went out to the desktop and came back had forgotten every part it was made of. It round-trips now, written the way `RocketComponentSaver` writes it.

  The half that matters is the DROPPING. A link that outlives the geometry labels a hand-sized tube with somebody's part number, so it goes the moment an edit changes what the part IS: any dimension row, or the material. That mirrors the kernel, whose own setters call `clearPreset()` for the same reason, and it errs towards dropping a link the desktop would have kept rather than keeping one it would not. A part you saved yourself gets no link, since it is in nobody's catalog.

  The per-part **line style** is carried through the file too, and deliberately gets no control: our schematic draws one line style, so a picker for it would be a control that does nothing.

- **A diameter can follow the part next door.** OpenRocket's **Automatic** checkbox, on a nose cone's base, a transition's two ends and a body tube's outside. It carried a real bug, not just a missing control: the file spells this as `auto`, our reader turned that into a hardcoded default for a nose cone and a body tube, and for a transition into an absent key that every view then drew at 12 mm while the kernel flew the neighbor's actual diameter. A design imported from the desktop was therefore drawn as one rocket and simulated as another.

  The rule is the kernel's own, from `BodyTube.getAutoOuterRadius`: take the part behind first, then the one ahead, and skip a neighbor whose facing end is itself automatic, which is what stops two parts pointing at each other. It reads the END that faces it, so a transition lends its aft diameter backwards and its fore diameter forwards. Resolved on every edit AND on import, written back to the file as `auto`, and handed to the kernel as automatic so it keeps following there too.

- **The rest of the Automatic boxes.** Seven more values OpenRocket lets you hand back to it, all of which we were reading as ordinary numbers and so pinning to whatever a file happened to say.

  Four of them follow a part's PARENT rather than the part beside it, so they get their own rule: a coupler, bulkhead, engine block or centering ring fills the bore of the tube it sits in, a centering ring's own bore is the motor mount running through it, and a tube fin set is sized from the body diameter and the fin count. Those are resolutions the DXF sheet and the printed solids already did privately; they are the part's actual dimensions now, kept correct on every edit, so the panel, the schematic, the 3D view and the engine all agree about a ring that has never been given a diameter. The file keeps saying `auto` rather than the resolved number, because writing the number would turn a design that FOLLOWS its tube into one pinned to whatever that tube happened to be that day.

  The other three are the kernel's own calculations: a recovery device's drag coefficient, a parachute's shroud-line length, and a shock cord's length. Those stay the kernel's to compute - the flag rides through the file and into `setCDAutomatic`, `setLineLengthAutomatic` and `setCordLengthAutomatic` - and the panel shows the value it arrived at rather than an empty row. A packed radius is written in `MassObjectSaver`'s own `auto <value>` form, marker and number together, so a reader that does not know the marker still gets a usable size.

- **Four numbers you can type the other way round.** OpenRocket offers some dimensions both ways, because both ways are how people actually have the figure, and it was always the one way here. A trapezoid fin's **sweep angle**, measured off its own span, which is what a plan gives you and the only signed row in the panel. A streamer's **strip area** and **aspect ratio** - how much fabric, and how long and thin - where typing either one re-cuts the strip and leaves the other alone. A mass component's approximate **density**, for when you know the lump is lead rather than knowing it weighs 40 g. And a motor cluster's **tube separation** as a distance between tube walls rather than a multiple of the tube diameter.

  None of them is stored, and none is a new value: each reads the keys the part does carry and writes those back, the way the inner-diameter row writes a wall. The arithmetic is the kernel's own, clamps included, because every one of its edges is reachable by typing: a fin with no height has no sweep angle, a streamer with no width reports a ratio of 1000 rather than a division by nothing, a cluster packed more than one diameter in stops at concentric, and a density on a part with no packed volume is refused rather than zeroing its mass. The area row needed a unit group the app did not have, so **square millimeters through square feet** are now a unit you can pick, defaulting to cm² and in² like the desktop.

  Along the way, the three cluster rows disappear on a **single** tube. Spacing, separation and rotation all describe where the OTHER tubes go, there are none, every consumer ignores all three, and the rows sat there taking values anyway.

- **Dual deployment is set on the stage, where OpenRocket sets it.** A stage now has a **Recovery** section: single or dual deployment, and which of the devices in that stage is the drogue. The flag lives on the device in the file, but the plan belongs to the stage, and the desktop has no per-device control for it anywhere.

  Ours was a checkbox on each parachute and streamer, which could mark TWO drogues in one stage. That is not a design OpenRocket can produce, and the simulation reads it as whichever device it walks into first, so the speed thresholds a deployment was judged against depended on tree order. Choosing on the stage makes it unreachable: the flag moves rather than multiplying, and switching back to single deployment clears the stage. A stage with nothing to deploy says so instead of offering an empty picker.

- **The buttons that reshape the design, not a number.** Every action OpenRocket's component dialogs offer, which the app had none of.

  **Convert to freeform** rebuilds a trapezoidal or elliptical fin set as a freeform outline with the same shape, so a stock planform becomes a starting point instead of a dead end. The outline is the one the app was already drawing and cutting from, and the fin keeps its count, wall, cant, cross section, tab, fillet, material and comment; only the four dimensions the outline now describes go away.

  **Split fins**, **Split pods** and **Split boosters** break a set into single parts at even angles, which is how you give one fin of three its own sweep, or move one booster. An override mass is divided between the pieces, since it was a figure for the whole set. **Split cluster** does the same for a motor cluster: one inner tube per position, each pinned where the cluster drew it, with whatever was attached to the tube duplicated too. Beside it, **Reset settings** puts a cluster's spacing and roll back to the default. A button that cannot do anything is disabled with the reason in its tooltip rather than hidden, because a one-fin set is exactly when someone goes looking for Split.

  **Calculate automatically** works out a through-the-wall fin tab from what is inside the airframe under the fin: it fits between the centering rings, reaches down to the motor mount and no further, and stays inside the root chord. That is the arithmetic a tab actually needs and nobody wants to do by hand. Ported case for case, including the rule that merges two rings glued face to face into one obstruction, and the one that ignores a ring no wider than the tube it centers. The depth is taken at the NARROWER end of the fin's span, so a tab on a boat tail is cut to the small end instead of through the skin.

  And the freeform editor gets its three: **Scale fin**, which takes the wall, tab and fillet with the outline, because a fin scaled without its tab no longer passes through its own slot; **Import from image**, which traces a fin off a photo or a scanned plan; and **Export CSV** of the point table, in the desktop's own file shape so a script that reads those already keeps working.

  The tracer is upstream's, threshold and all: the image is read by brightness so a dark shape on a light background works in any color, the fin must touch the bottom edge because that edge becomes its root, one pixel is one millimeter, and the traced outline is simplified at a fixed 0.8 mm tolerance - which is why a big image keeps more of a curve than a small one, and why Scale fin is the other half of the workflow. An image with nothing dark along its bottom edge is refused with that reason rather than a blank fin.

- **A design keeps what this app does not use.** A `.ork` from the desktop can carry things there is no model for here, the Appearance tab's per-part paint, shine and decal being the case that exists today. They were read nowhere and written nowhere, so every save threw them away: a design that came here to have one dimension corrected went back stripped of its paint, silently.

  Anything this app does not understand is now carried as raw XML and written back where it was. Nothing is parsed, nothing reaches the engine, and nothing can show up in the property panel, so there is no new surface and no new garbage in the model - just the elements, returned intact. It works by exclusion rather than by a list of things to keep, which means a tag a newer OpenRocket adds survives a round trip through this app without a code change here.

  It applies at three levels, because the things a `.ork` carries are not all components: a component's own children (the appearances), the children of `<rocket>` (a **kit name**), and the blocks that sit BESIDE `<rocket>` in the file. That last one is where the **Photo Studio** setup lives, along with the design's own preferences, its material overrides and its custom expressions - none of them a component, so none of them reachable by a pass over components, and all of them dropped on every save before this.

  Working out what actually falls outside the three sets meant diffing every element name OpenRocket's 34 savers emit against them, which turned up a bug worth having on its own: **what the stability calibers are measured against** was being overwritten. The app wrote a hardcoded "maximum" reference, so a design whose calibers were set against a fixed length came back measured against its widest body tube - a different stability number for the same rocket, with nothing said about it. The file's own reference is kept now.

  The exception is a **decal**, and it is the one thing that genuinely cannot survive: the image lives in a separate member of the `.ork` archive, and preserving `<decal name="flames.png">` would name a file that is not in the file we write. So the reference is dropped, the paint and shine it sat beside are kept, and the import says both of those things out loud instead of leaving you to find out later.

- **A design's own thrust curves are read.** OpenRocket embeds the thrust curve of every motor a design uses, inside the `.ork`, precisely so the file opens on an install that does not have those motors. This app took the XML out of the archive and dropped everything else on the floor, so a design built on anything outside our catalog opened with an empty mount and a blocked run - with the answer sitting unread in the file it came from.

  They are a fallback now, on both paths that used to end at a placeholder: a motor designation the catalog does not know, and one it does know whose curve will not download. The catalog is still tried first, so nothing changes for a design that already opens; the file's own curve is used when it cannot be, and the note says which happened. The match strips the delay off the designation, because the file names `J350-6` while the curve it carries is the motor `J350` - the delay is the mount's choice, not the motor's. Nothing is added to your own imported-motor list: the curve belongs to the design that brought it.

  What the file carried and this app did not use is now named in the import notes either way, which was the real problem with all of the above. A thumbnail is the one thing not worth mentioning, since whatever opens the file next regenerates it.

- **Every part has a comment.** The desktop gives each component a Comment tab; ours read the design-level one and dropped every per-part note on save. It is a text box at the foot of the panel now.

- **A part can be solid.** OpenRocket's **Filled** checkbox, on a nose cone, a transition and a body tube: no wall, no bore, material all the way through. It round-tripped in the file as `<thickness>filled</thickness>` and reached the kernel for the first two, never for a body tube, so a solid tube flew hollow and weighed what a wall would. It is a control now, the body tube is wired, and the wall and bore rows disappear while it is on, which is what the desktop greys out.

  It came out of a SECOND audit pass. The first one used the `.ork` file format as its authority, which answers what a saved design can carry and not what the desktop lets you set, so anything the config dialogs offer that is not a file field was invisible to it. Reading those dialogs found this, the shape descriptions, and a short list of things still open, all of it now recorded in `docs/AUDIT_COMPONENT_COVERAGE.md` with the scope mistake written down beside it.

- **The panel says what the chosen shape IS.** A nose cone or transition now carries a paragraph under its shape picker, where the desktop puts one: what an ogive is, what the shape parameter does to a power or parabolic series, and why an unclipped ellipsoid transition looks the way it does. It is the only place the app explains what a shape parameter of 0.75 means, and the clipped flag in particular is unreadable without it.

  The strings are OpenRocket's OWN, lifted from `l10n/messages*.properties` with the translations for all ten languages we ship, so the wording matches the desktop in each one rather than being a second description of the same thing. Two repairs on the way in: those files are ISO-8859-1 and the German one carries fourteen characters that are already broken upstream, which would have rendered as black diamonds, so the umlauts are restored. They carry a little markup - bold for the shape a parameter value produces, italics for the dimensions it is written in terms of, superscript for the power series exponent - which is rendered by building elements from a three-tag whitelist rather than by handing vendored text to `dangerouslySetInnerHTML`. Attribution is recorded in `engine-java/ATTRIBUTION.md`, and one misspelling in the upstream English is corrected rather than taught to the spell checker.

- **Every field OpenRocket has is now reachable.** A full audit against `DocumentConfig.java`, the desktop's own `.ork` reader, resolved through the class hierarchy and measured by injecting each of its 140 setters into a file, importing it, exporting it again and checking the kernel bridge. All 21 components the format can contain were already present. 82 distinct fields; these were the ones that were not.

  **Values the kernel never saw, although the file carried them faithfully.** A rail button flew at the kernel's default geometry, so its mass was wrong on any design that came from the desktop with a custom one. A lug, button or ring with an instance count of three was built ONCE, so three centering rings weighed as much as one. A ring, coupler or engine block sat on the axis whatever its radial offset said. A flipped nose cone, which is how a tail cone is modeled, came back the right way round. A recovery device's packed radius was ignored, so its mass sat at a radius nobody chose. All of them are wired now, in a rebuilt engine whose parity against the JVM is unchanged: 342 reference values bit-identical or within ULP on both targets.

  **Values that were simply lost.** A part COLOR was editable and written nowhere, so a design saved as `.ork` came back in its group colors: the one place the editor offered a control and then threw the answer away. A stage-level mass, CG or Cd override flew and was dropped on save, because the stage block writes its own name and id rather than going through the shared header that carries the override block. And the packed radius was read under a key nothing else in the app used, so every save wrote the 12.5 mm constant over whatever the file said.

  **Fields with no way to set them.** The fin cross-section (square, rounded, airfoil, which carries OpenRocket's own volume factors and so changes fin mass as well as drag), a transition's clipped profile, a cluster's spacing and rotation, off-center placement for internals, instance counts and spacing, a nose cone's flipped flag, what a mass component IS, a recovery device's packed size, the rest of a rail button's geometry, and a shock cord's cord length - that last on a component type which until now had no editable field at all.

  Our own RASAero extensions stay internal, as they were: `airfoilSection` and its leading-edge bluntness radius round trip and reach the kernel but are not OpenRocket fields, so they get no control. `comment`, `linestyle` and `preset` stay unexposed on purpose, and the audit in `docs/AUDIT_COMPONENT_COVERAGE.md` says why.

- **A shoulder gets its own section in the panel.** It is a different piece of the part from the cone or taper above it, and its four rows were running on under the planform as though they were four more dimensions of the same shape. A nose cone now has one **Shoulder** heading; a transition has **Fore shoulder** and **Aft shoulder**, kept apart rather than run together, because each end is its own build and eight rows under one heading is a wall. Same treatment the fin tab and the fillet already had.

- **A transition's shoulders weigh what they are built from.** Both halves of their mass were being dropped. The shoulder WALL round-tripped through `.ork` faithfully and `ComponentFactory` never handed it to the kernel, so a transition's shoulders flew as surfaces with no material, whatever the file said. The CAP - the disc that closes the far end - was read from the nose cone's `shoulderCapped` key, which a transition node does not carry, and the `.ork` writer emitted a hardcoded `false` for both of its sides, so a capped shoulder could not survive a save either.

  Now each side has its own thickness and its own cap, in the editor, in the file and in the engine. That last one is a Java change, so the bundled kernel was rebuilt for both targets; parity against the JVM is unchanged, 342 reference values bit-identical or within ULP on JS and WASM alike.

  Two things surfaced while wiring it. A cap is made OUT of the shoulder's wall, so capping a wall-less stub adds nothing - which is why the flag alone was never going to be enough. And an absent shoulder thickness is not a zero one: OpenRocket fills it from the part's own wall the moment the shoulder gets a length (`Transition.setForeShoulderLength`), which is worth knowing, because the panel shows a blank key as `0` and the kernel is not using that 0.

- **A shoulder can follow the tube it plugs into.** A switch beside each shoulder diameter, on a nose cone and on both ends of a transition. With it on, the diameter IS the bore of the part next door, and stays that way: widen the tube's wall and the stub that goes into it follows in the same keystroke. A shoulder diameter was never a free choice to begin with - it is the bore of the neighbor, transcribed by hand, with the usual result that resizing the tube left the stub at the old size and nothing said so.

  It is an explicit switch rather than "leave it blank and we will work it out", which is how OpenRocket spells auto for a ring's radius. For a ring, absent means "fill the tube". For a shoulder, absent already means "this part has no shoulder" - the starting design and most imported files are exactly that - so deriving from absence would have grown a shoulder on every design ever loaded and quietly changed its mass and CG. So the switch is set on parts created here and never on parts read from a file.

  Only the DIAMETER follows; how far the stub reaches into the tube stays a build decision. The resolver runs on every tree edit rather than at each read site, so what lands in the node is a plain number and the kernel bridge, both views, the DXF sheet, the print solids and the `.ork` writer need to know nothing about it. `.ork` has no tag for the switch, so a desktop round trip keeps the resolved number and freezes it, which is the same trade the linked-dimensions item records.

- **A coupler is drawn at the size you would cut it.** Every internal in the sketch was sized through one rule whose radius is capped at 85% of the parent. That cap is right for a chute, whose box is an invented fallback rather than a dimension anybody entered, and wrong for a coupler, which fills the bore by definition and so hit the cap every single time - while the DXF cut sheet, the printed solid and the 3D model all sized it from the real bore. One part, two sizes, depending on which view you were looking at. Rings, couplers, bulkheads and engine blocks now go through that same shared resolution in the sketch too: their own radii, else the bore of the tube they sit in, with a ring's bore taken from the mount through it. Everything whose size is still a fallback keeps the cap.

- **Couplers and inner tubes have their own ink.** They were the two parts deliberately left neutral, on the grounds that they "really are tube segments". What that produced was two unlabeled gray boxes told apart only by size, which is exactly what the cap was distorting for one of them. They now carry a color and a tag like every other internal.

- **A shoulder can be seen in the 2D sketch as well.** It was drawn there all along and reported as working because the rect was in the DOM, which is not the same as being on screen. A shoulder is a snug fit by definition - a 24 mm stub in a 26 mm tube - so its dashed box always lands within a pixel or two of the tube's own outline, and it shared the neutral gray every other dashed annotation used, against a tube stroked in a gray almost the same. It now carries its own ink, and the OWNING part's color when that part has one, which also says whose shoulder it is where two meet: a transition's fore shoulder and a nose cone's aft shoulder can sit in the same tube. Hovering names the part it belongs to.

- **Shoulders are part of the 3D model.** The stub that plugs a nose cone or a transition into the tube next door round-trips through `.ork`, is editable, draws in the 2D schematic and is part of the printed solid. The 3D builder was the one place that never read the keys, so the model stopped dead at the base of the cone. It is two more points on the same revolved profile, the pair `solidMesh` already appends for the print, and a shoulder wider than the part it steps down from is clamped rather than revolved into a flange standing proud of the airframe. A shoulder lives inside the neighboring tube, which is the one place the view could not show it until the airframe could be opened.

- **Look inside the rocket: a cutaway view in 3D, and something to see in it.** The 3D model drew the airframe and the loaded motor and nothing else, and said so in a comment ("Other internal components are not rendered in 3D (invisible in tubes)"). The only way to see where a centering ring sits, or whether the chute has bay to sit in, was the flat 2D schematic. **Cutaway**, beside Reset / Side / Aft, opens the airframe along its centerline; the mount, the rings, the couplers and the packed bays inside it are then seen directly rather than through a translucent shell, and the shell stops being translucent while it is open, because see-through exists to show what is inside a closed hull and only muddies an open one.

  Only the AIRFRAME is cut. What is inside it stays whole, so this is a rocket opened along one side rather than a scene sliced in half, and there is no hollow cross-section to cap. Body tubes and motor mounts are built as tubes now rather than solid rods, with the wall the part list already carried, so a cut shows a wall and a bore instead of the hairline a zero-thickness shell leaves. A wall thicker than the radius loses the bore and keeps the tube: the print export returns nothing there on purpose, since a blocked bore must not ship as a part, but a view that dropped the tube would just lose the rocket.

  **The internals are not drawn at invented sizes.** Centering rings, tube couplers, bulkheads and engine blocks come from the same resolution the DXF cut sheet and the printed solid use, so the ring you look at is the ring you would cut: explicit radii, else the enclosing tube's bore, with a ring's own bore taken from the motor mount it centers. That resolution moved out of the DXF writer into its own module so the 3D view could use it without dragging the R12 serializer into the first-paint bundle. Packed recovery gear and mass objects are drawn at the extent the 2D schematic dashes in, from one shared rule rather than a second copy of it, because the two views disagreeing about what fits in a bay is worse than either being rough. Their packed size still only reaches the tree from an imported `.ork` - the editor has no field for it and the kernel never reads it - so on a design built here this is the schematic's fallback box, and giving it a real one remains the recovery packed-dimension item's job.

  A click on the cut-away half is passed through to whatever is behind it. The raycaster knows nothing about clipping planes, so without that, pointing at the opened side would select a part nobody can see.
- **`.rse` motor import, which is how a hybrid gets into a design.** RASP `.eng` has no field for what a motor IS, so every motor imported from one was a motor of unknown type, and a hybrid you wanted to fly was a hybrid you could not bring in from a file at all. The import button takes RockSim `.rse` now, and the format is picked from the file's BYTES rather than its name — the same way `.ork` and `.rkt` are already told apart — so a `.rse` saved as `.eng` by a site that guessed still reads correctly.

  What arrives with it is more than a label. `.rse` records the mass at every sample, where `.eng` gives one propellant weight and leaves the mass curve to be reconstructed from the thrust curve; the simulation now flies the measured figures when the file supplies them. It carries the motor's real launch CG instead of the mid-length approximation RASP forces, and it is the only one of the two that can say a motor is sold PLUGGED, which is what the picker's plugged filter looks for. A file that asks for its own mass or CG to be recalculated (`auto-calc-mass`, `auto-calc-cg`, and an ABSENT flag means recalculate) gets the same reconstruction `.eng` does, which is what OpenRocket does with it. One `.rse` can hold a manufacturer's whole range rather than one motor, so every motor in the file is imported and the picker says how many landed.

  `services/rseParser.ts` is a TypeScript PORT of OpenRocket's `RockSimMotorLoader`, not an extraction of it, for the reason the `.rkt` design reader is one: that class is SAX-based and pulls in the file-loading machinery the engine extraction deliberately leaves behind. Three upstream pieces are deliberately not ported and each says so at the top of the file, the interesting one being `AbstractMotorLoader.calculateMass` — the mass reconstruction it does is the arithmetic `samplesToMotorSpec` was already doing for every motor without a mass column, so rather than carry a second copy the tests hold the two descriptions to each other.

- **Save a part you built, and pick it again on any design.** The component picker offered ~2,900 manufacturer parts and no way to add your own, so a nose cone dimensioned by hand had to be dimensioned again on the next rocket. **Save as part** now sits under that picker in the component panel, and what it stores is the WHOLE component rather than the handful of dimensions the picker's columns publish: the material and finish, a nose cone's shoulder and shape parameter, a parachute's line count and deployment settings, a body tube's motor-mount flag, the part's color. None of those has a column in a catalog row, which is why a saved part carries its own node and applying one writes that node instead of the per-type dimension map a catalog pick writes.

  Your own parts are listed in the same dialog as the catalog and are ordinary rows in it: searched, faceted, range-filtered, fit-ranked and sorted alongside the manufacturers' parts, marked with a ★, and removed by the ✕ beside them. They sort AHEAD of the catalog under every column and both directions, because the picker draws a capped 200-row window over 1,088 body tubes, and a part you saved and were told was saved must not be off the end of it. Saving again under the same maker and part name replaces the earlier copy. A part that could not fill the picker's columns is refused at the save rather than stored and never seen again, and a refused write says so instead of closing the dialog as though it had worked.

  **A saved part can be edited**, from My Parts, without going back through a design: its name, maker and notes, and its geometry, material and color. The dialog is master-detail, the shape the motor picker already uses: the library on the left grouped by type, the selected part's editor on the right, one pane at a time on a phone with a way back. Saving leaves the part selected and refreshes the list under it, because editing a library is something you do to several parts in a sitting and a modal per part makes each edit a separate errand. Discard puts a part back as it was stored, and moving to another part with unsaved edits asks first. The editor is built out of the property panel's own field rows rather than a second set of inputs, so a saved nose cone is edited with the same fields, in the same units, with the same validation as a nose cone in a rocket. It leaves out the half of the panel that describes a part's PLACE in a rocket - position, move, the fit-ranked picker, the descent-rate readout - because a saved part has no parent and no design to be judged against until it is applied. This is also why a saved part's id is now opaque and stable rather than the maker and name spelled out: an id that encoded the label made a rename inexpressible, since it produced a different id and so copied the part rather than moving it, leaving the original behind under the old name. Saving again under a name another part of the same type already uses is refused, since two identical rows in the picker cannot be told apart.

  **Menu > My Parts** is where the whole library lives, every type at once, independent of what the open design contains. That is not a convenience: the picker only opens when a component of a MATCHING type is selected, so a saved bulkhead was invisible, and could not be deleted, on any rocket without a bulkhead in it - reaching it meant adding a throwaway part to get at the picker. It is the same argument the saved launch locations dialog was built on, and it shows parts the picker deliberately hides, the ones missing the dimensions they would be listed by, since the only list you can delete from must not be the one that drops them. Deleting asks first, here and in the picker alike, because a saved part can be the only copy of geometry somebody worked out once the design it came from is gone.

  They persist under `parts:custom` through a new swappable `PresetStore`, the fourth store of that shape after motors, materials and templates, and the picker and the manage view both refresh in place when one is saved or deleted rather than tearing down an open dialog. Parts attached to the one being saved are not saved with it: the apply path is a shallow merge and every child would arrive carrying the id it had in the design it came from, so an assembly needs its own apply. The save dialog says so before you save rather than leaving it to be discovered on another rocket.

- **The motor picker filters by total impulse, by whether a motor comes plugged, and by what actually fits the mount.** Three filters that were missing for different reasons. The impulse CLASS chips were the only way to narrow by how much motor it is, and a class is a doubling bucket: H covers everything from 160 to 320 N·s, so "at least 400 N·s" is a number that comes out of a design and lands between two letters with no chip to pick. There are min and max boxes now, in whatever impulse unit you work in, beside the class chips in the motor dashboard as well.

  **Plugged** finds the motors sold without an ejection charge, which is what a staged flight or an electronically triggered recovery wants: 381 of the 815 bundled motors, and 374 of those have no numeric delay at all, being mostly reloads and every hybrid. It filters on what the manufacturer LISTS rather than on what is possible, because any motor can be flown plugged and the delay control already offers that on every one of them - so this answers the other question, which is which motors are built that way.

  **Fits the mount** is a checkbox that says what it measures. It was a claim the picker's own documentation already made and the code did not: what really happened was that the diameter slider's top stop was quietly defaulted to the mount's size the first time you opened the picker, which narrowed the list with nothing on screen saying why, and then became the remembered setting. Pick a motor for a 29 mm mount once and that stored range followed you to a 54 mm mount and hid every motor it exists to fly. So the mount's cap is now the checkbox's job - per-mount, visible, and switchable - and the diameter range is a plain preference again. It judges the LENGTH too, counting the motor overhang, because that is where the app already seats a motor: a 75 mm motor in a 70 mm tube hangs 5 mm out of the aft end and the rocket flies it, so measuring against the bare tube would have hidden a motor that fits. A motor whose length the catalog never recorded is judged on bore alone rather than dropped, since every bundled row carries one but a motor imported from an `.eng` need not, and hiding it would be a guess dressed up as a measurement.

  The diameter slider is marked at every standard motor size, so the ten positions read as 6, 13, 18, 24, 29, 38, 54, 75, 98 and 150 mm rather than as a continuous scale with a number that only appears once you have dragged it. Each mark names its size on hover, and the marks inside the selected range are lit, so they say which sizes are in as well as where they are.

  Ticking the box PULLS THE DIAMETER CEILING DOWN to the size the mount takes, and clearing it gives back whatever ceiling you had, so the restriction is a thing you can see on the slider rather than a hidden rule. The whole track stays draggable, and dragging the ceiling past what the mount takes clears the box, because asking to see 38 mm motors in a 24 mm mount is asking to see past the mount. It never widens a narrower choice: someone who asked for 13 mm and under did not ask for 18 mm by ticking a box. What is REMEMBERED between sessions is your ceiling and never the mount's cap. An empty list says so and names the fit filter rather than leaving a blank panel. The picker's filters now read in the order the questions come in: the engine code, the maker, the impulse class, the impulse itself, then the diameter, which is a property of the mount rather than of how much motor this is.

- **One dialog shell, and any dialog can be widened.** Twenty-two dialogs each hand-rolled the same five things: the overlay, the panel, `useFocusTrap`, a `stopPropagation` to keep a click inside from closing it, and a `✕`. The copies had drifted, and the drift was the bug. Two skipped the `.dialog-panel` class and so never got the full-bleed treatment every other dialog has on a phone. Nine declared no maximum height and ran off the bottom of a short window. Three different title scales were in use, so a heading changed size depending on which dialog you opened. The accessible name was sometimes an `aria-label` repeating the visible heading instead of pointing at it, and one dialog put `role="dialog"` on the OVERLAY, telling assistive tech the whole viewport was the dialog.

  `components/common/Dialog` replaces all of that with one component: overlay, panel, focus trap, Escape, a heading that IS the accessible name, `leading` controls before the title for a dialog you navigate within, an `actions` slot in the header, a `toolbar` band under it and a pinned `footer` below. Three body layouts, because there are genuinely three kinds of dialog: `scroll` for a list or table, `pad` for prose and short forms, and `fill` for a map, a chart or two panes that scroll separately, which is the one case that needs a definite height rather than a maximum because a `flex-1` child of an auto-height parent collapses to nothing. A dialog whose height must not follow its content can state one, so the settings panel no longer resizes and re-centers itself every time you switch between a tab holding two rows and one holding thirty. Three named stacking layers replace the three z-indexes that were being picked by hand, and the backdrop click now stops bubbling for every dialog rather than only the one that had noticed it needed to: a nested dialog renders inside its parent's overlay, so a bare close there dismissed both at once.

  **Escape now closes the dialog on top, and only that one.** The listener has to be on the window, because a dialog is not always the thing focused when Escape is pressed, so every open surface heard every press and two of them both closed: dismissing the rename prompt inside the design library shut the library behind it too. One dialog, the flight path's stage colors, had spotted this and written its own capture-phase listener with a `stopPropagation` to stop it, which only works between two surfaces that already know about each other - which is why it existed in exactly one place. The rule belongs to the trap every modal shares: the last open surface in document order answers, and a modal that deliberately cannot be dismissed swallows the key rather than passing it down to whatever sits underneath. A dialog can also refuse to be dismissed while it is busy: the report export cannot be closed by a stray backdrop click or keypress while the PDF is being written, because that drops the run's result and the "Loading" state with it, while its ✕ keeps working, since a close button that stops responding is worse than an interrupted export.

  **The expand control** sits in the header of any dialog it would help. It widens the panel to nearly the viewport and the choice is REMEMBERED per dialog, because expanding is a preference and not a gesture: someone who wants the parts picker wide wants it wide every time, and re-expanding on every open would be the same annoyance as re-typing a filter. It is hidden below the `lg` breakpoint, where the panel is already full-bleed and the control would do nothing, and absent entirely from a dialog whose content widening would only make harder to read, like a page of prose.

  Every dialog in the app is on it: the parts picker, the motor picker, the motor dashboard, the motor spec sheet, Settings, Help, the design library, the examples list, saved locations, the location editor, the site map, the wind profile, the report export and its print settings, the flight-path export and its stage colors, the flight-data CSV export, the 3D-print export, the rocket configuration, the scale dialog, the rename prompt, About and Privacy. The confirmation prompt and the work-in-progress notice share a second shell, `components/common/AlertDialog`, because they are `alertdialog`s rather than dialogs: a heading, a sentence and a button or two, with no toolbar, no footer, no scrolling body and nothing to expand into. What they need and an ordinary dialog does not is a DESCRIPTION - the message is the thing a screen reader should read out on arrival - and neither of them pointed at one. They had drifted the same way their bigger siblings had: two backdrop opacities, two heading scales, one naming itself with an `aria-label` repeating its own visible heading and the other with a hardcoded element id that would have collided the moment a second prompt appeared, and one carrying a hand-written window-level Escape listener beside the one every modal already shares. Whether there is a way OUT is now one thing rather than three: given a cancel handler it is the button, the Escape key and the backdrop alike, and without one the prompt must be acknowledged - no button, and Escape and the backdrop do nothing rather than dismissing something the app is waiting on. Both keep the z-index they had, now named as a layer, and both stay centered cards on a phone rather than filling it.

  Converting them turned up four things beyond the drift above. The 3D-print export's Save row had been pinned below its part list and would have started scrolling with it. The report export needed TWO focus traps, with the dialog's switched off whenever its print-settings popover was open: the popover was a sibling of the panel inside the shared overlay, and a trap anchored on a panel cannot reach controls that are not inside it, so the fill color, paper size and orientation were unreachable by keyboard - as its own dialog on its own layer it simply owns its own trap. Help was titled "Help" while showing a page called something else, and now takes the page's title as its heading and accessible name. And the per-dialog close labels the shell replaced left `picker.close` and `help.close` behind as dead strings, which the key test caught.

- **The part picker ranks the catalog against your design, and shows the numbers you pick on.** It was a single narrow column of 2,941 parts with one free-text box, and it hid the fields that decide the choice. A body tube read `Always Ready Rocketry BT_1.15_12_MMT` / `⌀ 32.4 × 304.8 mm` / `Blue Tube, 1.15"/29mm, MMT, 12" len`: the outer diameter stated twice, the BORE (29.2 mm) only as prose although it is the number that decides what goes inside the tube, and the material absent entirely although the picker's job is to prefill geometry AND material. Now a sortable table with the columns each type is actually identified by, the unit named once in the heading rather than after every cell, a manufacturer facet, an outer-diameter range typed in whatever unit is on screen, and honest counts.

  **The part that OpenRocket's preset dialog cannot do:** the picker is opened from a known node in a known design, and used to be told only the component TYPE. It now receives the geometry around that node, so it can rank by what fits. Picking the coupler for a Public Missiles 2.1" tube meant reading 237 rows; the five that actually fit its 51.5 mm bore now lead the list, best gap first. Fit RANKS rather than hides, which is the second design this went through: hiding by fit opens empty on ordinary designs, because no nose cone in the catalog is within the match tolerance of a 54.66 mm airframe (manufacturers' nominal sizes cluster in families that do not line up). So the fitting parts come first, the rest are still there to scroll past, and a checkbox hard-filters for anyone who wants that.

  Fit means different things per part and the rules say which: a coupler, centering ring or bulkhead is measured against the bore it slides INSIDE, with 2 mm of glue-gap slack and a few hundredths of nominal oversize allowed; a body tube or nose cone is measured against the airframe it CONTINUES, to a much tighter 0.6 mm, because two tubes 2 mm apart in diameter are not the same tube, they are a visible step. A centering ring additionally has to clear the motor mount it holds, which is its SIBLING in the same body tube rather than its child, and counting couplers among those siblings made the widest part in the bay the constraint instead of the mount. A parachute abstains: its fit is packed volume, which the model does not carry, and ranking a canopy diameter against a bore would be confidently wrong.

  The enclosing bore is why this needed a module of its own. It is not a stored field: a body tube carries an outer radius and a wall thickness, so the number a coupler has to hit is `(outerRadius - thickness) * 2`, and nothing had ever computed it.

  Also in the rows: the bore and the material, for every type that has them; a nose cone's shape TRANSLATED rather than printed as the kernel's lowercase enum, which read `ogive` / `haack` beside translated headings in all ten languages; and a Notes column carrying only the part of the catalog description that is nowhere else. Those descriptions are comma-separated and mostly restate the geometry, so the segments that are purely a measurement are dropped, along with a leading segment that just names the type, a part number repeating the Part no. column however it is punctuated, and a nose cone's shape now that it has a column. `Blue Tube, 1.15"/29mm, MMT, 12" len` becomes `Blue Tube · MMT`: the trade name and the role, which are what people search by and were the only things in there that the table could not show. A part number is dropped however the catalog spells it: 417 rows put two identifiers in the one field and cite them singly (`PN BNC-20R`) or slash-joined (`PN 30400/30408`), which together accounts for 1,136 of the 1,227 rows carrying such a segment. The 91 left name a DIFFERENT code than the part-number column does, which is the one place that code appears, so they stay.

  **The columns hold still.** The table was laid out by the browser's default `table-layout: auto`, which measures each column from whichever rows happen to be rendered, so every keystroke in the search box relaid the whole thing out and the columns visibly jumped. Each column now declares a fixed width, the one Notes column absorbs whatever is left, and cells truncate into their width with the full value on hover, which is also what keeps a long material name from making one row taller than the others.

  **Two more facets, per type.** Nose cones filter by shape, and everything with a material filters by material. The raw material names could not be a filter: body tubes alone carry 39 of them, including eight near-duplicate `Fiber, vulcanized, Coupler, BT-xx, bulk` rows and three spellings of one balsa density. So the facet groups them into families by an ordered set of keyword rules, and 39 becomes six. Order matters in those rules, because `Fiberglass, G12, filament wound tube` and `Carbon fiber epoxy composite` both contain the word "fiber" and a glassed phenolic is a phenolic; a test asserts every material in the shipped catalog lands in a family, so a sync that brings in a new one cannot quietly drop out of the facet. Each dropdown is built from what that type actually has, so it never offers a value that would return nothing: body tubes have six families, bulkheads five, and they are not the same five. The Material COLUMN still shows the raw catalog name, because G10 and G12 are both "Fiberglass" to the filter and are not the same material to build with, and the material joined the free-text haystack so `g12` and `mylar` are still reachable by name. Family names are deliberately left untranslated, to match the column they sit over.

  **An inner tube can be picked at all.** It could not before, and neither the catalog nor OpenRocket has an inner-tube type: an inner tube IS dimensionally a body tube, so it reads the body tube rows, 51 of which are explicitly motor mount tubes (`Blue Tube, 1.15"/29mm, MMT`). `catalogPatch` needed no new case, because the row it receives is a body tube row. It gets no fit control, though, and that is deliberate: the constraint that decides an inner tube is the MOTOR it has to take, the motor belongs to a simulation rather than to the tree, and scoring its outer diameter against the enclosing bore would rank a snug 51 mm sleeve above the 29 mm mount actually wanted. The outer-diameter range answers the physical question instead.

  **Shape and drag coefficient sort.** Both were columns with no order on them, which was an oversight rather than a decision.

  **No drag-coefficient filter, because there is nothing to filter.** Every one of the 151 parachutes the catalog ships carries a null Cd: OpenRocket's preset files have no DragCoefficient for a parachute, so the app applies its own default. A facet would have offered exactly one value. What the column showed instead was worse than useless, a bare `0.80` that read as a published spec, so a value the catalog omitted is now parenthesised with the reason on hover, and the default itself lives in one constant that the column, its sort and `catalogPatch` all read.

  **The filters sit on two rows.** One row ran to a search box, three dropdowns, two number fields, a checkbox and a button, which wrapped unpredictably. Free text has the first row to itself; the narrowing controls have the second, with **Clear filters** pushed to the far right so it reads as the way out rather than as one more filter.

  Two smaller lies are gone. The list sliced to 300 rows and then printed 300 as the total, so a 1,088-row type read as though the catalog were small; it now caps at 200 and says `Showing 200 of 1,088`. And the footer's `{{count}} parts` was a bare key called with a count, so a single match read "1 parts"; it is a real plural family now, in each language's own categories.

- **Dutch, Polish, Russian and Japanese.** Four more languages in the switcher, `Nederlands`, `Polski`, `Русский` and `日本語`, bringing the app to ten. Each is a full translation of all 1240 non-plural strings, plus however many plural forms its own grammar needs, so no screen falls back to English partway through.

  These four are what the plural-category fix above was for, and each one leans on it differently. Japanese selects between exactly one form, so its file carries 1248 keys and no `_one` that nothing would ever reach. Dutch selects between two, like English and German, so 1256. Russian and Polish select between four, so 1272, and those extra `_few` and `_many` forms are the whole reason they could not ship before: Russian inflects the same noun three different ways across 2, 5 and 21, and with only English's two suffixes everything but 1 and the fractional case came out in English. Verified at runtime rather than by key count, across counts 0, 1, 2, 3, 5, 11, 21, 22, 25 and 101 in every language, checking both that the category selected matches `Intl.PluralRules` and that no English word leaks into a non-English bundle.

  Nothing about the app had to change to take them. A region tag was not needed for any of the four, so all of them widen the way the existing base languages do: `nl-BE`, `pl-PL`, `ru-UA` and `ja-JP` each land on their base bundle, and every case is pinned in the resolution test. Glyph coverage comes from the OS through the `system-ui` stack rather than a bundled webfont, so Cyrillic and Japanese needed no font work. One typographic note for whoever edits `ru.json` next: the ten long dashes in it are grammar, not decoration. Russian has no present-tense copula, so the dash is what stands in for "is" between two noun phrases, and it is also the standard mark after a quoted term being defined. Removing them leaves sentences that are simply ungrammatical.

- **Portuguese, as two languages rather than one.** Brazilian and European Portuguese ship as separate translations, `Português (Brasil)` and `Português (Portugal)`, because about a third of the app's strings are not the same sentence in both: the nouns it leans on hardest are each a different word (rocket, stage, launch pad, thrust, drag, landing), the everyday verbs differ (save, delete, download, run), and a verb in progress is built one way in one and another way in the other. A single bundle would have read as a foreign dialect to one of the two audiences on every screen.

  Shipping a region-tagged locale meant removing `load: 'languageOnly'` from the i18n setup. That option existed to widen a browser set to `es-ES` or `es-MX` onto the `es` bundle, but it strips the region from EVERY code, so both Portuguese tags would have resolved to a `pt` bundle that does not exist and every Portuguese browser would have got English. i18next's own best-match already does the widening that option was there for, and it widens in both directions: an unshipped region falls back to its base language where we ship one (`es-MX` to `es`), and a bare language falls forward to the first region listed where we ship only regions (`pt` to `pt-BR`). Both halves are load-bearing and neither is visible in the config, so every case is pinned in a test rather than left to be rediscovered. `pt-AO` and `pt-MZ` write the European orthography but land on `pt-BR`, which is the deliberate cost of putting the larger population first behind a bare `pt`.

- **Settings ▸ Materials: what a newly added part is made of.** A row per material slot — the fourteen structural part types, plus a parachute's canopy and its shroud lines, a streamer and a shock cord, since a part can carry more than one kind of material at once. Custom materials and the adhesives can be defaults too. A row left on **Automatic** keeps the built-in density, which is what everything did before.

  The choice is spent when you ADD the part: the material is written onto it there and then, so it shows in the property panel and travels with the design in the `.ork`. Desktop OpenRocket has the same preference and resolves it the other way, leaving the part unset and applying the preference when it computes mass — which means the same file weighs one thing on the machine that made it and another on the machine you sent it to. Doing it at creation needs no engine change, and it puts what you chose in the file. Parts already in a rocket are never touched, and neither is a design you open.
- **Two elastic cords that upstream gets wrong by a factor of ten.** OpenRocket's flat elastic cords read 0.0018, 0.0043 and 0.008 kg/m for 2, 6 and 12 mm, and then 0.0012 for 19 mm and 0.0016 for 25 mm: the two widest lighter than the 6 mm. It is a dropped digit, and it makes a 3 m shock cord of 3/4 in flat elastic weigh 3.6 g instead of about 37. **Elastic cord, corrected** is offered in both widths at 0.0123 and 0.016. mmrocket-sim found the error and published those values, credited in `engine-java/ATTRIBUTION.md`; interpolating upstream's own 6 mm and 12 mm entries gives 0.0127 and 0.0167, the same answer. The wrong entries stay exactly as they are, because a design that names one has to keep reading back the density it was saved with.
- **The twenty-two shock cord and shroud line materials that were missing.** The app's material table is supposed to BE OpenRocket's, because the engine applies a material by its density and any difference means the two programs weigh one design two ways. It was not: upstream carries 42 line materials and the app carried 20. Absent were every **Kevlar 12-strand above 5/16 in** (the 3/8, 7/16, 1/2, 9/16, 5/8, 3/4 and 1 in sizes), all five **nylon flat webbings**, both **elastic rubber bands**, all seven **braided elastic cords** and the **Paraline** - which is most of what a shock cord or a set of shroud lines is actually made of. Nothing said so from inside the app: an absent material is simply one the picker does not offer, and a `.ork` naming one arrives as a custom material with its density intact, so the design still flies right and only the list looks short. The block is now generated from `Databases.java` rather than typed.
- **Thirteen adhesives in the material list, because upstream has none.** OpenRocket's material database has no epoxy and no wood glue, which was fine while nothing in the app was made of glue and stopped being fine the moment fin fillets started counting toward mass and CG: the fillet's material picker could offer thirty-one materials, not one of which a fillet is ever made of. The table now carries an **Adhesives** group: West System 105 with each of its four hardeners, Six10 and G/5; AeroPoxy PR2032/PH3660 and ES6209; RocketPoxy G5000; TotalBoat High Performance; BSI Quik/Mid/Slow-Cure; J-B Weld Original; and carpenter's glue. Every density is read off a manufacturer document, cited in a comment beside the entry and again in the documentation, and where the maker publishes a CURED specific gravity that is the number used, since that is what a fillet actually weighs. `data/materials.ts` now keeps the two lists apart: `UPSTREAM_MATERIALS` stays verbatim OpenRocket and may not be added to, because a name or density this app has and the desktop does not is a design the two weigh differently; `ADHESIVE_MATERIALS` is ours, and the documentation's **Materials** section is its justification. ProLine 4500 is deliberately absent: its maker publishes no density and neither do the community comparisons, so the docs give the recipe for measuring your own rather than the app carrying a guess. The same section covers the two traps: a wood glue bead is 52% solids and dries to half its volume, and a fillet thickened with microballoons can be 600 rather than 1180.
- **Fin fillets are flown, not just stored.** The glue bead along a fin root has real mass, and OpenRocket's kernel has always known how to compute it: `FinSet.calculateFilletVolumeCentroid` gives its volume and centroid, and `calculateCM` adds `filletMass` to every fin unconditionally. What was missing was one line on this side. The engine bridge never called `setFilletRadius`, so the field stayed at its initial 0 and every fillet flew as if it were not there. The `.ork` reader, the writer and the rocket scaler all carried `filletRadius` faithfully, which is exactly what made it invisible: the number was on disk, in the tree and in the panel's reach, and only the engine never saw it, so a design with 6 mm epoxy fillets simulated light against desktop OpenRocket with nothing on screen to say why. It is wired now, with the bead's own material and density, and a fin set gains a **Fillet** section: the radius, and what the bead is made of. On three fins around a 26 mm tube a 6 mm cardboard fillet is +1.1 g and moves the CG 2 mm aft; the same bead in something epoxy-dense is +2.0 g. A tube fin set has none, since a `TubeFinSet` is a `Tube` and the kernel has no fillet to give it. Two things fall out: the import note that used to say fillets "are not yet counted in mass or CG" is gone, because they are; and the `.ork` writer no longer files a Fiberglass fillet under `PaperProducts`, writing the material's own catalog group when the design has one, the way it already did for every other material. **A design with fillets will read heavier than it did before, which is the point:** it was reading light. Designs without one are unchanged, bit for bit, which the engine parity golden confirms.
- **Fin marking guide: where each fin, lug and rail button goes around the tube.** The report could print a fin's SHAPE but never its POSITION, and a tube fin set got no printed aid at all, because a tube has no planform to cut a template from. A new **Fin marking guide** section prints one 1:1 strip per body tube that carries a fin set, its length the tube's circumference plus a paper thickness, so the ends meet once it is wrapped rather than falling short by the thickness of the paper the marks are printed on. Everything angular on that tube lands on the one strip: fin sets, tube fins, launch lugs and rail buttons, each an arrow across the strip under its own name, which is what makes the guide answer "where does the lug go relative to the fins". The seam is placed in the widest gap between marks so nothing to be marked ends up under the tape, and a **Fore** arrow says which way the strip wraps. Canted fins mark on the slant, with dashed lines at the root's fore and aft ends and a cross at its center. A strip too long for the page, which is every 4 in tube on every paper the report offers, is cut into pieces that butt together and are taped in order, with the joins kept off the marks; a strip is never scaled down. Anything no strip can carry is named in a footnote instead of being dropped: a lug on a nose cone, whose circumference changes along its length, or a lug on a tube with no fin set. Ported from OpenRocket's `FinMarkingGuide`.
- **Fin sets have an editable rotation, and every part's rotation is now called the same thing, in the same place.** Where a set's first fin sits around the body round-tripped through `.ork` and the 3D view drew fins at it, but nothing could set it, so the only way to have a fin set anywhere but 0 was to import a file that already did. It is now a field on all four fin set types. The marking guide is what made it matter: the guide prints where each fin goes relative to the launch lug, and that relationship is this field. While adding it, the panel was calling one kernel property by two names, since `FinSet.getBaseRotation()` returns `getAngleOffset()`: a launch lug and a rail button said **Angle around body**, a pod said the same, and the new fin field said Base rotation. All four are **Rotation** now. They have also moved out of the dimension list, where a lug's angle sat between its radius and its length, into the component panel's **Placement** section beside **Position from** and **Offset**, which is the section that already answers where the part goes rather than what shape it is. The **Overrides** rows now come last on every part, rather than sitting between the material and the placement: they override what the rest of the panel adds up to, so they belong after it, and where they fell used to depend on the part, since a parachute has two sections between them and a body tube has none. The panel is sections throughout now, each under its own heading: **Part** (the name and the catalog picker, the rows that say what the part is rather than what size it is), the dimensions, **Fin tab** (a fin's through-the-wall tab, four fields describing the piece buried in the airframe, which used to run on under the planform as though they were four more dimensions of the same shape), **Motor** (whether a tube mounts one, how far the motor hangs out, and an inner tube's cluster), the material, **Placement**, **Appearance** and **Overrides**. Color is in that Appearance section rather than beside the name, because it says how the part is DRAWN rather than what it is, and nothing about it reaches the simulation; it sits directly above Overrides on every part, the two things read least often, in the order they are least often wanted. A stage has no Appearance section, having no color of its own. The Overrides heading was also two sizes and one shade away from the others, which only showed once the sections around it had headings at all.
- **The drift region: where it comes down across a range of winds, not just the one you typed.** *(Experimental — the panel says so, and so does the documentation. Each flight in a sweep goes through the same validated kernel as any other simulation, so the individual landings are as good as the app's flight results generally are, but the region drawn around them has not been checked against a real recovery, and the controls, the default grid and the two-sigma choice are all likely to move.)* The ground track drew the landing point for the single set of conditions in the launch panel, which is the wrong question on the morning of a launch — nobody knows the wind to a tenth of a meter per second or the heading to a degree. A **Drift** button on the ground track now flies a **grid** of winds around that flight (a speed band with a step count, a heading count, and how wide an arc to fan them over) and draws where every one of them came down. Three shapes, in each stage's own color: the **shaded envelope**, which is the exact region of the conditions flown and the shape to walk out and look at; the **dashed ellipse**, the familiar two-sigma recovery ellipse that fits on a flight card and compares between designs and days; and a **dot per flight** with a cross at the mean landing, so where the dots crowd is where the rocket lands on most of those days. The readout under the plot gains each stage's swept **range band** beside the distance and bearing it already carried. Everything but the wind is held exactly as the simulation has it — same design, motor, ignition, rod, site and run settings, and one turbulence seed across the whole grid — so the spread is attributable to the wind rather than to a dozen things moving at once, and the same sweep run twice draws the same region. A multilevel wind profile is scaled and turned as a whole rather than replaced, so the shear it describes survives the sweep, and each level keeps its own turbulence intensity. The flights go over the same worker pool a batch of simulations uses, several at once, with a running count and a Cancel; a canceled sweep keeps nothing, because half a grid is an arbitrary subset of the conditions rather than half a region. The speed band is capped by the same NAR / Tripoli limit the Run button enforces, so a sweep never draws ground the app refuses to fly to. One sweep is held at a time, it belongs to the flight it was built around, and editing the design or that row's motor or conditions leaves it up with a note saying it is older than what is on screen rather than silently redrawing it as current. Nothing about it is saved with the design.
- **Every download says which rocket it came from.** A downloads folder is a flat list shared with everything else the browser saves there, and the exports did not agree on how to name a file: the drag-sweep CSV was the literal **aero-table.csv** and the flight-events CSV the literal **flight-events.csv** - so the same two files from a second design silently replaced the first - while a printed part came out as **Nose cone.stl**, which does not say whose nose cone. There is one rule now, in reading order. Something about the rocket is the rocket plus what the file is: **Bertha-design.ork**, **Bertha-design.rkt**, **Bertha-design.CDX1**, **Bertha-aero-table.csv**, **Bertha-report.pdf**. A design document is no exception to that, because a name should say which rocket AND which document, and re-saving an opened **Bertha-design.ork** gives the same name back rather than stacking suffixes - the rocket's name is read from inside the file, never from the filename. Something about a simulation carries the run as well, because a rocket has several and they are the thing being compared: **Bertha-C6 flight-flight-data.csv**, **Bertha-C6 flight-flight-events.csv**, **Bertha-C6 flight-flight-path.kml**. A printable part carries the component: **Bertha-Nose cone.stl**. The rocket's name is resolved once, the same way everywhere - its own name, else the file it was imported from, else the app default - rather than four exports each spelling that fallback out inline. A part that is blank drops out instead of leaving a double separator, so an unnamed design or a sim with no name yet still gets a usable filename, and nothing can produce a file called only ".csv".
- **The flight events table exports to CSV, and "Before you fly" folds.** A **⬇ CSV** button on the events table writes the timeline as a file, titled with the run it came from. Where the table on screen keeps the per-event extras on a sub-line, the file gives every one of them its own column - stability, thrust-to-weight, angle of attack, Mach and dynamic pressure - because a spreadsheet wants a rectangle it can sort and chart, and a file has no 380px column to respect. Most rows leave most of those columns blank, which is the honest shape: only the rail-departure row has a thrust-to-weight, and an empty cell says it does not have one rather than that it is zero. Values are written in the Settings units rather than the table's own chips, the way every other export does, because a file outlives the session and often goes to somebody else. This is separate from the flight-data CSV, which writes the per-timestep series and can already carry the events as comment lines: a comment is for a reader, and this answers the other question. Alongside it, the **Before you fly** card now folds: click its heading, acknowledge the notes, and the explanation collapses. The fold is remembered across runs, tab changes and reloads. The acknowledgment is not ceremony - because the fold is remembered, that click is the last time the notes get asked for on this browser, so it is worth being a thing you do deliberately rather than something that happens silently; the dialog restates what the simulation cannot tell you and who is still responsible for the flight. Canceling leaves the card open, and opening it back up needs no acknowledgment, because reading a warning again needs no permission. What does NOT fold is the heading itself - the ⚠ and the words stay above the numbers in both states. The card is a standing caution on every run rather than a notice to be dismissed once, so nothing here can remove its last trace; the explanation is always one click away.
- **The flight as a table of events, and Max-Q.** Results now carries a **Flight events** timeline beside the charts: one row per event, with the time it happened and the state of the rocket at that instant. The engine has always exported the kernel's full event list and the app read five of them, marking those as labels over the charts; a label strip answers *when* and nothing else, and the numbers that say whether each moment went well were computed on every run with nowhere to be read. The events that were invisible are named now (rail departure, ignition, stage separation, tumble, simulation end), each row carries the altitude and speed at its instant, and the moments that are read for more than that carry it: rail departure gives the static margin, thrust-to-weight and angle of attack it left the rail with, and burnout gives its Mach. A deployment says which parachute fired and at what speed, so a dual-deploy drogue is told from the main, and a cluster's burnouts are told from each other. The extras sit under their own row rather than as columns, because only one row in the table has a thrust-to-weight worth printing and a column for it would be one number and a dozen blanks. Every stage is in the one table, interleaved on the single launch clock rather than grouped per stage, because that is the order the flight happened in: a spent booster comes down while the sustainer is still coasting, and the charts beside the table already draw both. **Max-Q** is new, as a row and as a summary tile: the peak of the dynamic pressure q = ½ρv², which is the number that decides whether an airframe holds together, and the one quantity here the kernel never recorded. It is derived in the app rather than added to the engine, because the engine already records both halves of it. The speed it uses is the airspeed, not the speed over the ground: those differ on a windy launch, and dynamic pressure is a property of the air the rocket is flying through. A result saved back when runs kept only the summary series has no air density stored and so reports no Max-Q, rather than a zero that would look like an answer.
- **Map imagery under both results views.** The ground track is drawn over satellite or street imagery of the field the flight was flown from, and the 3D path's ground plane carries the same imagery so the trajectory arcs over the real field instead of an empty grid. **None · Satellite · Street** switches the layer in either view, and the choice is shared with the launch-site map for the session, because it is one question about how you want to read the ground rather than a setting per view. Both views start on **None** and fetch nothing until the ground is asked for: the range rings and the trajectory are the measurement and do not depend on a picture, so opening Results is not a reason to reach out to somebody else's tile servers. The launch-site map is the other way round and still shows imagery by default, because there the picture is the answer. Neither view can use the site map's fixed zoom, since both size themselves to the flight: the tile zoom is derived from the resolution actually being drawn, rounded to the NEAREST step rather than up, which is the difference between 16 tiles and 49 for the same picture. The plan view then scales its tile layer by the leftover fraction, so the imagery bends to the range rings rather than the rings to the imagery, and the rings stay because they are the measurement. The plan view also no longer zooms closer than about 100 m across: still air lands a rocket a tenth of a meter from the pad, and a view scaled to that was a picture of ten centimeters of grass with no imagery at any zoom, so a landing on the pad now reads as a dot on the pad. The 3D ground covers the track's own reach plus a margin instead of the whole 60-unit plane, which is 9 tiles for a typical club flight against 36. Tiles come from Esri as before, carry the credit their terms require wherever they are drawn, and share one cache with the launch-site map; a field you checked at home still draws with no signal, and somewhere never viewed falls back to the plain plot and bare ground plane, which are still correct. Requested with CORS throughout, because the 3D canvas is read back by the image export and a single texture loaded without it would taint that canvas and break the export silently; the tile cache was renamed to retire entries an older build had stored as opaque responses, which cannot answer a CORS request.
- **A comparison appendix: how this stacks up against OpenRocket, ZenRockets and mmrocket-sim.** Three pages in the documentation, in English and Spanish, answering the question the Overview page raised and never settled. Against **desktop OpenRocket** the physics is not the story, because it is the same code: the page is about the program around the engine, and it names what the desktop has that this does not (optimization, custom expressions, simulation extensions and scripting, flight configurations you can switch between, appearance and Photo Studio, the fin marking guide, a library for your own components, `.rse` motors, packed recovery dimensions) with the reason under each, several of them traceable to packages that are simply not in the extraction. Against **ZenRockets** the headline is that they do not run OpenRocket's engine at all, so the same rocket need not give the same apogee in both: their trajectory service is built on RocketPy. They are far ahead on designing the motor itself, on importing an altimeter's flight log, and on half a dozen readouts this does not have yet; this writes `.ork` and `.rkt` back out where they import only, works with the network off, and has Component Analysis. Against **mmrocket-sim** the page leads with the relationship rather than a scoreboard, because the opt-in supersonic aerodynamics in this engine are their work, carried under GPL-3.0 with attribution; it compares what there is evidence for and says plainly why it does not tabulate their interface. Every page opens with the date it was written and the versions it compared, because a comparison goes stale without anything breaking, and every version in that line that could be read from a file is read from one: the app's from package.json, the OpenRocket commit from `extract/UPSTREAM`, mmrocket-sim's from `extract/MMROCKET-SIM`. Each page's longest table is the one listing what the other tool does better, and every row in it carries the reason, because a gap with no reason behind it is just an apology.
- **The flight-path export can be written in a language other than the app's.** A **Language** box beside the units, defaulting to "Same as the app". It belongs to the file for the same reason the units do: a KML going to somebody else may want their language whatever you have the app set to. To make it mean anything, the built-in templates' own English prose moved into the locale files - before this the export localized the eight waypoint names and hardcoded everything else, so "Apogee" translated while "flight path", "ground track" and every line of the summary balloons did not. The whole file follows the box now. A phrase whose word order changes between languages is composed through the translator with its values rather than glued together in the template, because a template joining translated fragments in English order produces English order in every language: Spanish puts the stage name after the word, not in front of it. The strings are on the model as `{{labels.*}}`, so a custom template can follow the box too, and the values behind them are still there for one that wants to write its own sentence. What it cannot reach is text you wrote yourself - the mission name, your component names, and prose hardcoded in an imported template.
- **The KML flight-path export carries the flight's numbers, in Google Earth's own balloons.** The export was geometry and labels only - a path line per stage, a ground track and a named pin at each point of interest - while every number behind the picture stayed in the app. Google Earth already has a place for them: a feature's description, shown in a balloon when it is clicked. There are now three. The **document** carries the flight summary (rocket, motor configuration, launch site and elevation, peak altitude, velocity and acceleration, maximum range from the pad, time to apogee, flight time, and one line per stage giving that stage's landing coordinates, distance, bearing and time); each **stage folder** carries that stage's own range and its landing distance, bearing, time and coordinates; each **waypoint** carries the time since liftoff, the altitude above the pad and above sea level, the distance and bearing from the pad, its own coordinates, and for an ejection the recovery device that deployed. Every coordinate is tagged `(lat, lon)` and written to six decimals, because a bare pair in a KML file is ambiguous in a way that has a wrong answer waiting - KML's own coordinate triples are longitude first, so a reader who knows the format has an active reason to read it backwards - and it is written in the signed decimal degrees the app's own launch fields take, so it pastes straight back in. The landing coordinates are the ones that matter at a launch: a distance and a bearing read the map, but the pair is what you type into a handheld to go and find the rocket, so the per-stage lines lead with it. Maximum range is reported separately from the landing distance because they are different numbers - a rocket drifts downrange under the chute and often partway back, and the range-safety figure is the excursion. A line with nothing to say disappears rather than rendering empty, so a run that ended while the rocket was still in the air reports no landing, and a site with no recorded elevation reports no "above sea level" altitude that would really be a height above the pad. **Summary balloons** switches the whole lot off for a file the descriptions would only get in the way of. The balloon markup is written pre-escaped rather than wrapped in CDATA, so a rocket named `Bill & Ted` reaches the balloon as its name instead of as `Bill &amp; Ted`. Every line carries a bold label, so a balloon reads as a list of facts rather than a paragraph, and nothing else is added around them: the name Google Earth prints above a balloon and the Directions links it prints below come from its own default template, and a custom `BalloonStyle` would replace both. Every described feature also gains an empty `Snippet`, without which Google Earth prints the first lines of each description under its name in the Places tree and turns a tidy waypoint list into a wall of text. The new values are on the export model too, so a custom Mustache template can use them.
- **Longitude is a required launch field, and saved pads are now "launch locations".** Longitude was the one site field a flight would fly without: it was optional, so a blank one silently reached the kernel's Coriolis term and every KML origin as nothing at all, while 0 is a point in the Gulf of Guinea rather than "unset". The map made a wrong one visible, which made a missing one worth refusing: it is marked like the latitude and the site altitude, a run without it is refused and NAMES it, and it is stored as null when cleared rather than absent, so clearing it survives a reload instead of quietly coming back from your defaults on the next open. Saving a location with either coordinate blank is refused for the same reason, rather than minting one at 0°, 0° that would then apply itself silently every time it was picked. Alongside that, the feature is called **launch locations** throughout - the menu, the dropdown, the manage dialog and the documentation - because "pad" is the concrete thing you set a rocket on and what is being saved is a place. The word still means the launch point where it is describing physics (the wind AT THE PAD, the origin of a ground track), which is how the hobby uses it. The stored data keeps its old key, so nothing saved is lost.
- **A map of the launch site.** A latitude and a longitude are four digits each and no feedback whatsoever: a dropped minus sign moves a Colorado field to western China and nothing on screen looks any different. The Launch site card now has **🗺 Show on map**, and the location editor carries a map beside its fields, so the numbers can be checked against the ground they name. **Satellite** imagery is the default because it is the layer that answers the question - a club field is a mown strip in a hayfield, invisible on a street map and unmistakable from above - with a street layer for the roads in and the town you are near. Both come from Esri's map services; the street layer is built on OpenStreetMap data and credits it, but the app deliberately does not draw from OpenStreetMap's own tile servers, which are volunteer-funded and not there for applications to build on. **Clicking the map sets the coordinates**, to the four decimal places 📍 Use my location writes, which is how a field with no published numbers gets entered at all rather than only checked; it writes through the panel's own change path, so it is one ordinary undoable edit, and typing a coordinate moves the pin, so the map and the fields are two views of one thing rather than two places to be wrong. Drag to pan and scroll or use the buttons to zoom; a drag never counts as a click. Tiles are cached as you look at them, so a location you checked at home still draws at the field with no signal - which is the point rather than a nicety, since the field is where there is no signal. Somewhere you have NEVER viewed cannot be drawn offline, and the map says so and falls back to a coordinate grid rather than showing an empty gray box. Built without a mapping library: showing one point and letting it be dragged is the whole requirement, and Leaflet or MapLibre would bring a layer system, a plugin surface and a stylesheet for the parts we do not use, so the tiles are plain images at computed offsets over a Web Mercator projection tested against hand-computed figures.
- **Saved launch locations.** The launch site is a property of the FIELD, not of a flight, and it was the only launch input with no memory: every new simulation meant retyping a latitude, longitude and elevation from memory, which is exactly how they come out wrong. The Launch site card now leads with a location row - a dropdown of the fields you have saved, a button that saves the three numbers currently on screen under a name, and a manage dialog that lists each location with its coordinates (so two fields both called "the club field" can be told apart) and lets you rename or delete one. Applying a location goes through the panel's own change path, so it is one ordinary undoable edit rather than a special case. The dropdown reads **Custom location** whenever the fields match no saved location, decided by COMPARING THE NUMBERS rather than by remembering which location was last clicked - so it stays honest after an import, after 📍 Use my location, or after typing over one field. Picking **Custom location** yourself returns the three site fields to your Settings launch defaults - the Kennedy Space Center as shipped - so the option is a choice as well as a state: it was inert at first, and an entry you can highlight but never pick reads as broken however good the reason for it. It briefly CLEARED the fields instead, which was worse in practice than it sounded, since all three are required: the map had nothing to draw and the Run button refused until you typed a coordinate from nothing. A real place leaves the run flyable and gives the map somewhere to open, and it is read from Settings rather than hardcoded, so somebody who set their own home field gets that instead of Florida. One ordinary edit like applying a location, so undo brings the old site back. Saving under a name that already exists updates that location instead of leaving two entries a dropdown cannot distinguish. A location deliberately holds ONLY the site: the rod, the wind and the atmosphere are conditions on the day, and a location that restored last month's wind would be worse than one that restored nothing, because it would look authoritative. Locations live in this browser on this device through the same swappable-store pattern as custom motors, materials and export templates; no account and no server. The list is also its own menu entry - **Launch locations**, beside the Motor Dashboard - because a manage view reachable only from the one panel that already has a dropdown is a manage view nobody finds; picking a location there applies it to the simulation you have open. A location edits in FULL: name, latitude, longitude and elevation, because the thing you most often want to fix about a location is a number and renaming could not reach it - a coordinate typed wrong, or a field's published elevation corrected. The same dialog creates one from nothing, which is how you add a location from the menu, where there are no launch fields on screen to capture. Its bounds are the store's own, so a value the store would refuse cannot be typed in the first place, and its elevation field uses whatever unit the launch site card is showing rather than always meters.
- **3MF export, for the whole rocket at once.** Menu → **Export → 3D print (.3mf)** writes every printable part of the design in one go, and 3MF joins STL / OBJ / GLB on each part's own ⬇ button. It is the format worth having: STL is naked triangles - no name, no color, no declared unit, one object per file - so a rocket exported part by part arrived in the slicer as a pile of anonymous solids you had to re-identify by eye. A 3MF carries all four, so the slicer's object list reads *Nose cone*, *Body tube*, *Centering ring*. The dialog lists what the design can ACTUALLY print, all ticked, and leaves out what has no solid body at all rather than offering a parachute or a mass component a tick box that does nothing. Two choices beyond which parts: one file of named objects or a zip of one file per part, and whether each part is dropped onto the build plate rather than left where it sat in the rocket. Orientation is deliberately NOT changed - the rocket's axis runs along X, so bodies arrive lying down, and standing them up would be right for every tube and wrong for every fin and ring, besides making the 3MF differ from the STL of the same part. A part whose geometry fails the manifold check is left out and NAMED, because a fin silently missing from the file is a fin discovered missing at the printer.
- **RockSim `.rkt` designs open and save.** Menu → **Import → RockSim** reads a RockSim design, and **Export → RockSim** writes one, so a rocket moves both ways between this app and RockSim the way it already did with OpenRocket. Bodies, transitions, inner tubes and motor mounts, centering rings, bulkheads, engine blocks and couplers, trapezoidal / elliptical / freeform fin sets with their cant, rotation and through-the-wall tabs, tube fins, launch lugs, parachutes and streamers, mass objects and shock cords, external pods, and up to three stages - with their dimensions, materials, finishes, placement and measured mass and CG. The reader works off the file's BYTES rather than its name, so a `.rkt` picked in the OpenRocket dialog still opens, and one code path loads both formats. Written as a TypeScript port of OpenRocket's `file/rocksim/` package rather than an extraction of it: that package is SAX-based and drags in the desktop's document, appearance and warning machinery, while the schema it encodes is small enough to read straight out of `RockSimCommonConstants.java`, which keeps both directions plain DOM and unit-testable beside the `.ork` pair. Neither format is a superset of the other and both directions say so rather than dropping things quietly - RockSim's ring tails are named in the import notes, its detachable pods come in as fixed, its subassemblies are merged, and on the way out the app tells you that a rail button or a parallel stage had no RockSim element to be written into. What never transfers either way is the **motors and the launch conditions**: RockSim keeps those with its simulations, which are a different object from the design, so an imported rocket arrives with no motor loaded and the import says so instead of seating a default. RockSim measures in millimeters and grams and states every circular dimension as a diameter, so the three conversions are tested from a fixture written element-for-element from RockSim's own schema rather than only round-tripped through our own writer - a reader and writer that share a wrong factor round-trip perfectly.
- **OpenRocket's example rockets, built in.** The sixteen designs desktop OpenRocket opens from *File → Open Example* now ship with the app, under **menu → Import → Examples** (and as the second tab of **Open…**, beside your own rockets, since a first run has nothing in the other one). They are the best starter designs that exist for this app: real, varied, authored by the people who wrote the physics, and between them they cover most of what it can do - motor clusters, pods and winglets, tube fins, parallel and serial staging, dual deployment, a payload section that separates and comes down on its own chute, two 3D-printable parts. Each entry carries the author's own note about the design, because a list of sixteen bare filenames does not tell anyone which one to open. Opening one is an import, not a template: you get your own unsaved copy, so an example can be taken apart freely and opening it again gives you a fresh one. They are pulled from the SAME OpenRocket commit the engine is extracted from, so an example can never demonstrate something the bundled kernel does not have, and each file's stored flight data is stripped on the way in - 90% of the bytes, 2.9 MB of the 3.3 MB across the set, and dead weight here because the app runs its own simulations and never reads it. At ~330 kB the whole set is precached like the rest of the app, so an example opens on a first offline load rather than only if you happened to be online when you went looking. Every one of them is imported and built through the real kernel in the test suite, with its motors resolved against the catalog: an example that imports but cannot fly is a worse example than no example.
- **A Safety page, and a "Before you fly" card on every run.** The app now says plainly what its numbers are worth. Above the results tiles sits a card that names what the model never had - fin flutter, structural loads, parachute inflation and opening shock, how your motor performs on the day - and says that no number on the screen can warn you about any of it. It leads the numbers rather than following them, because what a reading is worth is a thing to know before reading it. Beside that, the two things to actually do: weigh and balance the rocket you built, enter those as overrides and re-read the margin and the rail-exit speed; and fly under your safety code, inside your field and its waiver, where the RSO's call outranks anything on screen. It carries the same amber and the same ⚠ a flight warning does, because it is one. The card links to a new **Safety** page in the documentation (also reachable from menu → **Safety**), which covers what a simulation result is and is not, what the physics does compute, an explicit list of what it does not, what to verify on the bench before trusting a stability margin, the two NAR / Tripoli limits the app enforces and refuses to fly outside, and what remains the flyer's responsibility - airspace, motor certification and storage, permission, the range and the RSO.
- **The workbench tabs moved into the top bar, and the panes are yours to size.** Design / Simulations / Results were a strip of their own under the header, spending a full row of the window on two or three words while the header beside them ran empty from the badges to the far-right controls. They now sit in that gap, which took the top of the app from 92px to 55px. Below them, the divider between the component tree and the drawing, and the one between the drawing and the right-hand column, are draggable: pull them, or focus one and use the arrow keys (Shift for bigger steps, Home and End for the extremes), or double-click to put it back. Both widths are remembered. The three right-hand columns - the part editor, the simulation editor and the run's numbers - share ONE width, because they were a matching 380px on purpose and columns of different widths read as an accident rather than as a choice. A width stored on a wide monitor cannot crush the drawing when the same browser opens on a laptop; each divider keeps room for everything else on screen.
- **The drawing can take the whole window.** The **⤢** button at the right end of the rocket view's toolbar puts both side columns and the static statistics strip away, which roughly doubles the room the drawing has. An airframe is 15-25x longer than it is wide, so horizontal space is what it runs out of first, long before vertical. **Escape** brings the panels back. The Simulations tab deliberately ignores it: the button lives in the rocket view's toolbar, which is not on that tab, so honoring it there would hide the simulation editor with no control left anywhere to bring it back.
- **The component tree fits more rocket.** The left column is wider (360px by default, and now adjustable) and the padding in front of each row is gone: a stage's row started 37px from the pane's edge through four separate gutters stacked on the same side, none of them earning it, and every level of nesting inherited the lot. It starts at 19px now, and each row gained 20px of width for the part's name. The design actions - **+ Stage**, **+ Add** and **Scale** - share one row above the list, where they were split across two places that read as unrelated groups.
- **Show or hide the import notes, and have it remembered.** What a `.ork` could not bring across can be folded away on the loaded-design card. It was already collapsible, but the state was thrown away every time the card unmounted - on every tab change, every Close and every reload - so the notes sprang back open on the next import and the fold had to be repeated forever. It is a preference now, app-wide rather than per design: it is a reading habit, and a per-design flag would mean re-collapsing the notes on every file you open.
- **Every simulation now records every series the engine computes, and the CSV export asks what to write.** Runs used to keep 17 of the kernel's 69 series, so the app could neither plot nor export the rest - it had never asked for them, though the flight was simulated identically either way. Measured on a C6 flight at a 0.01 s step: 509 ms and 427 KB before, 596 ms and 1537 KB after. 87 ms is not worth two thirds of the flight data. The **CSV** button now opens an export dialog rather than downloading immediately: tick the variables (the list is what the run actually recorded, with units), choose the field separator, decimal places and exponential notation, choose which comments to include and what character marks them, and pick the stage on a staged flight. The choices are remembered between exports. The old button wrote twelve fixed columns, comma separated, six significant digits, with the event comments always on - one opinion about a file somebody else has to read.
- **A ground-track view, and horizontal position in the flight CSV.** The flight seen from directly above: where the rocket went over the ground, north up, the pad at the center, with range rings carrying the measurement and a ring at each landing point. Underneath, every track says how far and on what bearing - the two numbers you walk on. It draws the same traces the flight charts do, so a staged flight shows each stage's own descent, a spent booster usually landing well away from the sustainer. The app could already answer this outside itself through the KML and GPX export; now it answers without leaving. The flight CSV gained **East** and **North** columns beside altitude, which it had never carried, so a landing point can be got out of the file at all.
- **Running opens the Results tab, and the title says what you ran.** Every run lands on Results now, one simulation or a batch, because running is asking to see the answer and clicking over afterwards was a step with nothing behind it. Run one simulation and the pane's title is simply its name. Run several at once and the title becomes a dropdown listing exactly those, so you can switch between them; the choice governs all three results views - the flight charts, the ground track and the 3D path - so switching shows the same flight whichever way you are looking at it. It is deliberately not the Simulations tab's tick boxes: those say what Run should fly, which is a different question from what you are reading. Opening a row's results from the table points the views at that row too.
- **The flight-chart panels you pick are remembered.** Which measures are open was component state, reset every time the Results tab was opened, so anyone who works with thrust or mass re-ticked them on every visit. It is a preference now, and a panel named by a preference this build does not have is dropped rather than left blank.
- **Imported inner structure keeps its size, and no longer blocks the run.** A centering ring, bulkhead, tube coupler or engine block takes its outer radius from whatever it sits in, and a centering ring takes its inner radius from the motor mount through it; OpenRocket writes those as `auto` rather than a number. The importer read them as numbers, so `auto` fell through to nothing and every ring in an imported file arrived with no radius at all — which the design check then called a zero dimension, refusing to fly the whole rocket with *"a required dimension is zero: Centering Ring"*. The export half was wrong in the opposite direction: it wrote `auto` for every ring whatever the design said, so a ring you had sized by hand came back the width of its body tube. Both now say what is actually there, blank meaning automatic exactly as the file does, and a derived radius is no longer marked as a field you have to fill.
- **Cancel a run, and run everything that is out of date.** The Run button becomes **Cancel run** while a batch is in flight, rather than going dead and saying "Simulating…" for up to the full timeout; a run still waiting for a worker is dropped and one already going costs its worker, which is the only way to interrupt the engine mid-flight. Canceling is not a failure: rows that already landed keep their results, the rest go back to what they were, and nothing turns red. Beside it, **Run outdated (n)** flies every simulation whose numbers are missing or stale, counting them in the label. It ignores the tick boxes on purpose, since bringing a workspace up to date is a different question from flying a chosen few, and it leaves you where you were standing rather than jumping to the Results tab.
- **Nothing locks while a simulation runs.** The component tree, the property editor and the 2D/3D views were covered by an overlay for the duration of a run, so that an edit could not leave a result describing a rocket that was no longer on screen. That case is handled rather than prevented: a run records the design it flew and discards any answer that comes back against a different one, so editing during a run costs the run instead of freezing the app for it. It matters more now that a batch of simulations can be several seconds long. The simulation editor follows the same rule: a run remembers the motor, ignition, launch conditions and options it was flown with, and an answer that comes back against any of them having changed is dropped rather than installed over your edit, which would have left the row claiming to be current with numbers from the conditions you just replaced.
- **Simulations run in parallel.** Running several at once now spreads them across a pool of engine workers (one per core less one, capped at four) instead of flying them one after another, so a batch of twelve is bounded by the pool rather than by twelve flights end to end. Rows say which state they are in: **Queued** while waiting for a worker, **Running** once one picks it up. A simulation that hangs is killed on its own and marks only its own row, where before a single stuck flight rejected every run in flight with it, and the timeout starts when a run reaches a worker rather than when it was submitted, so a healthy batch is never timed out for being busy. Idle workers are released after a minute, since each one holds a full engine.
- **Dual deployment, and the recovery warnings that depend on it.** A parachute or streamer now carries a **Drogue (dual deployment)** tick, saved to the `.ork` as OpenRocket's own `<isdrogue>`. It decides how the flight engine judges every deployment: a stage with a drogue warns on the **main** coming out too fast or too slow, and on the **drogue** too slow at apogee to inflate, while a stage without one is judged against the single deploy-speed threshold as before. None of that could happen until now. Nothing set the flag, so every rocket the app built looked like single deployment to the engine and three of the four thresholds were unreachable however they were set - including two that already had settings and tinted tiles. The drogue threshold gained a setting of its own (global, with a per-simulation override like the rest), and the engine check behind it, which OpenRocket ships commented out, is enabled in our build.
- **Parts inside a mass component.** A mass component can hold inner structure of its own, so an altimeter bay or a payload sled is modeled as the sled plus the rings, bulkheads, hardware and recovery gear nested in it. The extracted engine had been carrying a copy of OpenRocket's `MassComponent` from before upstream allowed this, which meant a `.ork` the desktop saves happily failed to open with *"Bulkhead not currently compatible with MassComponent"*. The stale copy is gone and the editor now offers the same children the engine accepts.
- **A name for a flight-path export.** Several exports opened in one Google Earth session were indistinguishable: every two-stage design contributes a folder called *Sustainer* and a track called *Sustainer flight path*, and two designs can each own a *Simulation 1* — nothing in the tree or on the map said which flight was which. The export dialog gained a **Mission** box whose text is prefixed to the document name, every folder and every track, so *Sod Blaster* gives *Sod Blaster Sustainer flight path*; a name that already leads with the mission is left alone rather than stuttering. **Prefix the waypoint names too** extends it to the markers and is off by default, because a near-vertical flight packs every marker into a few screen pixels — the labels already overlap enough to have a switch of their own, and longer ones only make that worse. The mission name is deliberately not remembered between exports (a stale one silently mislabels the next file, which is worse than retyping it); the marker checkbox is, because that one is a working habit rather than a property of one flight.
- **A color per stage, in the flight-path export.** **Stage colors…** offers one swatch per stage, starting from the same palette the flight charts use, so a stage keeps its identity between the graph and the map. One color drives all three of that stage's marks: the flight-path line at full strength, the ground track darkened, and the waypoint pins. Darkened rather than merely made translucent, because seen from straight down a ground track sits directly beneath its flight path and two lines of the same brightness read as one — dark means on the ground, bright means airborne, at any zoom. Only a color you actually change is stored, so the palette can move later without stranding a saved value, and **Cancel** leaves the previous choice untouched.
- **Flight conditions for the Aero sweep.** The panel gained **AoA**, **Wind dir** and **Roll rate** controls, which the whole sweep is now flown at — every sweep ran at zero for all three before. Roll rate is what makes the roll-damping column mean anything, since damping opposes an existing roll. A **Worst** button sets the wind direction to the angle where the rocket's CP sits furthest forward — where it is least stable — answering "is this stable in any orientation". On a symmetric three-fin rocket the CP does not vary with that angle and Worst reports 0; on a two-fin design the CP swings from 18.8 cm to 48.1 cm across it.
- **Roll dynamics in Aero.** Every fin set's **roll forcing** and **roll damping** coefficients, from *Component Analysis ▸ Roll dynamics*. Both read zero on a rocket that is neither canted nor rolling; giving a fin set a cant angle brings the forcing up, which is the one place in the app that confirms a cant is doing what you intended.
- **Per-component stability table in Aero.** Each part's **mass** (per instance, all instances and the set's CG), **CNα** and its own **CP**, tabulated beside the drag table and following the same crosshair — the figures desktop OpenRocket shows in *Component Analysis ▸ Stability*. It answers why the CP sits where it does: on the default rocket the fin set carries 33.7 of the 35.7 total CNα, which is what holds the CP aft. Parts with no normal force are left out rather than listed as zeros.
- **A Charts / Per component switch in Aero.** The panel shows either the three curves or the component tables, rather than stacking all of them in one scroll. The tables report at a single Mach: the hover crosshair picks it on the Charts pane, a slider on the other, and the two share one value so switching lands on the point you were just looking at.
- **Shaded cells in the Aero tables.** Drag and CNα cells carry a tint in proportion to their value, so the parts that cost you most stand out without reading every figure, with the scale shown beneath. The style is switched from the buttons beside the legend, or from **Settings ▸ Colors** — one preference, either place: *By magnitude* (the default) is one color that strengthens with the value, scaled against the largest figure in the table; *By heat* reproduces the desktop's green-to-red exactly — its formula, its fixed 0–1.5 Cd scale, dark text on light cells.
- **Per-component drag table in Aero.** Each part's drag at one Mach, split into pressure / base / friction — the figures desktop OpenRocket shows in *Component Analysis ▸ Drag characteristics*, which answers "what is costing me drag" in a way the stacked chart cannot. Rather than a Mach spinner it follows the charts' hover crosshair, so scrubbing a curve updates the split beneath it, and rows are ordered worst-first. A part that exists more than once also shows its **per-instance** drag and how many there are.
- **Flight-path exports for drift casting.** The KML export now sets the **track**'s altitude and the **waypoints**' altitude separately, and both offer **Clamped to the ground** — which lays them flat on the terrain, for when the question is what the rocket drifts *over* rather than how high it went. A common pairing is the track at sea level with the pins clamped: the flight suspended in the air where it belongs, its labels readable against the ground they sit over. **Draw shadow down to the ground** adds KML's `<extrude>` curtain under the track and a plumb line under each pin, and a clamped track is tessellated so it drapes over hills instead of cutting through them. Three presets — **Drift cast**, **Flight path**, **Landing plots** — set the waypoints, the lines and the placement together in one click, without hiding anything: the dialog always shows what the file will contain.
- **A Sketch tab on phones, drawn in landscape.** The rocket drawing — 2D, 3D, Aero and the flight views — has its own tab beside Rocket and Simulate, instead of sharing the screen with the stats strip and being squeezed into a couple of hundred pixels. The 2D views are landscape drawings (a hobby airframe is 15–25× longer than it is wide), so on a phone held upright they are now turned a quarter turn — nose at the top, the rocket's length running down the screen, rulers and markers and all — and turned back once the phone is sideways and already the right shape. The view switch and the 2D presets turn with the drawing, so they sit along the screen's long edge at the top of the sheet they control. The **3D** model and the **Aero** charts turn the same way — a Mach sweep is a wide drawing too. The Rocket tab keeps the design banner and the static stats. Nothing changes on a desktop, where all of it still shows at once.
- **Flight-path exports place the track properly.** The KML/GPX export dialog gained a **Placement** section: what altitudes are measured from (automatic, the ground, or sea level — automatic picks sea level only when the launch site has a real altitude, so a ground-relative track is never buried under the terrain), whether waypoint names are drawn, and whether pins carry their stage's color. Staged flights get a track color per stage and waypoints named for the stage that flew them (“Booster Apogee”), and a separated stage's track now starts at separation rather than repeating the ascent it flew bolted to the sustainer — so a spent booster reports its own peak speed. A design whose launch position was never filled in — both coordinates still zero — is exported from the Kennedy Space Center rather than dropped on Null Island, and coordinates are projected with WGS84 degree lengths. The flight-path model matches desktop OpenRocket's field for field, so Mustache templates written for either app render correctly in the other.
- **Choose your units.** Settings ▸ **Units** picks the unit for each kind of quantity — component and motor dimensions, altitude, mass, velocity, wind speed, acceleration, angle, bulk / fabric / cord density, temperature, pressure, thrust and impulse — with **Metric** and **Imperial** presets for setting them all at once. Every field, readout, chart, ruler and stat follows. The unit shown beside a value is itself a picker for **that one field**: set a nose cone's length to inches and its thickness, the component tree, the rulers and the stats strip all stay as they were. Per-field choices stick across reloads and never rewrite your defaults; a field you leave alone keeps following them. A field showing a non-default unit is tinted amber — and says so to a screen reader — so one inch measurement among centimeters reads as deliberate rather than as a glitch. The Units tab can reset every per-field choice at once, and the Metric / Imperial buttons clear them too. The PDF report and both CSV exports are written in your units and name the unit they used — and the report dialog can pin its PDF and CSV to **Metric** or **Imperial** instead, for when the document is for someone else. Designs are unaffected — the engine and every saved `.ork` stay SI, so switching units never edits your rocket.
- **Keep several rockets.** Designs are now a library rather than one working file: **Open…** lists your saved rockets to switch between, **Save As…** branches a copy, and **New** starts a fresh one without disturbing the last. Everything still autosaves as you edit. Your existing design is carried into the library automatically the first time you open the app.
- **Import / Export replace Open / Save for files.** Menu → **Open** and **Save** now mean the in-app library; `.ork` files move to and from your disk through **Import ▸ OpenRocket** and **Export ▸ OpenRocket**, alongside the other export formats.
- **Exports work in the installed app on iPhone and iPad.** A download started from an installed PWA silently did nothing on iOS; exports there now go through the system share sheet ("Save to Files"). Every export — `.ork`, RASAero, CSV, 3D meshes, cut sheets, schematics — shares one save path.
- **Works offline, and installs.** The app now caches itself, the physics engine, and both reference catalogs, so it opens and runs a full simulation with no connection — useful at a launch site with no signal. Your browser will also offer to install it (home screen on mobile, its own window on desktop). When a new version is deployed, a prompt offers to reload rather than reloading under you mid-design.
- **Loading screens say what they are doing.** The startup splash reports the engine download with real progress ("Downloading engine… 1.4 / 2.3 MB") and names the compile step, and the motor and component pickers show the same for their catalog downloads — instead of a single static "Loading…" through a multi-megabyte transfer. A failed catalog load now reports the error and offers a retry, where it previously left an empty list with no explanation.

- **Multi-stage flight charts.** The Flight tab now plots each stage of a staged flight as its own colored line, with a stage selector to choose which to overlay. A spent booster's separate climb, descent, and landing are drawn from its own flight branch; the time axis spans every stage, and event markers and the hover readout cover all shown stages. Single-stage flights are unchanged.

### Changed
- **The adhesives are offered where they belong and nowhere else.** Adding thirteen of them put thirteen rows of glue under every body tube, centering ring and bulkhead, none of which is made of it. A structural part's list drops the **Adhesives** group, and a fin fillet's list has only adhesives in it. Only that one group is filtered, and deliberately: every other bulk material in the table is something a part can legitimately be made of, people build fins from aluminum and nose cones from printed PLA, and guessing which suit which component would block real designs to save a little scrolling — OpenRocket does not do it either. Filtering the fillet rather than merely ordering it costs nobody a bead of something unusual, because a thickened mix or a putty is a custom material and the add form asks which group it goes in. Whatever a part ALREADY uses stays in its list either way: a `.ork` naming an epoxy on a body tube would otherwise leave the select with no option for the value it holds, reading as "no material" on a part that has one.
- **A custom material joins a real group instead of a `Custom` one, and a custom material named after a built-in replaces it.** The picker filed everything you defined under a group of its own, which put it at the top of the list and away from the material it is usually a variant of: a plywood you measured belongs beside the plywood, not above the plastics. It now sits in the group you pick when you add it (the groups that material type already uses, plus **Other**), still marked with its ★, and the provenance is carried by that star rather than by where it sits. Name one after a built-in and it now REPLACES that entry, in place, at your density. It used to appear as well, so the list held two materials called `Blue tube` in two different groups and which one a design picked up depended on which the lookup reached first. Materials already saved under the old `Custom` group are re-homed on the way out of the store rather than stranded in a group nothing else is in.
- **Fixed: none of the runtime catalogs loaded with the network off.** The motor, component and material lists are files under `public/data` fetched at run time, and they are precached by the service worker, so "offline at first open" was supposed to cover them the way it covers the app shell and the documentation. It did not, and had not for as long as the cache-buster has existed. Each catalog is requested with `?v=<content hash>` so a CDN cannot serve a stale copy; `manifest.json` is itself precached, so with no signal the app still read a hash and still asked for `data/motors.generated.json?v=429fee4cf0b3` - and Workbox keys its precache on the bare path, stripping only `utm_*` and `fbclid` from a URL before matching. Every one of those requests was a miss, fell through each runtime rule and died at the network. No motors, no components, no materials, on precisely the device standing at a launch site. The worker now ignores that parameter when matching the precache, which costs nothing: the in-build copy changes only when the app is rebuilt, and a rebuild is what actually busts that cache, while the separately deployed catalog host the hash exists for is a different origin served by its own rule. `npm run e2e:offline-data` checks it against a real build and a real worker, and runs in CI beside the update-flow check - it fails on every catalog if the fix is removed. Nothing else could have caught it: the Playwright suite runs against the dev server, which registers no worker at all.
- **The material table is data now, not code, and it ships where the other data ships.** `src/data/materials.ts` was 94 hand-typed entries in a TypeScript array, which is how it came to be missing twenty-two of upstream's line materials. There is no longer a table in `src/` at all: `public/data/materials.generated.json` is a runtime file fetched on demand, exactly like the motor and component catalogs, cache-busted by the same `manifest.json` and published to the same `data` branch. A new `npm run sync:materials` writes it from two inputs, OpenRocket's own `Databases.java` and the hand-maintained `scripts/data/materials.app.json` that carries the adhesives and the corrected elastic cords; every row keeps a `kind` saying which it came from. Regenerating is idempotent, and the script refuses to write at all if its parser reads fewer materials than the file has `newMaterial` calls, or if one of ours would take an upstream material's name and silently shadow it. The citations that were comments are fields now, `source` and `note` on every entry, and they stay in the maintained file rather than being shipped to a browser that has no use for them. `extract --check` reads the generated JSON rather than parsing TypeScript with a regex, which is both sturdier and how the old blind spot became impossible. Because the list is a download it can now fail to arrive, so the picker says so and keeps naming the material the part already has, instead of showing an empty list that reads as "this part has no material". The About dialog's contributor list moved the same way, for the same reason: it was a generated JSON file sitting in the source tree because that is where it was first put.
- **The documentation now covers two features it had never mentioned, and the Features page lists four more it was missing.** An audit against the code rather than against the docs found them. **Playing the flight back** was undocumented everywhere: the 3D path has a T-minus countdown, play and pause, a scrubbable timeline and speeds from 0.25x to 4x, and Settings has a **Playback** tab holding the speed a run starts at - none of it appeared on any page, so a control and a setting that both ship were invisible. **Freeform fins** were the other: the property panel has had a point-by-point outline editor (drag the amber points, tap a blue midpoint to insert one, select a point to delete it or type exact coordinates, X along the body and Y above it) and the user guide never said so, while the ZenRockets comparison listed it as parity. Both now have sections of their own. The **Features** page also gained the ground-track view, the Motor Dashboard, mass / CG / drag overrides and running several simulations at once, each of which was documented on its own page but missing from the one page that claims to be the list, and it no longer carries the **Undo / redo** bullet twice.
- **The app and the docs name the OpenRocket commit they are built from.** "The same physics core" was as specific as it got: the documentation's Overview page never named a version at all and the README said "a post-24.12 development build", so a reader comparing their numbers against desktop OpenRocket's, or asking whether a feature from some release is in here, had nowhere to look. Overview now states the pinned commit and its date in both languages, the About dialog shows the same pair with a link to the commit itself, and the README points at the pin rather than describing it. None of it is typed into any of those places: `engine-java/extract/UPSTREAM` is the one file that names the ref, and the app's Vite config and the documentation's Docusaurus config each read it at build time, so one bump moves all three together. The commit's date is a field in that file now instead of a sentence in its header, and the `reproducible` job checks it against the commit it already checks out, so a bump that moves the ref and forgets the date fails there rather than shipping a confidently wrong date to every reader.
- **Engine repinned to OpenRocket `98f05af97` (2026-09-21), and the example set is sixteen.** Five commits on from `6deae5079`, and NOTHING under `core/src/main/java`: two swing spinner step sizes (upstream PR #3332) and the deletion of the "Base drag hack (short-wide)" example design (PR #3331). `swing` has no entries in `extract/manifest.txt`, so not one extracted file moved - `extract --check` reports zero differences against the new ref, no patch drifted, `DIVERGENCE.txt` is unchanged and parity cannot have moved. The example is the only part that reaches here: `sync-examples.mjs` reads upstream's examples directory directly, so the bundled set drops from seventeen designs to sixteen and the base-drag hack goes with it. That is upstream's call and the right one - the hack is a modeling trick people used because OpenRocket did not compute base drag properly, and the work that made it unnecessary is already in the kernel we ship. While counting the set again, the strip figures in the docs were re-measured rather than copied: 2.9 MB of the 3.3 MB upstream, not the "96%, 3.5 MB of 3.6 MB" that was there, which did not reconcile with the ~340 kB result printed beside it.
- **File > Save is gone, and the header says when your rocket was last saved.** The item never stood between anyone and their work: editing autosaves on a half-second debounce, leaving the page writes a synchronous journal the next load folds back in, and the only two things Save itself did were flush a write that was already coming and send a never-named design to Save As. What it really offered was the reassurance that saving was happening at all, and it charged a click and a menu trip for it. The top bar now carries that plainly - **Saved just now**, aging to "Saved 6 minutes ago" on a design nobody is touching, with the exact time on hover. It is set from the write's own success path rather than from anything that merely asked for one, so a refused save leaves the last honest time standing instead of claiming a save that did not happen, and it says nothing at all before the first write or while the storage banner is up, since that banner says the opposite and outlives any single save. **Save As…** stays, because naming a design is a real action with a real choice in it.

### Fixed
- **Motors and tubes placed off the centerline now count toward roll inertia.** A mass sitting away from the roll axis adds its mass times the distance squared to the rocket's roll inertia. The OpenRocket kernel gave that term to pods and to the motors of a multi-motor cluster, but not to a single inner tube moved off the axis, the usual way to build a split cluster, nor to the motor inside it, and a clustered tube lost the spread of its copies about their center. Two motors 15 mm off the axis therefore had 4.9% less roll inertia drawn as two split tubes than drawn as one `double` cluster, though the mass is in the same places. Both now read the same, to the last digit. This is the first deliberate physics divergence from desktop OpenRocket in the engine, since the defect is in desktop OpenRocket too; it is a two-part kernel patch recorded in `engine-java/patches/LEDGER.md`, found by the mmrocket-sim project. What moves is roll inertia alone: the Rotational inertia flight data column and how quickly a rocket with canted fins spins up. The spin rate it settles at, the per-fin-set roll forcing and damping, the CG, CP, stability margin and the trajectory do not move. Parity against the JVM grows to 348 reference values with six new ones for this, and every existing physics value is unchanged.
- **A multi-level wind profile is reproducible now, like every other run.** `randomSeed` reached the turbulence of a single-level wind and not of a layered one. Upstream's four-argument `addWindLevel` builds each level's sub-model with the no-arg `PinkNoiseWindModel` constructor, which seeds itself from `new Random().nextInt()`, and nothing in the bridge put the run's seed back: `setRandomSeed` stores an int on `SimulationConditions` and never reaches the wind model, and the explicit seeding was in the single-level branch on the other side of the `if`. So a profile with any per-level stddev flew a different gust pattern every time. Five runs of one design at seed 7 came back 12.26 m, 232.44 m, 8.58 m, 14.86 m and 204.35 m of apogee, where the single-level control repeated to the last digit.

  This is what the wind sweep compares. A sweep changes one parameter across runs and reads the difference, and with unseeded turbulence the difference it read was mostly noise, on the feature whose whole purpose is layered wind. The profile editor ships and makes per-level stddev editable, so it was reachable by hand as well.

  The fix is one call, `MultiLevelPinkNoiseWindModel.setSeed`, made after the levels are in place. It is upstream's own method, and upstream's own `SimulationOptions.toSimulationConditions` makes exactly this call; we hand-build the simulation conditions rather than going through `SimulationOptions`, so it was ours to make and we were not making it. No kernel patch, and no seeding scheme of our own: the per-level seeds are upstream's, derived by altitude rank, so they do not depend on the order the levels arrived in. A profile with no turbulence is unaffected, and parity against the JVM is unchanged at 342 reference values on both targets.

- **A wind profile cannot be built with two levels at one altitude, and a level with no altitude is not flown at zero.** The kernel keys its wind levels on altitude: `MultiLevelPinkNoiseWindModel` binary-searches its sorted list to insert one and throws on a collision. So the profile editor let you type a second level at 0 m and the run came back as `EngineCallError: engine simulate failed: Wind level already exists for altitude: 0.0` - the kernel naming its own internals, after the design was built, for something the editor had invited. A row that repeats an earlier row's altitude is now flagged in place, says why under the table, and the Run button refuses the simulation by name before it starts. A new level also lands 300 m above the HIGHEST level rather than above the last row, which on an unsorted 0/600/300 profile used to land on 600 and collide the moment it was added.

  The other half was an altitude read as a quantity with a harmless zero. It is not one - it is the level's identity - and both readers defaulted it: the engine bridge through `JsonLite.dbl(lvl, "altitude", 0)`, the `.ork` reader through `finiteNum(...) ?? 0`. A file or a call that omitted or garbled an altitude therefore flew a layer at the pad, where it either displaced the real surface wind or collided with it and failed every run. The bridge now refuses such a level and names which one it was; the `.ork` reader drops it, and drops a file's own repeated altitude the same way, keeping the first. Stored launch defaults go through the same rule. Emptying an altitude box writes nothing at all, rather than moving the layer to 0 m on the way to retyping it - the columns beside it still read a blank as 0, because a still layer is a real reading.

- **A unit conversion can no longer store Infinity.** `NumberInput` refuses a non-finite entry, so Infinity could not be typed; but a field's box holds display units and the node holds SI, and the conversion between them overflows on its own wherever the display unit is the larger: 1e306 g/cm3 is 1e309 kg/m3, and 1e306 km is 1e309 m. `DimensionFields` wrote `fu.fromUi(v)` straight through, so that went into the node, was persisted, and was exported to the `.ork` as `Infinity` - which the reader takes back as 0, leaving a field showing a dimension the geometry never had. One guard now sits on the way out of every numeric row, dropping the whole patch rather than one key, since a derived row writes two linked numbers and half of that pair is worse than neither. The wind profile editor has the same guard across its four columns.

- **A lazy view that fails to load no longer takes the app down with it.** There was no error boundary anywhere. Rocket3D, FlightPath3D, ComponentPicker and SavePartButton are each an `import()` fetched on first use, and a failed chunk fetch rejects, Suspense re-throws the rejection during render, and with nothing above to catch it React unmounts the entire tree: a blank window, no view switch, no menu, nothing left to click. A stale Pages deploy produces exactly that - the chunk name the loaded build asks for is gone, the server answers with its index.html, and the browser reports the HTML body as a bad module (Safari: `'text/html' is not a valid JavaScript MIME type`). Each of the four now sits behind a boundary wrapped around its Suspense, so the failure is contained where it happened and everything beside it keeps working, and the fallback distinguishes a missing chunk from a bug inside the view. It offers Reload and nothing else, deliberately: React's `lazy` caches a rejected import, so a Retry button would remount without going back to the network - a control that does nothing - and a new deploy has new chunk names that only a fresh document knows.
- **Plural forms are checked against each locale's own grammar, not English's.** The locale test asserted that every file carries exactly English's key set, which is right for an ordinary string and wrong for a plural family: i18next picks the suffix with `Intl.PluralRules`, so which forms a file needs is a fact about that language. English and German select between two (`one`, `other`); Spanish, French and Portuguese three (`many` as well); Japanese one; Russian and Polish four (`few` and `many` too). Held to English's two, a Japanese file has to carry a `_one` nothing will ever select, and a Russian file cannot carry the `_few` it does not work without, so those languages could not be added at all rather than merely being untranslated. Each locale is now held to the categories its own rules declare, which is both halves of that at once.

  Not a hypothetical, either: a declared category the file omits does not degrade to that file's `_other`, it falls through to ENGLISH, so `t('sweep.flights', { count: 3 })` would have rendered "3 flights" inside an otherwise Russian UI. The new rule immediately found `_many` missing from all four of the Spanish, French and Portuguese files, across all eight plural families. Unreachable in practice, because `many` in those languages starts around a million and every counter here is a handful of parts or simulations, but it was a real hole and it is filled.

  Also one spelling for a family instead of two. `banner.notes` and `print.count` gave their singular as a bare key beside a `notes_other` / `count_other`, which worked only because i18next falls back to the bare key when `_one` is absent, and which hid the family from anything counting forms. Both are now `_one` like the other six, and the test rejects a bare base key outright.

- **A material picker that did nothing, on the one part that had one.** `hasMaterial` claimed a camera shroud (`fairing`) took a material, so the panel offered the picker. The kernel builds a shroud as a `MassComponent` with its mass set outright, so the choice changed nothing that flies, and `writeFairing` has no `<material>` element to put one in, so it was dropped on the next save. Picking a material did nothing and then forgot itself. The shroud no longer offers one. Everything else that does keeps it: a new `ork/materialRoundTrip.test.ts` writes a material this app has and OpenRocket does not onto every type `hasMaterial` admits, plus a fin's fillet material and a recovery device's canopy and line materials, round-trips each through a `.ork`, and checks the name and density come back — and that the name really is in the file's `<material>` element rather than in some private tag the desktop cannot read.
- **The material check could not see a material with a quote in its name.** It parsed a name as `"([^"]*)"`, which stopped at the escaped quote in upstream's `Styrofoam \"Blue foam\" (XPS)` and at the double-quoted spelling the `.ts` file uses for a name containing an apostrophe. The entry was therefore skipped on BOTH sides, the two lists balanced, and the check reported clean — a parser that drops a row is worse than no parser, because it is a check that passes. Both patterns now allow escapes, and each side's parsed count is compared against the number of entries actually present, so a name the parser cannot read fails the check instead of disappearing from it. The app's own materials are now marked off by an `END OF UPSTREAM` line rather than by the name of the list that happens to follow.
- **`extract --check` now holds the material table to upstream too.** It was the one port in the repo that no Java file mirrored, and so the one nothing compared: upstream loads its materials from a resource at startup, so the extraction replaces `Databases.java` with a shim that synthesizes by name the handful the carved kernel asks for, and the rest of the list lived only on the TypeScript side. The check now reads upstream's own `Databases.java` out of the pinned source and compares it entry by entry, failing on a missing material, an extra one or a changed density, and naming each. The app's adhesives are the one allowed exception and sit in their own exported list below the upstream block. This is what found the twenty-two missing line materials, and it is why a future upstream bump that adds a material cannot pass quietly.
- **The Rogers Kbf note had "conservative" backwards.** The opt-in body-in-presence-of-fins carryover (RASAero feature #3) moves CP slightly aft, and three places in this repo called that "a more conservative static margin". It is the opposite: margin is `(xCP - xCG)/d` with x measured aft, so an aft CP RAISES the margin the app displays. The term is the closer answer for the geometries it was validated against, not automatically the safer one - on an erroneously aft prediction it overstates how much margin the rocket actually has, which is the direction a reader must not be misled in. Corrected in the `FinSetCalc` patch, the `setRogersModifiedBarrowman` javadoc and `docs/rasaero/README.md`. Comment-only in every case: the extracted tree is still exactly upstream plus patches, `DIVERGENCE.txt` is re-blessed at 733 lines for `FinSetCalc` (was 727, the six added comment lines), and the compiled engine is untouched because comments do not survive compilation. The correction is taken from mmrocket-sim, whose RASAero extensions these are, and it credits Ken Karbon, Apogee Peak of Flight 687. Nothing user-facing said it - the flag has no UI and no wiki page - so this is a correction to what the next person reading the kernel would have believed.
- **File > Open filled up with copies of the same rocket.** Two separate causes, both of which made a new library entry where one already existed. An import deliberately becomes its OWN saved design rather than an edit to whatever was on screen, but nothing looked at the NAME, so the ordinary loop of tweaking a rocket in OpenRocket and importing it again left a stack of rows all called the same thing, each a real design with its own id and nothing to tell them apart by. Importing a rocket whose name is already saved now asks: **Overwrite** it, or **Keep both** and name this one, with the next free "… (2)" suggested. Overwriting writes into the existing entry rather than beside it. The same question covers the bundled examples, since opening one is an import. Underneath that, any two saves that overlapped while the design was detached from the library each created an entry of their own: the autosave debounce is half a second and the first write to IndexedDB is the slowest the app makes, so a second keystroke inside it was enough, and tabbing away right after an import (which saves outside the debounce) hit it every time. All but the last of those entries was orphaned the moment it was written, because nothing was ever active in it. Overlapping saves now share one create. A create whose final pointer write is refused also rolls itself back instead of leaving its design indexed, which otherwise added an identical row every half-second for as long as storage kept saying no.
- **A recovery pin named `[Parachute.Parachute]` in the flight-path export.** The engine is OpenRocket's core through TeaVM, which carries no resource bundles, so every kernel string arrives as its lookup key in brackets - a deliberate protocol the app translates at the boundary. A recovery device the user never renamed has no name of its own, so the kernel falls back to its default name, which is itself a bundle lookup: the flight event's source reached the export as `[Parachute.Parachute]` and went straight into the KML placemark's name. The warnings panel already solved this one level up, so the export now shares that code rather than carrying a second answer, and a part is named the same way wherever you meet it. That shared code no longer just strips the brackets either: the kernel's name is mapped onto this app's own string for the same part, so it is TRANSLATED rather than left in English, and a recovery device follows the export's language box like every other word in the file. The mapping is transcribed from the kernel's `getComponentName()` overrides, with a test asserting every row still points at a string that exists, because nothing else would notice one being renamed out from under it. A kernel name this app has no part for degrades to a readable form rather than a bracketed one, and a device you DID name is untouched, because only the bracket form is a key. That distinction now also decides the PIN's name: an ejection pin is named for the EVENT, qualified by the device when you named it - "Drogue Ejection", "Main Ejection" - which tells the two apart on a dual-deployment flight while keeping the event vocabulary every other pin uses, and stacks with the stage into "Booster Drogue Ejection" on a staged flight. It reuses the qualifier the stage names already go through, so it inherits that guard against doubling a name. A device left on its default adds nothing the balloon's device line does not, so its pin is just the event. The event's own label is now **Ejection** rather than "Recovery deployment", in the dialog as well as on the map, so one thing has one name.
- **Switching the map layer moved your launch location.** The map's pan and click-to-place handlers sit on the box that also HOLDS the layer, zoom and recenter buttons, so a click on any of those bubbled through and was read as a click on the ground. Switching to the street layer relocated the site to whatever the button was covering - the top-left corner of the map - which showed up as the pin being in the right place on satellite and somewhere else on street. It was silent: nothing said the coordinates had changed, and the same went for the zoom and recenter buttons. Pointer events that start on a control are now ignored, and the drag capture is taken on the map box rather than on a tile, which used to drop mid-gesture as soon as a pan unmounted the tile under the cursor.
- **A launch location could save itself named after its own latitude.** The edit dialog focused and selected its name box from a `requestAnimationFrame`, which left a whole frame in which the dialog was on screen and focus had not arrived yet. Click into the latitude inside that frame and the callback yanked focus away mid-keystroke, so what you typed went into the NAME box instead and the location saved as "39.1234". It is a layout effect now, which runs before the browser paints, so there is no gap to land in. Caught as an intermittent end-to-end failure; a person would have blamed their own typing.
- **The street map layer 403'd, and should never have been pointed where it was.** It asked `tile.openstreetmap.org` for tiles. Those are donated, volunteer-funded machines, and OpenStreetMap's Tile Usage Policy reserves them for OpenStreetMap's own use and tells third-party applications to run their own or buy from a provider; they enforce it, so the layer simply refused to draw. The app also asked with `referrerPolicy="no-referrer"`, which strips the one header a provider has to see who is calling - the polite half of using someone else's tiles, and the signature they block on. The fix is not to comply our way into using someone's charity as a CDN: the street layer now comes from Esri's `World_Street_Map`, the same provider as the satellite layer, which is built on OpenStreetMap DATA and credits it in the attribution, so the surveyors are still credited over a CDN provisioned for being used. The referrer is sent again. A unit test asserts no tile URL points at `openstreetmap.org` and an end-to-end test asserts nothing reaches it on the wire, because the easy way to "fix" a blocked tile layer is to point it back at them.
- **A saved location could vanish from the dropdown while the database still held it.** IndexedDB's initial open makes the first read of a session the slowest by a wide margin, so a location saved in the meantime refreshed the list and resolved FIRST, and then the stale first read landed carrying the empty list it had taken before the save. The dropdown went blank over a database that had the location, and nothing retried, because nothing knew it was wrong. Both the picker and the manage dialog now read through one hook that numbers its reads and drops a superseded answer. It surfaced as an intermittent end-to-end failure and would have shown up as a location that "did not save" until the next reload.
- **The app now actually tells you a new version has shipped.** The reload prompt has always existed, but two things kept it from appearing. Nothing ever checked: the service worker was registered without a periodic check, so the browser only looked for a new build on a navigation, and a tab left open across a deploy - the normal way this app is used - never found out. It now checks about once an hour, and again whenever you return to the tab or your connection comes back, both rate-limited so alt-tabbing all afternoon is not a poll loop. And dismissing was permanent for the session: one click and it never mentioned the update again. There is now a **Later** that brings it back in a couple of hours, beside the ✕ that still means "not this session". The prompt also names the version you are running. It is still not a modal, and still never reloads on its own - interrupting an edit is the exact thing it exists to avoid.
- **A zoomed-in drawing keeps a margin under it.** The canvas box had padding on three sides, so zooming in left the bottom ruler and the roll slider's 360° label flush against the pane's bottom edge with nothing beneath them.
- **A flight-path preset you could not get back out of.** *Landing plots* narrowed the waypoints to the landing, but *Drift cast* and *Flight path* set only the lines and the placement and left the waypoints alone — so once you had clicked Landing plots there was no way back to either of the others as they are described, short of re-ticking seven boxes by hand. Every preset now states its selection in full, waypoints included, which is what makes each of them reachable from every other.
- **Multi-instance components under-reported in the drag breakdown.** The per-component drag the engine reports is for **one** instance, and it was being charted and exported as though it were the whole set — so a three-fin set showed a third of its drag. On the default rocket the fins read 19% of total drag when they are in fact 58%, and the missing 39% appeared nowhere. Affected the *Drag breakdown ▸ by component* chart and the drag CSV's per-component columns.
- **An empty view switch after starting a new design on a phone.** Starting or opening a design from the Results tab left you on that tab with no result to show and every view button hidden, because the view and the tab were written apart. Every write of the two now goes through one place that keeps them able to show each other.
- **A finished simulation going nowhere on a phone.** A run selected the flight chart but left you on the Simulate tab, so the chart appeared on the Sketch tab where you were not looking — and displaced your drawing when you got there. The flight views now have their own **Results** tab, which appears once a run has produced one and which a finished run takes you straight to; Sketch keeps the design views. The tab leads with the run's numbers — apogee, rod exit, max speed, landing, downrange — so they sit beside the charts they describe instead of a tab away.
- **Part colors unreachable on a phone.** Settings ▸ Colors hid the 3D part-color swatches below the desktop width, on the assumption that a phone had no 3D model to color. It does — through the Sketch tab — so the section now shows at every width.
- **The bottom tab bar scrolling away on a phone.** The app header's action group and the 2D / 3D / Aero toggle never wrapped, so on a phone the page was half again wider than the screen and could be scrolled sideways — taking the bottom tab bar, which is exactly one screen wide, off with it. Both rows now wrap. The shell is also measured against the *dynamic* viewport, so the tab bar no longer hides under the browser's address bar, and it keeps clear of the iPhone home indicator.
- **Two different motors acting as one in the dashboard.** Motors sharing a manufacturer, common name, and diameter — AeroTech's F67W (White Lightning) and F67C (Classic), several Cesaroni reloads, 14 pairs in all — shared a row identity, so selecting or check-boxing one also took the other, and a compare or combine could pull the wrong thrust curve. The full manufacturer designation is now part of that identity.
- **Freeform fin drawn ahead of where it flies.** A freeform fin whose tip trailing corner overhangs its root was measured to its aftmost point instead of its root chord, so a bottom-/middle-anchored fin was drawn, dragged, and snapped forward of its true station by the overhang. (The property panel and the simulation were always correct — this was a 2D-view display error.)

### Accessibility
- **Aft (head-on) view names its parts.** The aft view was marked `role="img"`, which collapsed it to a single node and hid every part name from screen readers; it's now a labeled group that still exposes each part.

## [0.0.7]

### Fixed — mass, CG & stability now match OpenRocket

Three separate defects were making a design's **on-pad mass, CG, and stability**
read differently from desktop OpenRocket. On a representative dual-deploy,
multi-stage design (`Fireball.ZL1.DD.multi`) they stacked up to **4.86 cal** in
our app versus **3.14 cal** in OpenRocket; with all three fixed, the app now
matches OpenRocket to the caliber-fraction (CG **138.15 cm**, stability **3.14
cal**), component-by-component.

- **On-pad stability now includes the motors.** The loaded (on-pad) CG, CP
  margin, and stability were being computed from the **unloaded** rocket — a
  seated motor's mass was never counted — so stability read too high and CG too
  far forward. This affected *every* design's on-pad readout; it was only obvious
  on rockets with heavy motors. The flight configuration's motor list is now
  refreshed after a motor is seated, so the static analysis includes the
  propellant and casing, matching `MassCalculator.calculateLaunch`.

- **Motor loaded mass (and CG) now read from the motor file, like OpenRocket.**
  The bundled motor catalog took each motor's loaded weight from thrustcurve.org's
  `totalWeightG` **metadata field**, which disagrees with the motor's own
  thrust-curve **file** for **197 of 815 motors** (e.g. AeroTech **J350W: 665 g
  metadata vs 651 g in the file**, Estes **B6: 19.1 → 15.6 g**). OpenRocket loads
  the file; the catalog sync now does too, reading loaded mass from the RASP
  header / RockSim `initWt`, plus the real **CG-vs-time** from RockSim data
  (used instead of a mid-length approximation).

- **Recovery-device mass is now positioned correctly.** A parachute, streamer,
  or shock cord's **packed length** was dropped on import and never applied in the
  engine, so its mass sat at the default 25 mm length instead of its real packed
  length. For a bottom-/top-referenced device this misplaced the CG — a shock
  cord could be tens of millimeters off. The packed length is now read from the
  `.ork` and applied to `ShockCord` / `Parachute` / `Streamer`.
